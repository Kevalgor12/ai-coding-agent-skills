# Technology Decision Matrix

**Head-to-head comparisons for every genuine "pick one of these" decision point among the 44 profiled technologies**

> **Snapshot date: 2026-09-09.** Every fact below is a snapshot in time drawn from the underlying per-technology research (`research/technologies/*.md`), which itself traces to official documentation fetched around that date. Version numbers, benchmark figures, and CVE lists move fast — **re-verify against live sources before treating any specific number here as current.**

## How to read this document

This is a knowledge map, not a skill. It contains no step-by-step instructions for an agent to follow — it exists to inform future skill design by surfacing where the research actually supports a tradeoff claim between competing technologies, and where it does not.

- **Grouping**: technologies are grouped into decision points using the `alternativesTo` relationships recorded in each technology's research file — i.e. only pairs/sets the source documentation (or a clearly labeled inference) itself treats as competing choices.
- **Citations**: every claim keeps the citation exactly as it appeared in the underlying data (`[Source: ...]` or `[Inference from *.md, not an explicit doc statement]`).
- **`[Synthesis: ...]`** marks a connection *I* drew by combining two or more separately-sourced facts that did not individually state the connection. Treat these as hypotheses to verify, not documented facts.
- **`Unresolved`** marks a place where the underlying research does not state a clear tradeoff between the compared technologies — this is called out explicitly instead of being filled in with a plausible-sounding recommendation.
- Facts that are vendor-published benchmarks (marketing figures on a project's own homepage/blog, not independently reproduced) are flagged as such inline; treat them as directional, not authoritative.

## 1. ORM: Mongoose vs. TypeORM vs. Prisma vs. Drizzle ORM

All four are named as mutual alternatives in the underlying research (Mongoose↔Prisma, TypeORM↔Prisma, Prisma↔TypeORM/Drizzle, Drizzle↔Prisma/TypeORM). Mongoose is MongoDB-only (ODM); the other three target SQL databases (ORM). None of the four official doc sets publish a direct feature-comparison page against the others — every "alternative" relationship below is inferred from the *absence* of an official migration guide from that competitor, which the underlying research treats as evidence the two are viewed as peers, not as a documented comparison itself.

| | **Mongoose** | **TypeORM** | **Prisma** | **Drizzle ORM** |
|---|---|---|---|---|
| Target database | MongoDB only | Any SQL DB (+ driver-dependent) | Any SQL DB via driver adapters | PostgreSQL, MySQL, SQLite (+ MSSQL/CockroachDB/SingleStore) |
| Core model | Schema/Model/Document, Active Record style | Both Active Record *and* Data Mapper, developer's choice `[Source: typeorm.io]` | Schema file → generated type-safe client; Prisma 8 emits schema as a JSON "contract" `[Source: prisma.io docs]` | "Headless" library — SQL-proximity query builder; "if you know SQL, you know Drizzle" `[Source: orm.drizzle.team/docs/overview]` |
| Injection defense | `sanitizeFilter` (off by default) wraps `$`-prefixed keys in `$eq` `[Source: mongoosejs.com/docs/api/mongoose.html]` | Parameterized queries/escaped identifiers on all drivers as of v1.0 for schema/DDL paths `[Source: typeorm.io/docs/releases/1.0/release-notes]` | Parameterized queries by default; `$queryRawUnsafe`/`$executeRawUnsafe` flagged as injection-risk if fed unsanitized input `[Source: prisma.io/docs/orm/v7/more/best-practices]` | Automatic parameterization via tagged templates / query builder; `sql.raw()` explicitly "never use ... for user-provided data" `[Source: orm.drizzle.team/docs/sql]` |
| Known CVE | **CVE-2026-42334** (CVSS 7.5): `sanitizeFilter` failed to recursively sanitize inside `$nor`, allowing NoSQL injection even with the flag enabled; patched in ^6.13.9/^7.8.9/^8.22.1/^9.1.6 `[Source: GHSA-wpg9-53fq-2r8h]` | None reported in the underlying data | None reported in the underlying data | None reported in the underlying data |
| Row/document-level security | N/A (document model) | Not documented as a first-class feature in the source data | RLS implemented via a **Client Extension pattern** layered on native Postgres RLS in v6/v7 (not a first-class schema attribute); Prisma 8 adds native RLS as a declared contract feature `[Source: github.com/prisma/prisma-client-extensions; prisma.io/docs/orm/prisma-client/client-extensions]` | RLS is **first-class**: `pgTable.withRLS()` + `pgPolicy()`, with provider-specific integrations for Neon and Supabase `[Source: orm.drizzle.team/docs/rls]` |
| Vulnerability-report scope | — | Explicitly scoped to *data-value* injection only; identifier/SQL-expression-position input, hostile schema/config control, and validation bypasses are **out of scope**, left to the developer `[Source: github.com/typeorm/typeorm/security/policy]` | — | — |
| N+1 mitigation | `.populate()` with `select` to limit fields; avoid `perDocumentLimit` `[Source: mongoosejs.com/docs/populate.html]` | `leftJoinAndSelect`/`innerJoinAndSelect` or `relations` object `[Source: typeorm.io/docs/performance-optimization/introduction]` | `include` for eager-load, or batch with `WHERE id IN (...)`; `relationLoadStrategy:'join'` (version-unconfirmed) `[Source: prisma.io/docs/orm/v7/more/best-practices]` | Not explicitly documented as an N+1-specific feature in the source data; relational-query performance guidance instead centers on indexing FK columns `[Source: orm.drizzle.team/docs/relations]` |
| Query-result caching | N/A documented | `cache:true` (default 1000ms) with Redis/IORedis backend supported; DB-table cache also available `[Source: typeorm.io/docs/query-builder/caching]` | No built-in result cache described; "Query Insights" (Prisma Postgres) identifies slow queries instead `[Source: prisma.io/docs/query-insights]` | Experimental `.​$withCache()` / global cache mode integrating Upstash Redis, auto-invalidating on mutation `[Source: orm.drizzle.team/docs/cache]` |
| Raw perf positioning | "save() sends only modified paths" (partial update) `[Source: mongoosejs.com/docs/documents.html]` | Cursor-based pagination recommended over offset/limit for large sets `[Source: typeorm.io/docs/performance-optimization/pagination]` | Vendor claims **~90% of raw PostgreSQL query throughput** for Prisma 8 — unverified methodology `[Source: prisma.io/docs/orm]` | "Thin TypeScript layer on top of SQL with **almost 0 overhead**" — vendor framing, not an independent benchmark `[Source: orm.drizzle.team/docs/overview]` |
| Official test-framework stance | **Explicitly discourages Jest** — "We strongly recommend using a different testing framework, like Mocha" `[Source: mongoosejs.com/docs/jest.html]`; if Jest must be used, `testEnvironment:'node'` is required | **No dedicated official testing guide exists**; all discovered Jest/SQLite guidance is third-party `[Inference from typeorm.md]` | Jest + `ts-jest` + `jest-mock-extended` (`mockDeep()`) is the **documented** unit-test pattern; integration testing against a real DB is presented as a separate complementary approach `[Source: prisma.io/docs/orm/prisma-client/testing/unit-testing]` | **PGlite** ("Postgres in WASM," ~2.6MB gzipped) is an officially documented in-memory/persistent Postgres for tests, no Docker/VM needed; `drizzle.mock()` gives a typed DB with no real connection; `drizzle-seed` for reproducible fake data `[Source: orm.drizzle.team/docs/connect-pglite, /docs/goodies, /docs/seed-overview]` |

**Unresolved:** none of the four sources make a direct, apples-to-apples performance claim against a *named* competitor from this list — Prisma's "~90% of raw PostgreSQL" and Drizzle's "almost 0 overhead" are both self-referential, not comparative, so the underlying research does not support ranking Prisma vs. Drizzle vs. TypeORM on raw throughput.

**`[Synthesis: combining Mongoose's explicit Jest discouragement with Prisma's Jest-first testing guide and Drizzle's PGlite+Vitest pattern]`** — the four ORMs sit on visibly different testing philosophies: Mongoose steers *away* from the most popular JS test runner entirely, Prisma leans on mocking the client, and Drizzle leans on running a real (if embedded) Postgres. A skill scaffolding "add tests for this ORM" cannot use one universal test-setup script across all four without checking which ORM is in use first.

## 2. Database model: PostgreSQL vs. MySQL vs. MongoDB vs. ClickHouse

PostgreSQL and MySQL are named as mutual migration targets (`postgresql.md`/`MongoDB` docs each name the other); MongoDB explicitly positions itself as a document-model alternative to relational schemas via its Relational Migrator tool (source: MongoDB, not PostgreSQL/MySQL — the relationship is asymmetric in the data); ClickHouse explicitly positions itself as the OLAP successor once a Postgres/MySQL OLTP workload shifts toward analytical queries.

| | **PostgreSQL** | **MySQL** | **MongoDB** | **ClickHouse** |
|---|---|---|---|---|
| Model | Relational (SQL), MVCC | Relational (SQL), Oracle-developed | Document (BSON) | Columnar OLAP |
| Positioned as alternative to | — | — (no `alternativesTo` recorded for MySQL itself in the source data) | PostgreSQL, MySQL, Oracle, SQL Server — via "Relational Migrator," explicitly framed as a migration *from* relational *to* document `[Source: mongodb.com/docs/relational-migrator]` | PostgreSQL, MySQL — explicitly framed as the OLTP-to-OLAP migration once workload shifts to analytical GROUP BY-style queries `[Source: clickhouse.com/docs/migrations/postgresql/overview]` |
| Auth methods | `trust`, password, `scram-sha-256`, GSSAPI, LDAP, RADIUS, cert, PAM, and (new in v18) **OAuth 2.0** via SASL OAUTHBEARER `[Source: postgresql.org/docs/current/auth-methods.html]` | `caching_sha2`, SHA-256, PAM, LDAP, Kerberos, OpenID Connect, WebAuthn; `mysql_native_password` disabled by default since 8.4.0 `[Source: dev.mysql.com/doc/refman/9.7/en/security.html]` | SCRAM (default), X.509, LDAP, Kerberos, OIDC/OAuth 2.0 `[Source: mongodb.com/docs/manual/security]` | SQL-driven RBAC (`CREATE USER`/`GRANT`/`REVOKE`) across 5 entity types (Users, Roles, Row Policies, Settings Profiles, Quotas); no privilege "lifetime" — privileges on a dropped table persist until explicitly revoked `[Source: clickhouse.com/docs/operations/access-rights]` |
| Row-level security | Native `ENABLE ROW LEVEL SECURITY` + `CREATE POLICY`; fails closed (deny-all with no policy) `[Source: postgresql.org/docs/current/ddl-rowsecurity.html]` | Not documented in the source data | RBAC is documented, but is **not on by default** on self-managed deployments — must be explicitly enabled `[Source: mongodb.com/docs/manual/security]` | Row Policies are one of the 5 RBAC entity types `[Source: clickhouse.com/docs/operations/access-rights]` |
| Encryption at rest | Not directly addressed in the source data (TLS in-transit documented) | Documented Keyring with file/KMIP/AWS KMS/HashiCorp Vault backends `[Source: dev.mysql.com/doc/refman/9.7/en/security.html]` | **Enterprise-only** for self-managed; Atlas offers Customer Key Management; Queryable Encryption/CSFLE for per-field encryption `[Source: mongodb.com/docs/manual/security]` | Config-file secrets can be symmetrically encrypted via `encrypted_by` `[Source: clickhouse.com/docs/operations/configuration-files]` |
| Transaction/write model | Full ACID, four SQL-standard isolation levels via MVCC/SSI `[Source: postgresql.org core concepts]` | Full ACID (InnoDB) | **Atomic single-document** writes only | **Deliberate trade-off: no general transaction support**; inefficient row-level update/delete and point queries — an explicit design choice, not a gap `[Source: clickhouse.com core concepts]` |
| Query performance tool | `EXPLAIN (ANALYZE, BUFFERS)` `[Source: postgresql.org/docs/current/using-explain.html]` | `EXPLAIN` (incl. JSON format) + Performance Schema/sys schema `[Source: dev.mysql.com/doc/refman/9.7/en/optimization.html]` | Index-based (ESR rule: Equality, Sort, Range for compound indexes); sharding recommended over vertical scaling for write-heavy workloads `[Source: mongodb.com/docs/manual/applications/indexes; .../analyzing-mongodb-performance]` | Sparse primary index (1 mark per ~8,192-row granule) keeps huge-dataset keys memory-resident `[Source: clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree]` |
| Headline v18/8.0/recent perf claim | v18: async I/O subsystem, **up to 3x** improvement reading from storage (vendor-cited) `[Source: postgresql.org/about/news/postgresql-18-released-3142]` | InnoDB buffer pool is "the primary tunable" `[Source: dev.mysql.com/doc/refman/9.7/en/optimization.html]` | WiredTiger cache defaults to `max(50% × (RAM − 1GB), 256MB)` — a first-order performance factor `[Source: mongodb.com/docs/manual/core/wiredtiger]` | Batch inserts of 10,000–100,000 rows recommended; async inserts shift buffering server-side `[Source: clickhouse.com/docs/best-practices/selecting-an-insert-strategy]` |
| Anti-pattern called out by own docs | Restoring `pg_dump` from an untrusted source is dangerous — dumps contain superuser code executed on restore `[Source: postgresql.org/docs/current/app-pgdump.html]` | Full table scans / overly wide data types `[Source: dev.mysql.com/doc/refman/9.7/en/optimization.html]` | Excessive `$lookup` (cross-collection joins) — a signal that data should be denormalized instead, since MongoDB's design is embedding-first `[Source: mongodb.com/docs/manual/data-modeling/design-antipatterns]` | Nullable(T) columns "almost always negatively affects performance" — a hidden UInt8 is-null mask on every access `[Source: clickhouse.com/docs/optimize/avoid-nullable-columns]` |
| Application-test methodology | **Explicit gap**: no official app-level testing guidance (ephemeral DBs, fixtures) — delegated to ORMs/tooling `[Source: postgresql.org, Section 9 of source doc]` | **Explicit gap**: reference manual has no first-party app-testing guidance `[Source: dev.mysql.com/doc/dev/mysql-server/latest/PAGE_MYSQL_TEST_RUN_PL.html]` | Officially documents a lightweight replica-set-for-testing topology, and ships `mongodb/mongodb-atlas-local` Docker image for local dev/test (**does not mention Testcontainers**) `[Source: mongodb.com/docs/manual/tutorial/deploy-replica-set-for-testing; .../atlas-cli-deploy-docker]` | Own test suite (functional/.sql scripts, Docker-based integration tests, gtest unit tests, sanitizers/fuzzing) documents testing **ClickHouse itself**, not application code against it — an explicit gap for app developers `[Source: clickhouse.com/docs/resources/develop-contribute/contribute/tests]` |

**Unresolved:** the underlying research does not state a direct performance comparison number between PostgreSQL and MySQL, or between either and MongoDB, for equivalent workloads — each technology's performance section is self-referential (its own tuning levers), not comparative.

**`[Synthesis: combining MongoDB's "excessive $lookup is an anti-pattern" note with ClickHouse's "no general transaction support" trade-off and PostgreSQL's ACID/MVCC core]`** — the four form a rough spectrum of *normalization tolerance*: PostgreSQL is built to make heavily normalized, joined, transactional schemas fast; MongoDB's own docs steer users *away* from join-heavy patterns toward embedding; ClickHouse abandons transactional/point-query support entirely in exchange for columnar analytical scan speed. This is a coherent narrative across the three research docs even though none of them states it explicitly as a unified spectrum.

## 3. Backend framework: Fastify vs. Express

Fastify's own homepage runs a head-to-head benchmark naming Express directly; Express's docs name Fastify (along with Koa/Hapi) as a framework it provides no migration guide from.

| | **Fastify** | **Express** |
|---|---|---|
| Homepage benchmark (req/s) | **~88,171** (v5.11.3) — vendor-published, not independently reproduced `[Source: fastify.dev]` | ~57,936 (v5.2.1) — same benchmark, summarized by Fastify as "roughly 1.5x" its own throughput `[Source: fastify.dev]` |
| Prototype-pollution defense | **Built-in, on by default**: `onProtoPoisoning`/`onConstructorPoisoning` both default to `'error'`; v5 route-params object no longer inherits `Object.prototype` `[Source: fastify.dev/docs/latest/Reference/Server; .../Guides/Migration-Guide-V5]` | Not a framework-level feature; relies on app-level middleware (e.g. `helmet`) for hardening |
| Error-message leakage | Default handler forwards error messages **verbatim to clients**, not sanitized by environment — can leak DB schema/query details unless the app sets a custom `setErrorHandler` `[Source: fastify.dev/docs/latest/Reference/Errors]` | Default handler returns full `err.stack` when `NODE_ENV` is not `"production"`, generic message otherwise — **environment-aware by default** `[Source: expressjs.com/en/guide/error-handling.html]` |
| Response-shape control as security | Explicit response JSON Schemas are documented as **both** a security control (prevents accidental field disclosure) and a performance one `[Source: fastify.dev/docs/latest/Reference/Validation-and-Serialization]` | No equivalent schema-enforcement mechanism documented |
| Documented CVE history in source data | Vulnerability policy covers core + official `@fastify/*` plugins only, excludes app code/3rd-party deps/`insecureHTTPParser:true` deployments `[Source: github.com/fastify/fastify/blob/main/SECURITY.md]` | Specific fixed CVEs named: **CVE-2024-43796** (XSS in `res.redirect`, fixed 4.20.0) and **CVE-2024-29041** (open-redirect in `res.location`/`res.redirect`, fixed 4.19.0/4.19.1) `[Source: expressjs.com/en/advanced/security-updates.html]` |
| Recommended security middleware | Response-schema validation is native; Ajv v8 handles input | `helmet` (security headers), `express-session` over `cookie-session`, `rate-limiter-flexible` (brute-force), `safe-regex` (ReDoS) — all **third-party, docs-recommended** `[Source: expressjs.com/en/advanced/best-practice-security.html]` |
| Validation/serialization performance | Ajv v8 + `fast-json-stringify` **compile** schemas into specialized functions ahead of request handling (not interpreted at runtime); schemas dedupable via `addSchema()` `[Source: fastify.dev/docs/latest/Reference/Validation-and-Serialization]` | `NODE_ENV=production` caches view templates/CSS and cites **roughly 3x** improvement from Express's own benchmarks `[Source: expressjs.com/en/advanced/best-practice-performance.html]` |
| Recommended production topology | Behind a reverse proxy (Nginx/HAProxy) — running Fastify directly on the internet is called an "anti-pattern and extremely bad practice" `[Source: fastify.dev/docs/latest/Guides/Recommendations]` | Reverse proxy also recommended, for TLS termination, gzip, and static-file offload; `PM2`/cluster module for one-process-per-core `[Source: expressjs.com/en/advanced/best-practice-performance.html]` |
| Official testing primitive | `fastify.inject()` (built on `light-my-request`) simulates HTTP requests **in-process, no real socket**, guaranteeing all plugins have booted `[Source: fastify.dev/docs/latest/Guides/Testing]` | **No official first-party testing guide exists**; `supertest` is community-standard but not expressjs-org-maintained, so excluded from official-doc citations per this project's sourcing rules `[Source: research/technologies/express.md Section 9]` |

**Unresolved:** the benchmark numbers are Fastify's own vendor-published figures; the underlying research flags them explicitly as "not independently reproduced," so a claim of "Fastify is 1.5x Express" should be treated as directional marketing, not a verified fact.

## 4. Frontend framework: React vs. Vue vs. Angular

Angular's own research doc infers React and Vue as its peer alternatives (no official Angular migration-from-a-different-framework guide exists); Vue explicitly contrasts its runtime reactivity model against Svelte's compile-time model (Svelte is outside the 44-technology list, noted for completeness). React records no `alternativesTo` entries of its own in the source data.

| | **React** | **Vue** | **Angular** |
|---|---|---|---|
| Reactivity model | Hooks (`useState`, position-in-render-tree) | Proxy-based automatic dependency tracking; explicitly rejected a compile-time "Reactivity Transform" proposal in favor of the runtime approach, contrasting with Svelte `[Source: vuejs.org/guide/extras/reactivity-in-depth]` | Signals (`signal()`/`computed()`/`effect()`) |
| Default XSS mitigation | None built-in beyond standard JSX escaping; `dangerouslySetInnerHTML` is the documented primary XSS vector, mitigated only by developer discipline `[Source: react.dev/reference/react-dom/components/common]` | **Automatic HTML-escaping** of `{{ }}` interpolations and dynamic attribute bindings, no developer action needed; `v-html` is the explicit bypass, "never on user-provided content" `[Source: vuejs.org/guide/best-practices/security]` | **Auto-sanitizes all template bindings** by security context (HTML/Style/URL/Resource URL) by default; `DomSanitizer.bypassSecurityTrust*` explicitly can "introduce security vulnerabilities" `[Source: angular.dev/best-practices/security]` |
| Built-in CSRF/XSRF handling | Not addressed (React has no HTTP client) | Explicitly framed as a **backend responsibility**, not something Vue addresses — points to OWASP cheat sheets `[Source: vuejs.org/guide/best-practices/security]` | **`HttpClient` includes CSRF protection by default** via an interceptor reading the `XSRF-TOKEN` cookie and setting `X-XSRF-TOKEN` `[Source: angular.dev/best-practices/security]` |
| Critical recent CVE | **CVE-2025-55182** (CVSS 10.0, unauthenticated RCE) in RSC Server Function payload deserialization, affecting React 19.0–19.2.0 and downstream frameworks incl. Next.js; a **follow-up incomplete patch** required a second fix (**CVE-2026-23864**) `[Source: react.dev/blog/2025/12/03 and /2025/12/11]` | None reported in the underlying data | None reported in the underlying data |
| Compiler/optimization story | React Compiler (stable v1.0, Oct 2025): auto-memoization, Meta-internal reports up to **12%** faster loads, **2.5x** faster on some interactions `[Source: react.dev/blog/2025/10/07/react-compiler-1]` | Compiler-informed VDOM: static hoisting, bitwise Patch Flags, Tree Flattening — also **accelerates SSR hydration** via "partial hydration at the template level" `[Source: vuejs.org/guide/extras/rendering-mechanism]` | Zoneless change detection (stable/default v21+): fewer unnecessary change-detection cycles, "improved Core Web Vitals" from removing Zone.js monkey-patch overhead `[Source: angular.dev/guide/zoneless]`; v22+ defaults undecorated components to `OnPush` |
| Bundle-size lever | Resource preloading APIs (`prefetchDNS`, `preconnect`, `preload`, `preinit`, React 19+) `[Source: react.dev/blog/2024/12/05/react-19]` | Tree-shaking saves ~14kb; precompiling templates saves another ~14kb; `petite-vue` (~6kb) exists for progressive-enhancement scenarios `[Source: vuejs.org/guide/best-practices/performance]` | `@defer` template blocks are the primary lazy-loading/code-splitting primitive (idle/viewport/interaction/hover/timer triggers) `[Source: angular.dev/guide/templates/defer]` |
| Default/recommended unit-test runner | No official recommendation — closest is a deprecation-warning page pointing to `@testing-library/react`; `react-test-renderer` explicitly **deprecated** `[Source: react.dev/warnings/react-test-renderer]` | **Vitest**, "created and maintained by members of the Vue / Vite team" `[Source: vuejs.org/guide/scaling-up/testing]` | **Vitest is now the default** for new CLI projects (v21+), **replacing Karma**; Karma/Jasmine remain supported for existing projects with a dedicated migration guide `[Source: angular.dev/guide/testing]` |
| Recommended E2E tool | Not prescribed by React itself | Playwright (praised for debugging, cross-browser) or Cypress `[Source: vuejs.org/guide/scaling-up/testing]` | Playwright or WebdriverIO, used alongside default Vitest `[Source: angular.dev/guide/testing]` |

**Unresolved:** the research contains no direct official statement from any of the three frameworks comparing its own performance or bundle size numerically against either of the other two — every performance claim above is self-referential (react.dev talks about React, vuejs.org about Vue, angular.dev about Angular).

**`[Synthesis: combining Vue's default auto-escaping, Angular's default auto-sanitization, and React's lack of a built-in equivalent]`** — Vue and Angular both ship a default-on template-output sanitizer as a documented framework feature, while React's docs frame `dangerouslySetInnerHTML` risk mitigation as entirely the developer's responsibility with no framework-level auto-escaping mechanism called out in the source data (JSX's standard text-node escaping is implicit, not documented as a named security feature the way Vue's and Angular's are). This is a genuine security-posture difference the individual docs state piecemeal but never compare directly.

## 5. Meta-framework: Next.js vs. Nuxt

Next.js documents a migration path *from Vite* (a React+Vite setup), not from Nuxt. Nuxt's `alternativesTo` entry for Next.js is explicitly flagged in the source data as **not officially stated** — it is inferred purely from Nuxt's feature set mirroring what Next.js does for React (SSR-by-default, file-based routing, hybrid rendering, built-in API routes).

| | **Next.js** (React) | **Nuxt** (Vue) |
|---|---|---|
| Framework relationship claim | Documents an official **Vite → Next.js** migration guide `[Source: nextjs.org/docs/app/guides/migrating]` | No official comparison to Next.js exists; the entry is an **inference**, not a documented claim `[Inference from nuxt.md, not an explicit doc statement]` |
| Default rendering | App Router (RSC) + Pages Router coexist | "Universal Rendering" (SSR + hydration) is the default, plus Client-Side and Hybrid modes |
| Per-route caching control | Cache Components model (`"use cache"` + Suspense) → Partial Prerendering | `routeRules` (`swr`, `isr`, `prerender`, `ssr:false` per route); deploys natively to Netlify/Vercel platform rules, but **unavailable when output is via static `nuxt generate`** `[Source: nuxt.com/docs/4.x/guide/concepts/rendering]` |

## 6. Realtime networking: WebSocket API vs. Socket.IO vs. WebRTC

The WebSocket API's own MDN documentation scopes Socket.IO as a separate userland library built *on top of* WebSocket (among other transports); Socket.IO's docs confirm this directly, describing itself as "not a raw WebSocket implementation." WebRTC serves a different use case (peer-to-peer media/data) and carries no recorded `alternativesTo` — it is included here because it shares the "realtime-networking" category, not because the data frames it as a substitute for the other two.

| | **WebSocket API** | **Socket.IO** | **WebRTC** |
|---|---|---|---|
| Relationship | Raw, standard, browser-native two-way channel | Protocol/framework layer *on top of* transports (one of which is WebSocket), adding reconnection/ack/broadcast/multiplexing `[Source: socket.io/docs/v4]` | Peer-to-peer (no server relay for media once connected); no `alternativesTo` recorded |
| Origin/CSRF-class defense | Servers should validate the `Origin` header on handshake (browsers always send it); only defends against **browser-originated** attacks since non-browser clients can forge `Origin` `[Source: developer.mozilla.org/.../Writing_WebSocket_servers]` | **CORS must be explicitly configured** (disabled/restricted by default since v3); CORS only covers the long-polling transport, so `allowRequest` is recommended as an additional handshake check `[Source: socket.io/docs/v4/handling-cors]` | Camera/mic access governed by the separate Media Capture and Streams API's consent model `[Source: w3.org/TR/webrtc]` |
| Transport-layer masking/hijack defense | RFC 6455 **mandates** client-to-server frame masking with a fresh random key per message — required even over `wss`/TLS, since masking is a distinct wire-level protection, not a TLS substitute `[Source: rfc-editor.org/rfc/rfc6455]` | N/A (built atop WebSocket/HTTP) | DTLS-SRTP mandated for media; self-signed certs required (not reusable indefinitely), must match document origin `[Source: w3.org/TR/webrtc]` |
| Documented DoS control | Only generic guidance ("a server can deny connections that attempt too many connections"), no specific algorithm/threshold prescribed `[Source: developer.mozilla.org/.../Writing_WebSocket_servers]` | `maxHttpBufferSize` (default **1 MB**, deliberately tightened from 100 MB in 2.x) acts as a basic DoS guard `[Source: socket.io/docs/v4/server-options]` | Not addressed as a DoS-specific control in the source data |
| Backpressure handling | **Documented core limitation**: no built-in backpressure — fast producers can overrun a slow consumer, causing unbounded memory growth; `WebSocketStream` (Streams API) exists specifically to close this gap `[Source: developer.mozilla.org/.../WebSockets_API]` | `socket.volatile.emit()` trades reliability for reduced buffering — the documented mechanism for loss-tolerant, performance-sensitive messages `[Source: socket.io/docs/v4/emit-cheatsheet]` | Outbound data-channel data auto-buffers; apps should monitor `bufferedamountlow` to avoid excess memory `[Source: developer.mozilla.org/.../Using_data_channels]` |
| Compression trade-off | `permessage-deflate` reduces payload size but carries a documented **CRIME-style compression-oracle risk** over TLS with secret data (RFC 7692 flags this explicitly) `[Source: rfc-editor.org/rfc/rfc7692]` | WebSocket `perMessageDeflate` defaults to **false**, while long-polling `httpCompression` defaults to **true** — not uniform, an explicit CPU-vs-bandwidth trade-off `[Source: socket.io/docs/v4/server-options]` | Codec choice is the analogous lever: AV1/VP9 named as more bandwidth-efficient than VP8/H.264 at equivalent quality `[Source: developer.mozilla.org/.../WebRTC_codecs]` |
| Official testing/mocking story | **None found** — no official unit/integration test framework, mocking library, or conformance suite for API *consumers* `[Source: developer.mozilla.org/.../WebSockets_API]` | Official testing guide demonstrates the same pattern across **Jest, Mocha, Tape, and Vitest**, with a documented `waitFor()` helper and `emitWithAck()` pattern `[Source: socket.io/docs/v4/testing]` | CI/headless guidance via Chrome flags (`--use-fake-ui-for-media-stream`, etc.) and Firefox prefs (`media.navigator.streams.fake`) to run without real devices `[Source: webrtc.org/getting-started/testing]` |

**Unresolved:** the research contains no quantified performance comparison (latency/throughput) between raw WebSocket and Socket.IO for equivalent workloads — only that Socket.IO's own docs concede WebSocket has "materially lower per-message overhead than HTTP long-polling," without a number for WebSocket vs. Socket.IO-over-WebSocket specifically.

## 7. API spec tooling: OpenAPI vs. GraphQL (plus Swagger)

OpenAPI's own FAQ states it and GraphQL "solve similar problems in slightly different ways." Swagger is not an alternative to OpenAPI — it is the tooling (UI/Editor/Codegen) that *consumes and visualizes* an OpenAPI/Swagger specification; its recorded alternative is OpenAPI Generator, a community fork of Swagger Codegen.

| | **OpenAPI** | **GraphQL** |
|---|---|---|
| Model | Discrete REST-style operations per resource/URL | Single-endpoint graph-query model `[Source: openapis.org/faq]` |
| Versioning strategy | Implicit via URL/path versioning conventions (`/v1`, `/v2`) — external to the spec itself | Schema evolution (adding fields/types without breaking existing clients) is presented as GraphQL's **alternative** to REST-style versioning `[Source: graphql.org/learn/schema-design]` |
| Security scheme model | Five types (`apiKey`, `http`, `mutualTLS`, `oauth2`, `openIdConnect`) defined under `components.securitySchemes`, referenced by name, applicable globally or per-operation `[Source: learn.openapis.org/specification/security.html]` | No equivalent formal security-scheme object; relies on transport-level (HTTPS/TLS) plus app-layer authorization |
| Documented DoS exposure | Not called out as an inherent spec-level risk (spec is static documentation, not runnable) | **Explicitly called out**: a single endpoint can express operations of widely varying cost (cyclic/deeply-nested queries, alias-based breadth, batching) `[Source: graphql.org/learn/security]` |
| Recommended DoS mitigation | N/A | Enforce max query depth, stricter limits for nested list fields, cap top-level fields/aliases, cap batched ops per request; **traditional fixed-window rate limiting is called out as insufficient** since request count can't distinguish cheap from expensive query shapes `[Source: graphql.org/learn/security]` |
| Introspection posture | N/A | Disabling introspection in production is common practice, but many dev tools depend on it — selective disabling (trusted-document allowlisting) recommended over blanket disabling `[Source: graphql.org/learn/introspection; graphql-js.org/docs/going-to-production]` |
| N+1-class performance issue | N/A (not applicable to a static resource-per-URL model in the same way) | **The most common documented GraphQL performance issue**, from the per-field resolver execution model; DataLoader-style batching is the standard fix `[Source: graphql.org/learn/performance]` |
| Caching strategy | Standard HTTP caching applies naturally (GET + cache headers) | Persisted queries (hash instead of full query text) enable HTTP/CDN caching of otherwise-uncacheable POST requests; multi-layer caching (resolver, HTTP/CDN, schema-build, Redis) recommended for `graphql-js` deployments `[Source: graphql.org/learn/performance; graphql-js.org/docs/going-to-production]` |
| Testing/contract-verification story | Mock servers generated directly from an OpenAPI Description are a **primary documented use case**; best practice recommends wiring the OAD into CI to verify implementation matches the spec `[Source: learn.openapis.org/introduction.html; .../best-practices.html]` | **No official testing methodology guide could be located** — `www.graphql-js.org/docs/testing/` returned HTTP 404 during the underlying research pass; the closest is an inference that the generic `graphql({schema, source, rootValue})` function is callable directly from a test runner `[Source: graphql.org — gap noted, https://www.graphql-js.org/docs/testing/ returning 404]` |
| Recent spec evolution | OAS 3.2.0 adds OAuth 2.0 Device Authorization Flow and `oauth2MetadataUrl` for automatic discovery, narrowing the gap with OpenID Connect discovery `[Source: openapis.org/blog/2025/09/23/announcing-openapi-v3-2]` | Not applicable — GraphQL spec evolution not covered comparably in the source data |

**Swagger (tooling, not a spec alternative):**

| | Detail |
|---|---|
| Relationship to OpenAPI | Consumes/visualizes an OpenAPI (formerly "Swagger") document; three distinct official tools — UI, Editor, Codegen `[Source: swagger.io tooling docs]` |
| Alternative | **OpenAPI Generator** — a well-known community fork of Swagger Codegen; no official Swagger-side migration guidance toward it exists `[Source: swagger-api/swagger-codegen README]` |
| Notable CVE | **GHSA-qrmm-w75w-3wpx**: attacker-crafted `?url` query-string value could point a hosted Swagger UI at an attacker-controlled spec (SSRF-adjacent/phishing); fixed by disabling query-string spec overrides by default in `swagger-ui`/`swagger-ui-dist`/`swagger-ui-react` **>= 4.1.3** `[Source: github.com/advisories/GHSA-qrmm-w75w-3wpx]` |
| EOL/patch policy | Only the **5.x line** receives security patches; 4.x EOL Aug 2023, 3.x EOL Nov 2021, 2.x EOL 2017 `[Source: github.com/swagger-api/swagger-ui/security]` |
| Production misconfiguration risk | Never set `clientSecret` in `initOAuth()` in production — exposes a confidential OAuth secret to every visitor `[Source: swagger.io/docs/open-source-tools/swagger-ui/usage/oauth2]` |

**Unresolved:** OpenAPI's own security-scope statement explicitly says deployment-level mechanics (key exchange, certificate management) are **out of spec scope** — so "which is more secure, OpenAPI or GraphQL" is not a question the underlying research can answer; the two operate at different layers (static contract vs. runtime query language) with GraphQL's larger attack surface being a function of its dynamic query model, not a documented security ranking.

## 9. Styling: Sass vs. Tailwind CSS vs. plain CSS

Tailwind v4 explicitly drops preprocessor support and names Sass (along with Less/Stylus) as unnecessary under its native-CSS-feature architecture. CSS itself (native nesting) is documented by MDN as a *migration target away from* Sass. Plain CSS names Sass as its own alternativesTo target.

| | **Sass** | **Tailwind CSS** | **CSS (native)** |
|---|---|---|---|

| Security incident | Tar-permission bug: standalone `.tar.gz` archives, `sass-embedded` npm (<1.54.5), and RubyGems non-native package (<1.56.2) shipped incorrect Unix file permissions, allowing executable overwrite by any local user against a root-owned install — **npm `sass`, Homebrew, and Chocolatey users were unaffected** `[Source: sass-lang.com/blog/security-alert-tar-permissions]` | Play CDN flagged unsuitable for production, but for **performance** reasons (large JS payload, runtime style application/FOUC) — docs stop short of calling it a security risk `[Source: tailwindcss.com/docs/installation/play-cdn]` | `:visited` selector history-sniffing mitigation: `getComputedStyle()` reports visited links as never-visited; only color-related properties may be styled inside `:visited` rules `[Source: developer.mozilla.org/.../Privacy_and_:visited]` |

| Combining-technologies penalty | N/A (Tailwind explicitly drops Sass support in v4) | Combining Tailwind with **CSS Modules** causes slower builds because "Tailwind runs per module" instead of one global stylesheet pass `[Source: tailwindcss.com/docs/compatibility]` | N/A |
| Official testing story | **No dedicated "Testing" section or officially maintained testing framework**; `sass:meta` introspection module is the closest building block, but is framed as inner-workings introspection, not a test framework `[Source: sass.md §9 Testing]` | **No dedicated first-party testing guide** — as a build-time CSS-generation tool it has no component behavior to unit-test; closest QA tooling is editor-time IntelliSense linting `[Inference from tailwind.md, not an explicit doc statement]` | Conformance testing lives in the shared **web-platform-tests (WPT)** repo, used by browser vendors — this is browser-conformance testing, **not application testing**; W3C CSS Validator is the author-facing tool `[Source: web-platform-tests.org; developer.mozilla.org Debugging_CSS]` |

## 13. Cross-cutting synthesis

These are inferences drawn by combining facts from **multiple** decision points above that no single source states as a unified claim.

- **`[Synthesis: combining the ORM (§1), database (§2), and Testing (§10) tables]`** — a project's ORM choice constrains its realistic test-database strategy more than its database engine does. Drizzle ships an official in-memory Postgres path (PGlite) with no Docker/VM required; Prisma leans on mocking the client entirely; TypeORM has **no official testing guidance at all**; and Mongoose actively steers users away from the most common JS test runner (Jest). Meanwhile PostgreSQL, MySQL, and ClickHouse all leave *application*-level testing as an explicit documented gap, delegating it to whichever ORM sits on top — so the ORM layer, not the database layer, is where a skill's test-scaffolding logic actually needs to branch.
- **`[Synthesis: combining Fastify's built-in prototype-pollution defense (§3) with the Express security-middleware list (§3) and Next.js's/Nuxt's own coordinated security releases (§5)]`** — there is a visible pattern across the newer/more prescriptive frameworks (Fastify, Angular, Vue, Next.js's Server Actions encryption) of moving a security control from "developer must remember to add a library" into "framework default," while the older/more minimal frameworks (Express, React) consistently document the equivalent protection as a *recommended third-party addition* rather than a built-in. This same axis reappears in the component-library comparison (§8: MUI vs. shadcn/ui's `sx`/CSP nonce requirement vs. shadcn/ui's zero-CSS-in-JS-runtime model) and in the styling comparison (§9: Tailwind's zero-JS-runtime model vs. Sass's historical implementation-permission CVE). A skill layer that wants to recommend "secure by default" stacks could use "does the framework document a built-in default, or only a recommended add-on" as a genuinely data-backed differentiator, distinct from marketing claims.
- **`[Synthesis: combining the GitHub Actions cache-poisoning note (§12) with Docker's layer-caching guidance (§2/Containerization data) and Vite's dependency-caching guidance (§11)]`** — caching shows up as a recurring *security* consideration, not just a performance one, across three independent tool categories: GHA restricts cache writes on low-trust triggers (`pull_request_target`) to prevent a poisoned cache being trusted by a later privileged run; Docker's `ARG`/`ENV` build-check rule exists because secrets can leak into image-layer history; and none of the ORM/database sources raise caching as a security topic at all (their caching guidance — TypeORM's Redis cache, Prisma's connection pooling, ClickHouse's async inserts — is purely performance-framed). This suggests build/CI-layer caching carries security research attention that data/query-layer caching in this dataset does not, which may reflect where the underlying documentation authors chose to focus rather than an actual absence of risk in query-result caching.
