## 1. Secrets & Credential Management

| Concern | Technology | Detail | Citation |
|---|---|---|---|
| Env-var leakage to client bundles | Vite | Only `VITE_`-prefixed environment variables are exposed to client code after bundling; secrets/API keys must never use this prefix since they end up readable in shipped client bundles — secret handling belongs server/edge-side. | [Source: https://vite.dev/guide/env-and-mode] |
| Secrets in image metadata | Docker | Docker Build Checks include a rule preventing sensitive data from being placed in `ARG`/`ENV` instructions, since both can leak into image history/metadata. | [Source: https://docs.docker.com/reference/build-checks/] |
| CI secret handling | GitHub Actions | Store all sensitive values as GitHub secrets (never plaintext in workflow YAML); automatic log redaction is "best-effort" ("automatic redaction is not guaranteed"), so use `::add-mask::VALUE` to mask additional runtime values. | [Source: https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions] |
| Structured secrets don't mask reliably | GitHub Actions | Treating structured data (JSON/XML/YAML blobs) as a single GitHub secret is discouraged since log redaction does exact-string matching and encoded/transformed values will not be reliably masked; each derived value should itself be a registered secret. | [Source: https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions] |
| Least-privilege CI tokens | GitHub Actions | Set `GITHUB_TOKEN` default permissions to read-only content access at minimum, elevate only per-job, and pin third-party actions to full-length commit SHAs — "currently the only way to use an action as an immutable release." | [Source: https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions] |
| Credential-free cloud auth | GitHub Actions | OIDC lets workflows authenticate to cloud providers (AWS, Azure, GCP, HashiCorp Vault) using per-job auto-expiring JWTs exchanged for short-lived cloud credentials, eliminating long-lived cloud secrets stored in GitHub. | [Source: https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect] |
| Registry auth tokens | shadcn/ui | Private component registries require Bearer-token, API-key/custom-header, or query-parameter auth; tokens should live in environment variables (e.g. `REGISTRY_TOKEN` in `.env.local`) rather than being committed, with server-side validation shown for Next.js and Express, plus documented HTTPS enforcement, rate limiting, token rotation, and access logging. | [Source: https://ui.shadcn.com/docs/registry/authentication] |
| OAuth secret exposure in docs UI | Swagger | Never set `clientSecret` in `initOAuth()` in a production deployment — it exposes a confidential OAuth client secret client-side to every visitor of a public docs page. | [Source: https://swagger.io/docs/open-source-tools/swagger-ui/usage/oauth2/] "Never use this parameter in your production environment. | At-rest key management | MySQL | Documented at-rest key management via MySQL Keyring, with backends for file-based keystores, KMIP, AWS KMS, HashiCorp Vault, and OCI Vault. | [Source: https://dev.mysql.com/doc/refman/9.7/en/security.html] |

| Live session cookies in test artifacts | Playwright | `storageState` files can contain live session cookies/headers ("could be used to impersonate you or your test account"); docs direct users to gitignore `playwright/.auth` and keep these files out of version control. | [Source: https://playwright.dev/docs/auth] |

## 2. Injection Risks

### 2.1 SQL / NoSQL Injection

| Technology | Mechanism / Guidance | Citation |
|---|---|---|
| Mongoose | `mongoose.set('sanitizeFilter', true)` (disabled by default) wraps any nested query object key starting with `$` in a `$eq`, defending against query-selector/NoSQL injection from user input. **Note:** see CVE-2026-42334 in §0 — this protection had a gap around `$nor` until patched. | [Source: https://mongoosejs.com/docs/api/mongoose.html] |
| MongoDB (driver-level) | Validate untrusted input before it is converted from JSON to BSON to prevent injection; prefer typed document-builder APIs over string concatenation; restrict/avoid server-side JavaScript in `$where`/`$function`/`$accumulator` (an injection vector via string concatenation), and disable it entirely via `security.javascriptEnabled: false` if unneeded. | [Source: https://www.mongodb.com/docs/drivers/client-libraries-best-practices/] |
| TypeORM | As of v1.0, parameterized queries and escaped identifiers are used across all drivers for schema introspection and DDL methods, explicitly preventing SQL injection in those paths — a hardening not present with this exact scope in 0.3.x. | [Source: https://typeorm.io/docs/releases/1.0/release-notes/] |
| TypeORM (scope limits) | The security guarantee is scoped to **data values only**: untrusted data reaching queries unescaped through documented APIs and driver parameter-binding defects are in scope, but untrusted input used in identifier/SQL-expression positions, hostile schema/config control, and bypasses of optional runtime validation are explicitly **out of scope**, left to the developer. | [Source: https://github.com/typeorm/typeorm/security/policy] |
| Prisma | Prisma's query API uses parameterized queries/prepared statements by default. Raw SQL via `$queryRaw`/`$executeRaw` should use tagged templates/parameterized inputs, while `$queryRawUnsafe`/`$executeRawUnsafe` are flagged as injection-risk if fed unsanitized input ("Never concatenate user input into SQL strings"). | [Source: https://www.prisma.io/docs/orm/v7/more/best-practices] |
| Prisma (no validation) | Prisma performs no input validation itself; validation/sanitization of user input is the application's responsibility. Zod is named as a commonly-paired library (a suggestion, not a bundled feature). | [Source: https://www.prisma.io/docs/orm/v7/more/best-practices] |
| Drizzle ORM | Automatic parameterization is Drizzle's primary security mechanism: the `sql` tagged template and all standard query-builder methods separate SQL structure from data values, converting interpolated values into database-native placeholders rather than inlining them as literal text. | [Source: https://orm.drizzle.team/docs/sql] |
| Drizzle ORM | `sql.raw()` (unparameterized SQL) is explicitly documented as unsafe for untrusted input — "never use ... for user-provided data" — restricted to trusted/pre-built SQL fragments only. | [Source: https://orm.drizzle.team/docs/sql] |
| Go | SQL injection prevention requires always using placeholder-based parameterized queries via `database/sql` (driver-dependent syntax, e.g. `$1`/`$2` for lib/pq/PostgreSQL) and never interpolating untrusted input into a query string. | [Source: https://go.dev/doc/database/sql-injection] |
| Express | Recommends parameterized queries/prepared statements to prevent SQL injection across MySQL/PostgreSQL/MongoDB backends, and suggests testing with `sqlmap`. | [Source: https://expressjs.com/en/advanced/best-practice-security.html] |

**[Synthesis: combining TypeORM's "identifier/SQL-expression positions are out of scope" carve-out with Prisma's "raw SQL via tagged templates is safe, `$queryRawUnsafe` is not" split, and Drizzle's identical `sql.raw()` carve-out]** — all three mainstream Node ORMs converge on the exact same residual attack surface: parameterization protects *values* substituted into a query, but none of them protect an app that lets untrusted input choose a table/column *name*, a `$nor`/`$where`-style operator key, or a raw SQL fragment. This is a structural blind spot of parameterized-query architecture generally, not a bug specific to any one ORM — an application-level allowlist for identifiers is required regardless of which of these three ORMs is chosen.

### 2.2 Other Injection Classes (Command, XXE, Deserialization, Template)

| Technology | Vector | Citation |
|---|---|---|
| Python | `pickle`/`shelve` deserialization of untrusted data carries an arbitrary-code-execution risk ("restrict globals" if processing untrusted pickles); `multiprocessing.Connection.recv()` uses pickle internally and inherits the same risk. | [Source: https://docs.python.org/3/library/security_warnings.html] |
| Python | `subprocess` carries shell-injection risk, especially with `shell=True`; `xml`/`xml.etree.ElementTree` is subject to XML entity-expansion (XXE-class) vulnerabilities; `zipfile` can be pointed at maliciously crafted archives causing disk-exhaustion "zip bomb" conditions. | [Source: https://docs.python.org/3/library/security_warnings.html] |

| Nuxt | GHSA-9473-5f9j-94wq: Server-side RCE via server-island props when `vue.runtimeCompiler` is enabled combined with dynamic component resolution (see §0). | [Source: https://nuxt.com/blog/v4-5-security] |

## 3. Cross-Site Scripting (XSS)

| Technology | Mechanism / Vector | Mitigation Documented | Citation |
|---|---|---|---|
| HTML (spec-level) | `Element.innerHTML`, `Element.outerHTML`, `Element.insertAdjacentHTML()`, `Document.write()` are the dangerous sinks that interpret a string as HTML/executable markup — e.g. `welcome.innerHTML = \`Welcome back, ${user}!\`` executes attacker-supplied markup. | Layered defense order: output encoding via a templating engine → always quote interpolated attribute values → sanitize untrusted HTML with DOMPurify → enforce Trusted Types via CSP's `require-trusted-types-for` → deploy a strict CSP as defense-in-depth. | [Source: https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS] |
| HTML | Event-handler content attributes (e.g. `onblur`, `onmouseover`) are a distinct XSS vector when untrusted input is interpolated unquoted into an attribute position. | — | [Source: https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS] |
| HTML | The HTML Sanitizer API is a purpose-built browser API for filtering untrusted HTML strings before DOM/shadow-DOM insertion. | Alternative/complement to DOMPurify. | [Source: https://developer.mozilla.org/en-US/docs/Web/API/HTML_Sanitizer_API] |
| React | `dangerouslySetInnerHTML` is React's equivalent of DOM `innerHTML` and the primary documented XSS vector. | Only use with fully trusted/sanitized markup, constructed close to where the HTML is generated, never with raw user input. | [Source: https://react.dev/reference/react-dom/components/common] |
| Vue | `v-html` (and raw `innerHTML`) bypass escaping entirely — "only use v-html on trusted content and never on user-provided content." Text interpolations (`{{ }}`) and dynamic attribute bindings are auto-escaped by default. | Never bind user strings to event-handler attributes (e.g. `:onclick`) — equally unsafe as unsanitized `v-html`. Vue also prevents rendering literal `<style>` tags bound to interpolated user content, mitigating CSS-based clickjacking. | [Source: https://vuejs.org/guide/best-practices/security.html] |
| Vue | User-provided URLs bound via `:href` must be sanitized **on the backend** before persistence, not only client-side; `@braintree/sanitize-url` is a client-side helper, not a substitute. | — | [Source: https://vuejs.org/guide/best-practices/security.html] |
| Angular | Angular treats all values as untrusted by default and auto-sanitizes template bindings by security context (HTML, Style, URL, Resource URL). `DomSanitizer.bypassSecurityTrust*` methods explicitly "introduce security vulnerabilities if the trusted value is malicious." | Trusted Types policies (`angular`, `angular#bundler`, `angular#unsafe-bypass`, `angular#unsafe-jit`, `angular#unsafe-upgrade`) map to specific internal risk surfaces. AOT compilation "should always be used in production" — it prevents template-injection vulnerabilities. | [Source: https://angular.dev/best-practices/security] |
| Angular | HttpClient automatically strips the `)]}',\n` security prefix from JSON responses to prevent cross-site script inclusion (JSON XSSI). | — | [Source: https://angular.dev/best-practices/security] |
| Swagger UI | Markdown rendering is sanitized by default via DOMPurify; the deprecated `useUnsafeMarkdown` option disables that sanitization, reintroducing the class of XSS risk sanitization exists to prevent. A recent patch (v5.32.15) scoped the DOMPurify instance to avoid mutating global state on a host page. | — | [Source: https://swagger.io/docs/open-source-tools/swagger-ui/usage/configuration/] / [Source: https://github.com/swagger-api/swagger-ui/releases] |
| MUI | Emotion-injected `<style>` tags require a `style-src-elem 'nonce-<base64>'` CSP directive matched to a per-request nonce; some components need `style-src-attr 'unsafe-inline'`. The docs explicitly caveat that this "doesn't create a vulnerability" by itself but "reduces defense layers" if markup injection already exists elsewhere — not a substitute for proper output sanitization. | — | [Source: https://mui.com/material-ui/guides/content-security-policy/] |
| Nuxt | On Cloudflare, "Rocket Loader" and "Email Address Obfuscation" must be disabled as they are documented causes of script injection and hydration errors in production. | — | [Source: https://nuxt.com/docs/4.x/getting-started/deployment] |
| GraphQL / Next.js / Vue (CSP tooling) | Next.js's CSP nonce workflow generates a per-request nonce in `proxy.ts`, set via a response header and custom `x-nonce` request header for Server Components; an experimental SRI hash-based CSP alternative (App Router only) preserves static generation. | — | [Source: https://nextjs.org/docs/app/guides/content-security-policy] |
| Vue (build variant) | A separate CSP-compliant npm build of vue exists (`csp` dist-tag, `1.0.28-csp`), though its exact mitigations (e.g. avoiding `new Function()` for `unsafe-eval` CSP compliance) were **not verifiable** from the fetched guide pages. | — | [Source: https://registry.npmjs.org/vue] |

**[Synthesis: combining Vue's "sanitize URLs server-side, not just client-side" rule with HTML's general layered-defense doctrine (encode → sanitize → CSP)]** — the common thread across every frontend framework in this dataset (React, Vue, Angular, HTML/DOMPurify) is that *none* of them treat client-side sanitization alone as sufficient; every framework's own docs push at least one layer of the defense (URL validation, Trusted Types enforcement, or CSP) back onto server-side or HTTP-header-level controls, meaning a security review of any of these frontends is necessarily incomplete if it only inspects client bundle code.

## 4. CORS, CSRF, and Cross-Site Request Handling

| Technology | Detail | Citation |
|---|---|---|
| Socket.IO | CORS must be explicitly configured (disabled/restricted by default since v3); CORS only applies to browsers and only to the HTTP long-polling transport, so it is explicitly documented as **insufficient alone** — `allowRequest` is recommended for additional server-side handshake validation. | [Source: https://socket.io/docs/v4/handling-cors/] |
| Angular | `HttpClient` includes XSRF/CSRF protection by default via an interceptor that reads the `XSRF-TOKEN` cookie and sets an `X-XSRF-TOKEN` header on mutating same-origin requests; configurable via `withXsrfConfiguration()` or disabled via `withNoXsrfProtection()`. | [Source: https://angular.dev/best-practices/security] |
| Vite (dev server) | Setting `server.cors` to `true` "allows any website to send requests to your dev server and download your source code and content" — explicitly flagged as **DANGER**; default behavior restricts to localhost/127.0.0.1. | [Source: https://vite.dev/config/server-options] |
| Vite (dev server) | Permissive `server.allowedHosts` (e.g. a bare top-level domain like `.com`) enables DNS-rebinding attacks letting an attacker's site download dev-server source/content. | [Source: https://vite.dev/config/server-options] |
| Fastify | Official plugins for CORS and CSRF exist as separate opt-in packages: `@fastify/cors`, `@fastify/csrf-protection`, alongside `@fastify/helmet`, `@fastify/rate-limit`, `@fastify/jwt`, `@fastify/auth`, `@fastify/basic-auth`, `@fastify/bearer-auth`, `@fastify/passport`. | [Source: https://fastify.dev/docs/latest/Guides/Ecosystem/] |
| Express | No first-party CSRF middleware is mentioned in the data; Express's documented security best practices instead focus on `helmet` for headers, session hardening, and brute-force/rate limiting (see §5, §6). | [Source: https://expressjs.com/en/advanced/best-practice-security.html] |
| WebSocket API | Cross-Site WebSocket Hijacking (CSWH) mitigation: browsers always send the `Origin` header on handshake requests; servers should validate it and reject (403) unexpected origins — though this only defends against browser-originated attacks since non-browser clients can forge `Origin`. | [Source: https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers] |
| WebSocket API | The `connect-src` CSP directive governs which origins a document's script may open WebSocket connections to, with a documented cross-browser inconsistency where `connect-src 'self'` does not reliably resolve to `ws:`/`wss:` schemes. | [Source: https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/connect-src] |
| Vue | CSRF/XSSI-class HTTP vulnerabilities are explicitly framed as a **backend responsibility**, not something Vue addresses; docs point to the OWASP XSS Prevention Cheat Sheet and HTML5 Security Cheat Sheet. | [Source: https://vuejs.org/guide/best-practices/security.html] |
| Nuxt | A community-maintained "nuxt-security" module (OWASP Top 10/Helmet-based: CSP, rate limiting, XSS protection, CORS, `X-Powered-By` removal, optional CSRF) is listed in the official Nuxt Modules directory but is **explicitly NOT an official Nuxt-team package**. | [Source: https://nuxt.com/modules/security] |

**[Synthesis: combining Socket.IO's "CORS only covers the HTTP long-polling transport" caveat with WebSocket API's "Origin header validation defends only browser-originated attacks" caveat]** — for any realtime layer built on WebSocket or Socket.IO, CORS/Origin checks are best understood as a browser-only, partial-transport control; a server accepting connections from non-browser clients (native apps, other backend services, curl) gets **no** CORS/Origin protection at all from either technology and must implement its own connection-level authentication (Socket.IO's `io.use()` middleware, or an equivalent handshake auth check) regardless of CORS configuration — this is exactly why Socket.IO's own docs recommend `allowRequest` as a required supplement, not merely a nice-to-have.

## 6. Transport Security (TLS/SSL)

| Technology | Detail | Citation |
|---|---|---|
| PostgreSQL | Server-side TLS via `ssl=on` plus a cert/key pair with `0600` key permissions, with optional mandatory client-certificate verification (`clientcert=verify-ca`/`verify-full`). | [Source: https://www.postgresql.org/docs/current/ssl-tcp.html] |

| ClickHouse | TLS-enabled protocol port variants exist (8443 HTTPS, 9010 inter-server TLS). | WebSocket API | `permessage-deflate` compression carries a documented CRIME-style compression-oracle risk when combined with secret data over a TLS channel; RFC 7692 flags this explicitly. | [Source: https://www.rfc-editor.org/rfc/rfc7692.html] |
| Go | Go 1.24+ ships a Go Cryptographic Module supporting FIPS 140-3 mode; in this mode `crypto/tls` is restricted to FIPS-approved protocols/cipher suites, not supported on OpenBSD, Wasm, AIX, or 32-bit Windows. | Express | Recommends terminating TLS at Nginx using Let's Encrypt certificates for all data in transit. | [Source: https://expressjs.com/en/advanced/best-practice-security.html] |
| Angular | The Angular service worker requires HTTPS (except on localhost during development) in order to function at all in production PWA/offline deployments. | [Source: https://angular.dev/ecosystem/service-workers] |
| Python | `ssl` module documents TLS/certificate-verification considerations as a general caution. | [Source: https://docs.python.org/3/library/security_warnings.html] |
| Prisma | v7 driver adapters enforce SSL certificate validation **by default**; connecting to a database with an invalid/self-signed certificate errors unless explicitly configured with `ssl:{rejectUnauthorized:false}` or a proper certificate — a v7 behavior change from v6. | [Source: https://www.prisma.io/docs/orm/v7/prisma-client/setup-and-configuration/databases-connections] |

**[Synthesis: combining WebRTC's DTLS-SRTP mandate, WebSocket's mandatory-masking-even-over-wss rule, and MySQL's ClickHouse-flagged wire-protocol SNI incompatibility]** — "TLS is on" is not a single binary state across this dataset's realtime protocols: WebRTC treats encryption as architecturally non-optional (no plaintext media mode exists at all), WebSocket treats masking as an *additional*, TLS-independent wire-level control that persists regardless of `wss`, and ClickHouse's MySQL-compatibility layer shows that even wrapping a protocol in TLS doesn't guarantee full interoperability (SNI routing can still break). A security review that only checks "is TLS enabled" for these protocols would miss meaningfully different residual risks in each.

|---|---|---|
| GraphQL | GraphQL APIs are called out as particularly exposed to DoS vectors because a single endpoint can express operations of widely varying cost (cyclic/deeply-nested queries, excessive breadth via aliases, batching attacks). Recommended mitigations: enforce maximum query depth, stricter depth limits for nested list fields, limit top-level fields/aliases per operation, cap batched operations per request. | [Source: https://graphql.org/learn/security/] |
| GraphQL | Traditional fixed-window, per-endpoint rate limiting alone is called out as **insufficient** for GraphQL since request count can't distinguish cheap from expensive query shapes; query complexity/cost analysis and business-logic-layer rate limiting are recommended instead. | [Source: https://graphql.org/learn/security/] |
| Socket.IO | `maxHttpBufferSize` (default 1 MB) acts as a basic DoS/resource-exhaustion guard on message size; this default was deliberately tightened from 100 MB (in 2.x) to 1 MB starting in v3.0, alongside disabling WebSocket `perMessageDeflate` compression by default — both framed as safer-by-default changes. | [Source: https://socket.io/docs/v4/server-options/] / [Source: https://socket.io/docs/v4/migrating-from-2-x-to-3-0/] |
| WebSocket API | DoS mitigation is documented only generically: a server can deny connections that attempt too many connections to protect itself, with **no specific rate-limiting algorithm or threshold prescribed**. | [Source: https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers] |
| React / Next.js | CVE-2025-55184/CVE-2025-67779 (DoS) disclosed alongside the critical RSC RCE; follow-up CVE-2026-23864 remained a DoS issue after the initial patch was incomplete. Next.js's May 2026 release separately patched Cache Components connection exhaustion. See §0 for version details. | [Source: https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components] / [Source: https://vercel.com/changelog/next-js-may-2026-security-release] |
| Python | `zipfile` can be pointed at maliciously crafted archives causing disk-exhaustion "zip bomb" conditions. `PYTHONHASHSEED` controls hash randomization, a mitigation against hash-collision denial-of-service attacks on dict/set. | [Source: https://docs.python.org/3/library/security_warnings.html] / [Source: https://docs.python.org/3/using/cmdline.html] |
| Express | `safe-regex` recommended to prevent ReDoS vulnerabilities. | [Source: https://expressjs.com/en/advanced/best-practice-security.html] |
| WebSocket API | `permessage-deflate` compression's CRIME-style compression-oracle risk (see §6) is a confidentiality concern that overlaps with resource-exhaustion-class compression attacks generally. | [Source: https://www.rfc-editor.org/rfc/rfc7692.html] |

**Not covered in the underlying research:** rate-limiting guidance for PostgreSQL, MongoDB, MySQL, Redis, or ClickHouse at the query/connection level is absent from the data beyond Redis's protected-mode default and MySQL's Connection Control feature (see §5.1/§11). ## 11. Error Handling & Information Disclosure

| Technology | Detail | Citation |
|---|---|---|
| Fastify | Default error handler forwards error messages **verbatim** to clients and does not sanitize by environment, which can leak database schema/query details if a DB driver error (PostgreSQL/MySQL/MongoDB) escapes to the client; mitigation is an application-level `setErrorHandler` sanitizing `statusCode >= 500` errors. | [Source: https://fastify.dev/docs/latest/Reference/Errors/] |
| Fastify | Defining explicit response schemas is documented as a security control (as well as a performance one): only schema-declared fields are serialized, helping prevent accidental disclosure of sensitive information. | [Source: https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/] |
| Express | The default error handler returns the full `err.stack` in the HTTP response body when `NODE_ENV` is not `"production"`, and only a generic message in production. | [Source: https://expressjs.com/en/guide/error-handling.html] |
| Prisma | Error formatting is environment-sensitive: pretty-printed ANSI error stacks with fix suggestions by default, but only minimal error output under `NODE_ENV=production`, avoiding leaking schema/query internals in production. | [Source: https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/error-formatting] |
| GraphQL | Production guidance recommends a custom error formatter to strip stack traces/internal implementation detail from error responses (error masking) while preserving structured error codes/metadata. | [Source: https://www.graphql-js.org/docs/going-to-production/] |
| GraphQL | Disabling introspection in production is common practice to reduce attack surface, but many developer tools depend on it, so it should be disabled selectively (e.g. trusted-documents-style operation allowlisting) rather than blanket. | [Source: https://graphql.org/learn/introspection/] / [Source: https://www.graphql-js.org/docs/going-to-production/] |
| PostgreSQL | Restoring a `pg_dump`/`pg_restore` archive from an untrusted source is explicitly flagged as dangerous because dumps contain superuser code that executes during restore. | [Source: https://www.postgresql.org/docs/current/app-pgdump.html] |
| Python | `http.server` is explicitly documented as "not suitable for production use; only implements basic security checks"; production HTTP serving is left to third-party WSGI/ASGI servers not documented by docs.python.org. | [Source: https://docs.python.org/3/library/security_warnings.html] |
| Python | The `random` module is not cryptographically secure and is explicitly discouraged for tokens/passwords/keys in favor of the `secrets` module; `hashlib` constructors take a `usedforsecurity` keyword-only flag to gate known-insecure/blocked algorithms. `tempfile.mktemp()` is documented as vulnerable to a race condition, superseded by `NamedTemporaryFile`/`mkstemp`. | [Source: https://docs.python.org/3/library/security_warnings.html] |

**[Synthesis: combining Fastify's "verbatim DB error forwarding" gap with Prisma's "environment-sensitive error formatting" and Express's "stack trace only outside production" pattern]** — three different layers of a typical Node stack (web framework, ORM, and the framework's own default error handler) each independently gate on `NODE_ENV`/production status for how much internal detail leaks in an error response; a misconfigured or missing `NODE_ENV=production` setting in deployment therefore compounds across all three layers simultaneously — Express dumps stack traces, Prisma dumps schema/query internals, and (absent a custom Fastify error handler) raw DB driver errors reach the client, all from the same single missing environment variable.

## 12. Prototype Pollution & Object-Model Injection

| Technology | Detail | Citation |
|---|---|---|
| Fastify | Built-in, on-by-default prototype-pollution protection: `onProtoPoisoning` and `onConstructorPoisoning` both default to `'error'`, rejecting JSON payloads with `__proto__` or `constructor` keys unless relaxed. As of v5, the internal route-params object no longer inherits from `Object.prototype`, closing another prototype-pollution surface; app code should use `Object.hasOwn()` instead of `.hasOwnProperty()`. | [Source: https://fastify.dev/docs/latest/Reference/Server/] / [Source: https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/] |

Heavy reliance on cascade relations is flagged as a security risk: cascades "may also bring bugs and security issues when some undesired object is being saved into the database." | [Source: https://typeorm.io/docs/data-source/data-source-options/] / [Source: https://typeorm.io/docs/relations/relations/] |

## 13. Compliance / Auxiliary Concerns (documented but adjacent to core AppSec)

| Technology | Detail | Citation |
|---|---|---|
| Google SEO | Google defines malware as software designed to harm a device/software/user, and unwanted software as executables/apps that behave deceptively (unauthorized browser-setting changes, undisclosed data collection, intercepting SSL/TLS connections without authorization). "Hacked content" (unauthorized third-party content injected via a security vulnerability) is a distinct spam-policy category that can flag an entire site even though the owner didn't create the offending content. | [Source: https://developers.google.com/search/docs/monitor-debug/security/malware] / [Source: https://developers.google.com/search/docs/essentials/spam-policies] |
| Google AdSense | AdSense Program policy prohibits sites from malware distribution, deceptive practices, or unwanted redirects as an eligibility requirement. ## 14. Notable Gaps in the Underlying Research

Stated explicitly per the task instructions, rather than inferred or filled in:

- **TypeScript** has no dedicated security-guidance page in its own documentation (no CVE/security-advisory process, no "secure coding in TypeScript" guide). The closest adjacent statement is a design-philosophy note that TS does not implement a fully sound type system — explicitly not security guidance. [Source: https://www.typescriptlang.org/docs/handbook/handbook/] / [Source: https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals]
- **Three.js**: no official page was found covering cross-origin texture/asset loading security (`crossOrigin` handling on loaders, canvas tainting from cross-origin images, or CSP guidance for shader/WebGL/WebGPU contexts) — flagged in the source data as an unresolved documentation gap. Because Three.js executes client-side in the browser sandbox, classic backend security concerns (SQL injection, auth, secrets handling) are out of scope for the library itself.
- **Tailwind CSS**: the Play CDN is flagged as unsuitable for production for *performance* reasons (large JS payload, flash-of-unstyled-content), not a stated security vulnerability — the docs stop short of calling it a security risk.
- **Jest**: no documented guidance on sandboxing test code, executing untrusted test files, or securing CI credentials used during test runs; no documented supply-chain guidance for transform/reporter/watch plugins that execute arbitrary code inside the Jest process.
- **CSS** (as a language, beyond `:visited` privacy): no broader CSS-specific security guidance was found in the data beyond the history-sniffing mitigation.
- **GraphQL / TypeORM**: no Row-Level-Security-equivalent authorization primitive documented for TypeORM (contrast with Drizzle and Prisma, §5.2).
- **SSRF for database/ORM layers**: no dedicated guidance found for outbound-URL-triggered SSRF risk (e.g., webhook or image-fetch-by-URL features) across MongoDB, PostgreSQL, MySQL, Mongoose, TypeORM, Prisma, or Drizzle.
- **Rate limiting at the database layer**: largely undocumented in the data for PostgreSQL, MongoDB, MySQL, and ClickHouse beyond Redis's protected-mode default and MySQL's Connection Control feature.
- **Next.js August 2026 patch**: the exact CVE identifiers for the two critical vulnerabilities addressed were not independently verified — sourced only from a WebSearch summary of the Next.js blog, not a direct advisory fetch (see §0).
- **ClickHouse TLS configuration**: dedicated TLS-configuration guides were located but not fully fetched in the source research pass, so procedural detail beyond port numbers is unconfirmed.
- **Mongoose 8.24.3 hardening fix**: applied `sanitizeFilter` to `countDocuments` and cursor operations, but the full technical detail of what was previously excluded was not confirmed from an official page.
