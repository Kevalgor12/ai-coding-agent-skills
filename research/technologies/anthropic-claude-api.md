## 1. Core Concepts

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview] The Claude API's core interaction primitive is the **Messages API**: Claude "determines when to call a tool based on the user's request and the tool's description," and every request/response cycle is built around a `messages` array of alternating `user`/`assistant` turns plus a separate top-level `system` parameter. The documented request example sends `model`, `max_tokens`, `system`, and `messages` as the baseline shape of every call.

[Source: https://platform.claude.com/docs/en/models/overview] The current model lineup (as documented, four active tiers) is: **Claude Fable 5.1** (`claude-fable-5-1`) — "For demanding reasoning and long-horizon agentic work," 1M context, 128K max output, thinking "Adaptive (always on)," $10/$50 per MTok; **Claude Opus 5** (`claude-opus-5`) — "For complex agentic coding and enterprise work," 1M context, 128K max output, adaptive thinking (not always-on), $5/$25 per MTok; **Claude Sonnet 5** (`claude-sonnet-5`) — "The best combination of speed and intelligence," 1M context, 128K max output, $2/$10 per MTok (this was introductory pricing, made permanent — see Section 12); **Claude Haiku 4.5** (`claude-haiku-4-5-20251001`) — "The fastest model with near-frontier intelligence," 200K context, 64K max output, extended (not adaptive) thinking, $1/$5 per MTok. Legacy-but-still-available models include Claude Fable 5, Opus 4.8, Opus 4.7, Opus 4.6, Opus 4.5, Sonnet 4.6, and Sonnet 4.5.

[Source: https://platform.claude.com/docs/en/models/overview] The docs explicitly recommend a default: "If you're unsure which model to use, start with **Claude Opus 5** for most workloads. Use **Claude Fable 5.1** for demanding reasoning and long-horizon agentic work, or when your evals on Claude Opus 5 at higher effort still fall short." Every model page also lists a "Comparative latency" ranking (Fable 5.1: Slower; Opus 5: Moderate; Sonnet 5: Fast; Haiku 4.5: Fastest) and a "Reliable knowledge cutoff" distinct from the broader "Training data cutoff."

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works] Tools fall into three documented execution buckets that recur throughout the API's design: **user-defined tools** (you write the schema, you execute, e.g. custom business logic), **Anthropic-schema client tools** (Anthropic publishes the schema — `memory`, `bash`, `text_editor`, `computer`, `browser` — "these schemas are trained-in," so Claude "calls them more reliably... than it would with a custom tool that does the same thing," but your application still executes them), and **server-executed tools** (`web_search`, `web_fetch`, `code_execution`, `tool_search` — "Anthropic runs the code... You never construct a `tool_result` block for these tools").

[Source: https://platform.claude.com/docs/en/build-with-claude/thinking] Content blocks include `text`, `thinking` (with a `signature` field — "an encrypted copy of the full reasoning that you pass back unchanged"), `tool_use`, `tool_result`, and image/document blocks (Section 3). A response's `thinking` block is described plainly: "You don't always see this text, and what you see is never the raw chain of thought: the text in a thinking block is a summary of Claude's reasoning."

## 2. Architecture

[Source: https://platform.claude.com/docs/en/build-with-claude/streaming] A streamed response follows a fixed event sequence: **(1)** `message_start` — "contains a `Message` object with empty `content`"; **(2)** a series of content blocks, each with `content_block_start`, one or more `content_block_delta`, and `content_block_stop`, where "each content block has an `index` that corresponds to its index in the final Message `content` array"; **(3)** one or more `message_delta` events for top-level changes; **(4)** a final `message_stop` event. The docs explicitly warn: "The token counts shown in the `usage` field of the `message_delta` event are *cumulative*." `ping` events may appear at any point, and unknown event types "should [be handled] gracefully" per the versioning policy (Section 12).

[Source: https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons] The full documented set of `stop_reason` values: `end_turn` (finished naturally), `max_tokens` (hit the output cap), `stop_sequence` (hit a configured stop string), `tool_use` (Claude is calling a tool — "A server tool call still missing its result block completes in a later response"), `pause_turn` ("Returned when the server-side sampling loop reaches its iteration limit while executing server tools such as web search. The default limit is 10 iterations per request"), `refusal` (Claude declined — "Read `stop_details` and retry on a fallback model"), and `model_context_window_exceeded` ("Claude stopped because it reached the model's context window limit. This lets you request the maximum possible tokens without knowing the exact input size"). The docs draw a hard architectural line: "Stop reasons (successful responses)... Part of the response body... indicate why generation stopped normally," versus "Errors (failed requests)... HTTP status codes 4xx or 5xx."

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works] The **client-tool agentic loop** is documented as a five-step `while` loop keyed on `stop_reason`: (1) send `tools` + user message; (2) Claude responds `stop_reason: "tool_use"` with one or more `tool_use` blocks; (3) execute each tool, format outputs as `tool_result` blocks; (4) send a new request with prior messages, the assistant's response, and a user message carrying the `tool_result` blocks; (5) repeat while `stop_reason == "tool_use"`. Separately, **server-executed tools run their own internal loop inside Anthropic's infrastructure** — "A single request from your application might trigger several web searches or code executions before a response comes back" — and that loop "hands control back to you before a server tool runs if Claude calls that server tool and a client tool in the same group of parallel tool calls," which is the one case a server tool's response arrives with no result block for your application to have produced.

[Source: https://platform.claude.com/docs/en/api/rate-limits] and [Source: https://platform.claude.com/docs/en/manage-claude/authentication] Every response carries a standard header set — `request-id`, `anthropic-organization-id`, `anthropic-workspace-id`, and (on rate-limited requests) `retry-after` plus `anthropic-ratelimit-*` headers reporting the most restrictive currently-enforced limit. Authentication is carried as `Authorization: Bearer <key>` (the legacy `x-api-key` header "is still supported in place of `Authorization`"), and every request requires the versioning header covered in Section 4/12.

## 3. APIs

### Tool definitions and tool_choice

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview] A tool definition is `{"name", "description", "input_schema"}` where `input_schema` is standard JSON Schema (`type: "object"`, `properties`, `required`). The default `tool_choice` is `{"type": "auto"}`: "Claude determines on each turn whether to call a tool or respond directly... It calls a tool when the request maps to that tool's described capability and the answer isn't already in context." This boundary is explicitly steerable via the system prompt — a light instruction increases tool use, a stronger one pushes further, and `"Use your judgment..."` keeps it conservative. To force a call rather than rely on prompting, `tool_choice` also accepts `{"type": "any"}` (any tool), `{"type": "tool", "name": "..."}` (a specific tool), and `{"type": "none"}`; any of these can add `"disable_parallel_tool_use": true` to cap the turn at one tool call. `strict: true` on a tool definition ("guarantee Claude's tool calls always match your schema exactly") is documented as **strict tool use**.

### Parallel tool calls and the tool_result round trip

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview] The worked example shows the canonical round trip: the assistant's `tool_use` block (`{"type": "tool_use", "id": "toolu_...", "name": "...", "input": {...}}`) is echoed back as `{"role": "assistant", "content": response.content}`, followed by a `{"role": "user", "content": [{"type": "tool_result", "tool_use_id": "...", "content": "..."}]}` message. Multiple tool calls in one assistant turn are handled by returning all corresponding `tool_result` blocks together, per the multi-tool handling pattern the docs reference.

### Structured outputs

[Source: https://platform.claude.com/docs/en/build-with-claude/structured-outputs] "Structured outputs constrain Claude's responses to follow a specific schema, ensuring valid, parseable output for downstream processing," via two complementary features: **JSON outputs** (`output_config.format`, e.g. `{"type": "json_schema", "schema": {...}}`) and **strict tool use** (`strict: true`, "Guarantee schema validation on tool names and inputs"). The mechanism is "constrained decoding," advertised as: "Always valid: No more `JSON.parse()` errors... No retries needed for schema violations." The older `output_format` top-level parameter and the `structured-outputs-2025-11-13` beta header are both deprecated — `output_config.format` needs no beta header — though "the API continues to accept the old beta header... and the `output_format` request field for a transition period." JSON Schema support is real but bounded: supported are basic types, `enum`, `const`, `anyOf`/`allOf`, `$ref`/`$def`, several string `format`s, and `minItems` of 0 or 1; **not supported**: recursive schemas, external `$ref`, numeric constraints (`minimum`/`maximum`/`multipleOf`), string-length constraints, and any `additionalProperties` value other than `false`. First use of a schema pays a one-time "grammar compiles" latency cost; compiled grammars "are cached for 24 hours from last use."

### Supporting endpoints

[Source: https://platform.claude.com/docs/en/build-with-claude/batch-processing] The **Message Batches API** (`POST /v1/messages/batches`) processes large volumes asynchronously: "A Message Batch is limited to either 100,000 Message requests or 256 MB in size, whichever is reached first." "Most batches finishing in less than 1 hour while reducing costs by 50% and increasing throughput"; results are "available for 29 days after creation," and batches "expire if processing does not complete within 24 hours." Nearly everything is batchable — vision, tool use (including all server tools), system messages, multi-turn conversations, extended thinking — but `stream: true`, `speed` (fast mode), and `max_tokens: 0` are all rejected inside a batch request with a validation error.

[Source: https://platform.claude.com/docs/en/build-with-claude/vision] The **Files API** lets you "Upload the image once, then reference the returned `file_id` in subsequent messages instead of resending base64 data" — documented specifically as the fix for multi-turn/agentic conversations where "each request resends the full conversation history," so a base64 image would otherwise be re-sent, in full, on every turn.

[Source: https://platform.claude.com/docs/en/models/overview] A **Models API** (`GET /v1/models`, `GET /v1/models/{id}`) exists for programmatic capability discovery: "The response includes `max_input_tokens`, `max_tokens`, and a `capabilities` object for every available model" — the documented mechanism for an application to look up context-window size, thinking/effort/vision support, etc. at runtime rather than hardcoding it.

Not documented / could not verify in this pass: the exact request/response schema of `POST /v1/messages/count_tokens` (the Token Counting API) was referenced from multiple pages (e.g. as the recommended pre-flight check before hitting context-window limits) but its dedicated reference page was not independently fetched in this research pass.

## 4. Configuration

[Source: https://platform.claude.com/docs/en/api/versioning] Every request must send an `anthropic-version` header (e.g. `anthropic-version: 2023-06-01`); "If you are using the client SDKs, this is handled for you automatically." See Section 12 for the full versioning contract and history.

[Source: https://platform.claude.com/docs/en/manage-claude/authentication] Three authentication mechanisms are documented: **API keys** (static `sk-ant-api...` secrets, three key types — personal, service account, and legacy workspace keys, each with different scope/lifecycle rules), **Workload Identity Federation** ("a short-lived bearer token exchanged from your identity provider's identity token," for "production workloads on cloud platforms... where you want to eliminate static secrets"), and **App Attest** (for iOS/macOS apps calling the API directly from-device, using Apple's App Attest service; tokens "expire after one hour" and "authorize only Messages API calls"). "API keys and Workload Identity Federation grant the same access to Claude API endpoints." Personal and service-account keys are identity-backed and "won't accidentally outlive the people or workloads that own them," unlike legacy workspace keys, which the docs now label "legacy" and recommend migrating away from.

[Source: https://platform.claude.com/docs/en/manage-claude/authentication] API keys not scoped to a specific workspace must send `anthropic-workspace-id` on every request or receive a 400 `invalid_request_error`. Key **expiration** is chosen at creation time (preset durations, custom, or "Never" for secrets-manager-stored keys) and "cannot be changed afterward"; expired keys "cannot be reactivated."

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching] and [Source: https://platform.claude.com/docs/en/build-with-claude/structured-outputs] Beta features are gated behind an `anthropic-beta` request header carrying one or more dated feature flags (e.g. the now-legacy `structured-outputs-2025-11-13`); GA features require no such header. This pattern recurs across nearly every newer capability documented in this reference.

## 5. Recommended Patterns

### Prompt architecture and system prompts

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] The documented general-principles hierarchy: **"Be clear and direct"** ("Think of Claude as a brilliant but new employee who lacks context on your norms and workflows... **Golden rule:** Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too"); **"Add context to improve performance"** (explaining *why* an instruction matters outperforms a bare directive — "Claude is smart enough to generalize from the explanation"); **"Use examples effectively"** — multishot/few-shot prompting, "one of the most reliable ways to steer Claude's output format, tone, and structure," with the documented recommendation to **"Include 3–5 examples for best results"** and wrap them in `<example>` tags (`<examples>` for multiple), keeping them relevant, diverse, and structured; **"Structure prompts with XML tags"** — "reduces misinterpretation," using consistent descriptive tag names (`<instructions>`, `<context>`, `<input>`) and nesting tags when content has a natural hierarchy (e.g. `<documents>` containing `<document index="n">`); **"Give Claude a role"** via the `system` parameter — "Even a single sentence makes a difference."

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] **Long-context prompting** (20K+ tokens): "Put longform data at the top... above your query, instructions, and examples. This improves performance across all models," and the docs cite a specific figure: "Queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs." Multi-document inputs should use `<document index="n"><source>...</source><document_content>...</document_content></document>` structure. For long-document reasoning tasks, the docs recommend **grounding responses in quotes**: ask Claude to extract relevant `<quotes>` before answering, "to help Claude focus on the relevant content and ignore the rest of the document."

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] **Chain-of-thought / thinking guidance**: on models with adaptive thinking, "Prefer general instructions over prescriptive steps. A prompt like 'think thoroughly' often produces better reasoning than a hand-written step-by-step plan." Multishot examples compose with thinking — "Use `<thinking>` tags inside your few-shot examples to show Claude the reasoning pattern." As a fallback when thinking is off, manual CoT via `<thinking>`/`<answer>` tags is still documented, though on Claude Opus 5 the docs steer away from that fallback toward "keeping thinking enabled at a lower effort level instead," because disabled thinking can leak internal tags into visible output (Section 6/13). Self-check prompting ("verify your answer against [test criteria]") is broadly recommended except on Claude Opus 5, which "verifies its own work well without explicit instruction," where the same instruction now causes **over**-verification.

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] **Agentic-system patterns**: long-horizon tasks should use structured state (`tests.json`-style structured formats for status, freeform text for progress notes, git for checkpointing); **subagent orchestration** is described as increasingly automatic — "These models can recognize when tasks would benefit from delegating work to specialized subagents and do so proactively without requiring explicit instruction" — with an explicit caution that some models "may spawn them in situations where a simpler, direct approach would suffice"; explicit **prompt chaining** (breaking a task into sequential API calls) remains useful "when you need to inspect intermediate outputs or enforce a specific pipeline structure," with self-correction (draft → review → refine) cited as the most common chaining pattern.

### Context management

[Source: https://platform.claude.com/docs/en/build-with-claude/context-windows] "For long-running conversations and agentic workflows, server-side compaction is the primary strategy for context management." Everything in a request — system prompt, every message (including tool results, images, documents), tool definitions, and generated output including thinking — "counts toward the context window." **Context awareness**: Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5, and Haiku 4.5 "track their remaining context window (their 'token budget') throughout a conversation," automatically, via injected tags: `<budget:token_budget>200000</budget:token_budget>` in the system prompt, then `<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>` after each tool call. Models without this injection (Opus 4.7+, Fable/Mythos 5.1/5) can instead use the beta **task budgets** feature for an explicit budget.

[Source: https://platform.claude.com/docs/en/build-with-claude/context-windows] `context rot`: "As token count grows, accuracy and recall degrade, a phenomenon known as context rot. This makes curating what's in context just as important as how much space is available" — an explicit statement that a larger context window is not automatically better.

### Prompt caching

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching] Two implementation modes: **automatic caching** (a single top-level `cache_control` field auto-caches the last cacheable block — "recommended starting point for most use cases") and **explicit breakpoints** (`cache_control` on individual content blocks for fine control). "Cache prefixes are created in the following order: `tools`, `system`, then `messages`," a strict hierarchy where each level builds on the last. Default cache lifetime is 5 minutes, refreshed at no charge on every hit; a 1-hour option exists via `"ttl": "1h"` for content reused less often than every 5 minutes but more than hourly, or when preserving rate-limit headroom matters (cache hits don't count against ITPM — Section 8). Minimum cacheable prompt length is model-dependent (512 tokens on the newest models up to 4,096 on some older ones — Section 8) and shorter prompts simply don't cache, silently, with no error.

## 6. Anti-Patterns

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] **Assistant-message prefill** is a deprecated pattern on current models: "Starting with Claude 4.6 models and Claude Mythos Preview, prefilled responses... on the last assistant turn are no longer supported. Requests... return a 400 error." Documented replacements per use case: forcing output format → Structured Outputs; eliminating preambles → explicit "Respond directly without preamble" instruction; steering around bad refusals → "Claude is much better at appropriate refusals now"; continuations → move the continuation into the user turn instead of prefilling; context hydration → inject in the user turn, or hydrate through tools/compaction.

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] **Aggressive tool-triggering language is an anti-pattern on current models.** "Claude Opus 4.5 and Claude Opus 4.6 are also more responsive to the system prompt than previous models. If your prompts were designed to reduce undertriggering on tools or skills, these models may now overtrigger. The fix is to dial back the language" — e.g. replacing `"CRITICAL: You MUST use this tool when..."` with plain `"Use this tool when..."`. The same section documents the inverse quirk on lower `effort`, where the model "scopes its work to what was asked rather than going above and beyond," so an under-specified prompt at low effort silently under-delivers.

[Source: https://platform.claude.com/docs/en/build-with-claude/thinking] **Manual extended thinking (`budget_tokens`) is a deprecated/removed anti-pattern on current models**, not merely a legacy option: on Claude Opus 4.7 and later, `thinking: {"type": "enabled"}` returns a 400 `invalid_request_error` outright (Section 13). The documented replacement is `thinking: {"type": "adaptive"}` paired with `output_config.effort`.

[Source: https://platform.claude.com/docs/en/build-with-claude/thinking] Toggling `thinking` mid-turn is explicitly flagged as unsafe: "The entire turn runs in a single thinking mode: you can't toggle thinking in the middle of a turn, including during the tool-use loop." Mid-turn conflicts don't error but "degrade gracefully" — the API silently disables thinking for that request — so the documented pattern is: "Toggle between turns, not within them." Editing, reordering, or partially dropping `thinking`/`redacted_thinking` blocks from the latest assistant message before resending is also an anti-pattern the API actively rejects (400, Section 15).

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool] For computer use specifically, the docs flag giving the model access to sensitive data as an anti-pattern: "Avoiding giving the model access to sensitive data, such as account login information, to prevent information theft" is one of four prescribed precautions (Section 7).

## 7. Security

### Threat model for prompt injection

[Source: https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks] Anthropic documents two distinct threat models with different mitigations: **jailbreaks / direct prompt injection**, "where the *user* of your application is the adversary and crafts inputs intended to bypass your guardrails," and **indirect prompt injection**, "where the user is trusted but Claude processes *third-party content* (web pages, emails, documents, tool results) that contains adversarial instructions." "While Claude is inherently resilient to such attacks, the additional steps on this page strengthen your guardrails."

[Source: https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks] Documented mitigations for **direct injection/jailbreaks**: harmlessness screens (a lightweight model like Claude Haiku 4.5 pre-screening input, output constrained via structured outputs to a simple classification); input validation against known injection patterns; system-prompt hardening that explicitly states ethical/legal boundaries and how to refuse; and responding to repeat offenders (throttling or banning users who repeatedly trigger the same refusal).

### Safe handling of untrusted tool content (indirect injection)

[Source: https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks] This is the most operationally load-bearing guidance in the doc set for agent builders: **"Put untrusted content only in tool results."** "Deliver third-party content to Claude inside `tool_result` blocks, never in `system` prompts or plain user `text` blocks. Claude is trained to treat instructions that appear inside tool results with appropriate skepticism." Further documented practices: **tell Claude what the content is and where it came from** (in the tool description or the result structure itself — "an inbound email from an unknown sender," "OCR text extracted from a user-uploaded image" — "This context helps Claude calibrate how much to trust embedded directives"); **state the untrusted-content policy explicitly in the system prompt** (a worked `<untrusted_content_policy>` example is given); **JSON-encode untrusted content** — "JSON escaping provides unambiguous delimiters between the untrusted payload and the surrounding structure, so an attacker cannot close a quote or tag to 'break out' into an instruction context"; **never put your own instructions inside tool results** — "instructions you place there may be ignored or flagged as a potential injection... Send your instructions in a `user` turn that follows the `tool_result` block"; **least privilege** — scope Claude's data/action access narrowly so a successful injection's blast radius is small; **screen tool outputs before Claude acts on them**, using the same lightweight-classifier pattern as input screening, applied to raw tool output before it's ever wrapped as a `tool_result`; and **red-team your own agent** with deliberately adversarial documents/emails/tool outputs before deploying.

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool] **Computer use carries elevated, separately documented risk**: "Computer use has unique risks distinct from standard API features. These risks are heightened when interacting with the internet." Four prescribed precautions: (1) "Using a dedicated virtual machine or container with minimal privileges to prevent direct system attacks or accidents"; (2) "Avoiding giving the model access to sensitive data, such as account login information, to prevent information theft"; (3) "Limiting internet access to an allowlist of domains to reduce exposure to malicious content"; (4) "Asking a human to confirm decisions that might result in meaningful real-world consequences and any tasks requiring affirmative consent, such as accepting cookies, completing financial transactions, or agreeing to terms of service." Anthropic also runs an automatic defense layer: "Classifiers will automatically run on your prompts to flag potential instances of prompt injections. When these classifiers identify potential prompt injections in screenshots, they will automatically steer the model to ask for user confirmation before proceeding with the next action" — but "These precautions remain important even with the classifier defense layer in place." Builders using computer use also carry a disclosure obligation: "Inform end users of relevant risks and obtain their consent prior to enabling computer use in your own products."

### Acceptable-use touchpoints for builders

[Source: https://platform.claude.com/docs/en/build-with-claude/vision] The Vision docs reference Anthropic's Acceptable Use Policy directly as a functional constraint, not just a legal document: "Claude cannot be used to name people in images and refuses to do so" and "Claude does not process inappropriate or explicit images that violate the Acceptable Use Policy" — both citing `anthropic.com/legal/aup`. These are documented behavioral limitations builders should design around rather than fight.

Not documented / could not verify in this pass: a single, dedicated "content filtering" API parameter or endpoint (as distinct from prompting-based harmlessness screens) was not found; content moderation is documented as a pattern you build with structured outputs and a classifier call, not a first-class filtering knob on the Messages API itself.

## 8. Performance

[Source: https://platform.claude.com/docs/en/build-with-claude/context-windows] Context window sizes by model: **1M tokens** — Claude Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5, Opus 4.8, Opus 4.7, Opus 4.6, Sonnet 5, Sonnet 4.6, and Claude Mythos Preview, each with up to **128K output tokens** (`max_tokens`) per request; **200K tokens** — other models, including Sonnet 4.5, with a lower per-request output ceiling. [Source: https://platform.claude.com/docs/en/models/overview] "1M tokens is roughly 555k words or 2.5M Unicode characters on the current tokenizer (introduced with Claude Opus 4.7); models before it fit about 750k words in 1M tokens" — a documented, quantified tokenizer regression/change in token-per-word density starting Opus 4.7 (see Section 13).

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching] Prompt-caching economics: 5-minute cache writes cost **1.25x** base input price, 1-hour writes cost **2x**, and cache reads cost **0.1x** base input price (**0.025x on Claude Fable 5.1/Mythos 5.1** specifically). Break-even is documented precisely: "caching pays off after one cache read for the 5-minute duration (1.25x write), or after two cache reads for the 1-hour duration (2x write)." Minimum cacheable length is model-dependent and non-monotonic across generations: **512 tokens** for Fable 5.1/Mythos 5.1/Opus 5/Fable 5/Mythos 5, **1,024** for Opus 4.8/Sonnet 5/Sonnet 4.6/Sonnet 4.5/Opus 4.1/Opus 4/Sonnet 4, **2,048** for Mythos Preview/Opus 4.7/Haiku 3.5, and **4,096** for Opus 4.6/Opus 4.5/Haiku 4.5. "Shorter prompts cannot be cached, even if marked with `cache_control`... no error is returned"; verify via `usage.cache_creation_input_tokens`/`cache_read_input_tokens`.

[Source: https://platform.claude.com/docs/en/api/rate-limits] **Cache-aware rate limiting** is a documented throughput lever, not just a cost one: "For most Claude models, only uncached input tokens count toward your ITPM rate limits." Worked example: "With a 2,000,000 ITPM limit and an 80% cache hit rate, you could effectively process 10,000,000 total input tokens per minute." Exception: Claude Haiku 3.5 counts `cache_read_input_tokens` toward ITPM. OTPM is "evaluated in real time as output tokens are produced... The `max_tokens` parameter does not factor into OTPM rate limit calculations, so there is no rate limit downside to setting a higher `max_tokens` value."

[Source: https://platform.claude.com/docs/en/build-with-claude/effort] The `effort` parameter is the primary documented lever for the intelligence/latency/cost trade-off: "By default, Claude uses high effort... You can raise the effort level to `max`... or lower it to be more conservative with token usage." Levels: `low`/`medium`/`high`(=default, equivalent to omitting the parameter)/`xhigh`/`max`, with `xhigh` and `max` support varying per model. "Effort is a behavioral signal, not a strict token budget. At lower effort levels, Claude still thinks on sufficiently difficult problems, but thinks less than it would at higher effort levels for the same problem." Effort touches every output token — text, tool calls, and thinking alike — and lower effort produces "fewer and terser tool calls."

[Source: https://platform.claude.com/docs/en/build-with-claude/thinking] Thinking's cost model: "the tokens Claude spends reasoning are billed as output tokens, even when the thinking text isn't returned to you, and they count toward `max_tokens` alongside the response text." Setting `display: "omitted"` (the default on newer models) reduces time-to-first-text-token in streaming by skipping the streamed thinking text but "You're still charged for the full thinking tokens. Omitting reduces latency, not cost."

## 9. Testing

[Source: https://platform.claude.com/docs/en/test-and-evaluate/develop-tests] Good success criteria are documented as **specific** ("Instead of 'good performance,' specify 'accurate sentiment classification'"), **measurable** (quantitative metrics or "well-defined qualitative scales... consistently applied *along with* quantitative measures"), **achievable** ("Your success metrics should not be unrealistic to current frontier model capabilities"), and **relevant** ("Strong citation accuracy might be critical for medical apps but less so for casual chatbots"). Documented evaluation-dimension categories: task fidelity, consistency, relevance and coherence, tone and style, privacy preservation, context utilization, latency, and price.

[Source: https://platform.claude.com/docs/en/test-and-evaluate/develop-tests] Eval design principles: "Design evals that mirror your real-world task distribution. Don't forget to factor in edge cases"; "Structure questions to allow for automated grading (for example, multiple-choice, string match, code-graded, LLM-graded)"; and — a specific, quotable stance — "**Prioritize volume over quality**: More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." Four grading methods are documented with worked code: **exact match** (categorical tasks, e.g. sentiment classification), **cosine similarity** (semantic consistency via sentence embeddings — SBERT), **ROUGE-L** (summarization relevance/coherence, "the length of the longest common subsequence between the candidate and reference summaries"), and **LLM-based grading** (Likert scales, binary classification, ordinal scales for subjective criteria). Best practice: "Generally best practice to use a different model to evaluate than the model used to generate the evaluated output."

Unresolved: the Claude Console's dedicated interactive **Evaluation tool** — reached via an "Evaluate" tab in the prompt editor — is referenced by title in Anthropic's own site search results ("Using the Evaluation Tool," `platform.claude.com/docs/en/test-and-evaluate/eval-tool`), and a WebSearch summary of that title (not an independently fetched page) describes side-by-side prompt comparison, a 5-point quality grading scale, prompt versioning/re-run, and CSV-based or auto-generated test cases keyed off `{{variable}}` placeholders. **[Source: WebSearch summary of https://platform.claude.com/docs/en/test-and-evaluate/eval-tool, page content not independently fetched]** Two independent direct fetches of that exact URL in this research pass returned only the `develop-tests` page's content instead of distinct Evaluation-tool content, so this section's specific UI-feature claims are flagged as low-confidence and not independently confirmed against fetched page text — treat the tool's *existence* as reasonably well attested (it is cross-linked from Anthropic's own docs navigation and search index) but its *feature list* as unconfirmed by direct fetch in this pass.

## 10. Deployment

[Source: https://platform.claude.com/docs/en/cli-sdks-libraries/overview] Anthropic provides three kinds of official developer tooling: the **`ant` CLI** ("shell scripting, typed flags, response transforms"); **client SDKs** in seven languages — Python, TypeScript, C#, Go, Java, PHP, Ruby — each with "idiomatic interfaces, type safety, and built-in support for streaming, retries, and error handling"; and **libraries/integrations** that "expose Claude inside another framework's API surface rather than the Messages API directly" (an Apple Foundation Models Swift package, and an OpenAI-SDK-compatibility layer).

[Source: https://platform.claude.com/docs/en/models/overview] Claude is available on five documented platforms with distinct model-ID conventions and lifecycle policies: the first-party **Claude API**, **Claude Platform on AWS** (Anthropic-operated, uses first-party model-ID strings), **Amazon Bedrock** and **Google Cloud** (partner-operated, each with their own model-ID scheme — an `anthropic.` prefix on Bedrock, and `@`-versioned dated snapshots on Google Cloud for some models — and their own retirement schedules independent of Anthropic's), and **Microsoft Foundry** ("deployments default to the Claude API model ID... and Foundry follows the Claude API lifecycle schedule").

[Source: https://platform.claude.com/docs/en/api/errors] Request/response size limits by endpoint: Messages API and Token Counting API **32 MB**, Batch API **256 MB**, Files API **500 MB**; exceeding these returns a 413 `request_too_large`, and on the direct Claude API "Cloudflare returns this error before the request reaches the API servers." For long-running requests, the docs recommend streaming or the Batch API over a bare long-timeout synchronous call: "Some networks may drop idle connections after a variable period of time... The SDKs validate that your non-streaming Messages API requests are not expected to exceed a 10-minute timeout."

## 11. Migration

### Agent architecture: the four build-time options

[Source: https://code.claude.com/docs/en/agent-sdk/overview] (Hosted on `code.claude.com`, a distinct first-party doc property from the Claude API docs.) The **Claude Agent SDK** — Python and TypeScript only — "gives you the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript." Its documented capability table: built-in tools (read/write/edit files, run commands, search the web), hooks (custom code at agent-lifecycle points), subagents, MCP, permissions, sessions (resumable/forkable), skills/commands/memory loaded from `.claude/`, and plugins. A comparison table is given directly: use the **Agent SDK** if "Building an agent without implementing the tool loop yourself"; use the **Claude Code CLI** for "interactive development or... one-off tasks from a terminal"; use the **Client SDK** if "Calling the API directly and implementing the tool loop yourself" ("You implement the tool loop yourself"); use **Managed Agents** if "Running long-running or asynchronous agents without managing your own sandbox or session infrastructure" ("Anthropic runs the agent and the sandbox"). "To drive the same agent loop from another language, run the CLI as a subprocess with the `-p` flag and `--output-format json`."

[Source: https://platform.claude.com/docs/en/managed-agents/overview] **Claude Managed Agents** is explicitly positioned against the raw Messages API: "Messages API — Direct model prompting access — Best for: Custom agent loops and fine-grained control" versus "Claude Managed Agents — Pre-built, configurable agent harness that runs in managed infrastructure — Best for: Long-running tasks and asynchronous work." Its architecture has four concepts: **Agent** (model, system prompt, tools, MCP servers, skills — created once, referenced by ID across sessions), **Environment** (an Anthropic-managed cloud sandbox, or a self-hosted sandbox on your own infrastructure), **Session** (a running agent instance in an environment), and **Events** (user turns, tool results, status updates exchanged over server-sent events, with server-side-persisted history). Documented "when to use" signals: long-running execution (minutes to hours, multiple tool calls), need for secure cloud sandboxes with pre-installed packages, self-hosted execution for compliance/data-residency, avoiding building your own agent loop/sandbox/tool-execution layer, stateful multi-interaction sessions, and cron-scheduled recurring runs. It is explicitly in beta ("All Managed Agents endpoints require the `managed-agents-2026-04-01` beta header") and — because it is "stateful by design: sessions are long-running... and store conversation history, sandbox state, and outputs server-side" — is "not currently eligible for Zero Data Retention... or HIPAA Business Associate Agreement (BAA) coverage."

### Model migration

[Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices] The documented migration checklist for moving to current models: be specific about desired behavior; frame instructions with quality/detail modifiers explicitly (the docs give a worked before/after: "Create an analytics dashboard" → "...Include as many relevant features and interactions as possible. Go beyond the basics..."); request animations/interactivity explicitly, since they are no longer inferred as aggressively; **switch `thinking: {type: "enabled", budget_tokens: N}` to `thinking: {type: "adaptive"}`** and move budget control to `output_config.effort`; migrate away from prefilled responses (Section 6); dial back "anti-laziness" prompting tuned for older, less-proactive models; and, specifically for Claude Fable 5.1, **pass thinking blocks back unchanged and keep conversation history append-only** — "modifying the conversation before a thinking block results in an error, or in the block being dropped."

## 12. Version Information

[Source: https://platform.claude.com/docs/en/api/versioning] The API versioning contract, per the `anthropic-version` header: Anthropic **preserves** existing input parameters and existing output parameters for a given version, but **may** add optional inputs, add output values, change error conditions for specific error types, or add new enum-like variants (e.g. new streaming event types). "Generally, if you are using the API as documented in this reference, Anthropic will not break your usage." Documented version history is short and stable: **`2023-06-01`** (current) introduced incremental streaming deltas, named SSE events (vs. data-only), and removed the `data: [DONE]` sentinel and legacy `exception`/`truncated` response values; **`2023-01-01`** was the initial release. "Previous versions are considered deprecated and may be unavailable for new users."

[Source: https://platform.claude.com/docs/en/models/overview] Model-ID versioning scheme: "Every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on." For pre-4.6 models, the "Claude API alias" is "a convenience pointer that resolves to the dated ID," but from Claude 4.6 onward the dateless string itself (e.g. `claude-opus-5`) *is* the pinned snapshot, not an alias over a hidden dated ID. [Source: https://platform.claude.com/docs/en/about-claude/pricing] "The $2/$10 per million input/output token pricing for Claude Sonnet 5, announced at launch as introductory pricing through August 31, 2026, is now the standard price. The previously scheduled increase to $3/$15... will not occur" — a documented example of Anthropic retracting a previously-announced pricing change rather than letting it take effect.

[Source: https://platform.claude.com/docs/en/about-claude/model-deprecations] Retirement-date commitments (Anthropic-operated platforms only — Bedrock/Google Cloud set their own schedules) as of this research date: Claude Fable 5.1 not sooner than 2027-09-01; Claude Opus 5 not sooner than 2027-07-24; Claude Sonnet 5 not sooner than 2027-06-30; Claude Opus 4.8 not sooner than 2027-05-28; Claude Opus 4.7 not sooner than 2027-04-16; Claude Sonnet 4.6 not sooner than 2027-02-17; Claude Opus 4.6 not sooner than 2027-02-05; Claude Haiku 4.5 not sooner than 2026-10-15. Retired-model examples with their replacement mapping include `claude-opus-4-1-20250805` (deprecated 2026-06-05, retired 2026-08-05 → `claude-opus-4-8`), `claude-sonnet-4-20250514`/`claude-opus-4-20250514` (deprecated 2026-04-14, retired 2026-06-15), and `claude-3-7-sonnet-20250219` (retired 2026-02-19).

## 13. Breaking Changes

[Source: https://platform.claude.com/docs/en/api/errors] **Prefill removed (Claude 4.6+ and Claude Mythos Preview)**: a request whose last message is an assistant turn (prefill) returns 400 with `"This model does not support assistant message prefill. The conversation must end with a user message."` [Source: https://platform.claude.com/docs/en/api/errors] **Extended (manual) thinking removed (Claude 4.7+)**: `thinking: {"type": "enabled"}` returns 400 with `'"thinking.type.enabled" is not supported for this model. Use "thinking.type.adaptive" and "output_config.effort"...'`. Conversely, **adaptive thinking is rejected on models that only support extended thinking** (Claude 4.5 and earlier): `thinking: {"type": "adaptive"}` returns 400 `"adaptive thinking is not supported on this model."` **Thinking cannot be disabled on Fable 5.1/Mythos 5.1/Fable 5/Mythos 5/Mythos Preview** — `thinking: {"type": "disabled"}` returns 400, and the error message's own suggested fallback (`"thinking.type.enabled"`) is *also* rejected on these always-thinking models; the correct fix is to omit the `thinking` parameter entirely.

[Source: https://platform.claude.com/docs/en/about-claude/model-deprecations] **Sampling parameters removed on Claude Opus 4.7+ and later**: "`temperature`, `top_p`, `top_k`... Returns a 400 error when set to a non-default value on Claude 4.7 and later models and Claude Mythos Preview." "The Python SDK (v1.0 and later) removes `temperature`, `top_p`, and `top_k`, so passing them raises a `TypeError`" client-side, ahead of the server even rejecting the request.

[Source: https://platform.claude.com/docs/en/build-with-claude/thinking] **Silent default-behavior break on Claude Opus 5**: unlike Opus 4.8/4.7/4.6 and Sonnet 4.6, where omitting `thinking` means thinking is off, "On Claude Opus 5, Claude Sonnet 5... thinking is already on and needs no configuration" — an application that upgraded its model string without touching its `thinking` config silently starts paying for and receiving thinking blocks it didn't request. Additionally, on Claude Opus 5 specifically, `thinking: {"type": "disabled"}` is accepted only at `effort: "high"` or below; "requests that combine `thinking: {type: 'disabled'}` with those [`xhigh`/`max`] effort levels return a 400 error."

[Source: https://platform.claude.com/docs/en/api/errors] **Thinking-block immutability is enforced, not advisory**: "If the most recent assistant message contains `thinking` or `redacted_thinking` blocks that were edited, reordered, filtered out, or reconstructed before being sent back to the API, the request returns a 400." The one carve-out: "text placed in the empty `thinking` field of an omitted block is ignored rather than rejected."

[Source: https://platform.claude.com/docs/en/about-claude/pricing] **Tokenizer change, Claude 4.7 and later**: "This tokenizer produces approximately 30% more tokens for the same text. The exact increase depends on the content and workload shape" — a breaking change for any hardcoded token-budget math, not a request-shape 400, but explicitly flagged by Anthropic as needing re-baselining after upgrade.

## 14. Limitations

[Source: https://platform.claude.com/docs/en/build-with-claude/vision] Documented vision limitations, verbatim from Anthropic's own list: "Claude cannot be used to name people in images and refuses to do so"; "Claude might hallucinate or make mistakes when interpreting low-quality, rotated, or very small images under 200 pixels"; "Claude's coordinate and localization outputs are approximate"; "Claude can give approximate counts of objects in an image but might not always be precisely accurate, especially with large numbers of small objects"; "Claude cannot determine whether an image is AI-generated and might be incorrect if asked. Do not rely on it to detect fake or synthetic images"; and, most consequentially for regulated use cases, "Although Claude can analyze general medical images, it is not designed to interpret complex diagnostic scans such as CTs or MRIs. Claude's outputs should not be considered a substitute for professional medical advice or diagnosis." Image request limits are also hard caps: max 20 images per turn on claude.ai, 100/request on the API for 200K-context models, 600/request for 1M-context models, and a stricter per-image dimension limit kicks in automatically once a single request exceeds 20 combined image/document blocks.

[Source: https://platform.claude.com/docs/en/build-with-claude/context-windows] **Context overflow is a hard boundary, not a soft one, for the input side**: "If the input alone already exceeds the model's context window, the API returns a 400 `invalid_request_error` ('prompt is too long') on every model." Only on the *output* side, and only on Claude 4.5+ models, does the API instead accept the request and stop gracefully with `stop_reason: "model_context_window_exceeded"` if generation itself fills the remaining window; earlier models return a validation error there too, unless the `model-context-window-exceeded-2025-08-26` beta header is set.

[Source: https://platform.claude.com/docs/en/build-with-claude/structured-outputs] Structured outputs' JSON Schema support has hard, documented ceilings (Section 3): no recursive schemas, no numeric or string-length constraints, no external `$ref`, `additionalProperties` must be `false`. An application relying on `minLength`/`maximum`-style validation cannot express that constraint in the schema Claude enforces and must validate it separately.

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool] Computer use is **not Anthropic-hosted by default**: "Your application must... Run each call in order in an environment you control," including building the sandboxed container, the action handlers for all 17 member tools, the agent loop, screenshot capture, and coordinate scaling — a substantial documented infrastructure burden distinct from server-executed tools like web search.

[Source: https://platform.claude.com/docs/en/api/rate-limits] Rate/spend limits are hard, tier-scoped ceilings, not soft guidance: "All limits described here represent maximum allowed usage, not guaranteed minimums." Reaching a tier's monthly spend cap pauses *all* API usage until the next calendar month (00:00 UTC) unless a higher tier is requested — and importantly, on that specific 429, "the response has no `retry-after` header. Retrying, including the SDKs' automatic retries, fails until access resumes."

## 15. Debugging

[Source: https://platform.claude.com/docs/en/api/errors] Every error is JSON with a stable top-level shape: `{"type": "error", "error": {"type": "...", "message": "..."}, "request_id": "req_..."}`. Documented HTTP status codes: 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error`. "The official SDKs automatically retry transient failures (such as connection errors, rate limits, and 5xx server errors) with exponential backoff, twice by default, honoring the `retry-after` header when present." SDKs surface these as typed exceptions per language (`anthropic.NotFoundError` in Python, `Anthropic::Errors::NotFoundError` in Ruby, `com.anthropic.errors.NotFoundException` in Java, a single `*anthropic.Error` in Go branched on `.StatusCode`) rather than raw JSON, and the docs explicitly instruct: "Catch the SDK's typed classes rather than string-matching error messages, handling the most specific classes first."

[Source: https://platform.claude.com/docs/en/api/errors] Every response carries a `request-id` header (`req_...`) that also appears in error bodies as `request_id` — "When contacting support about a specific request, include this ID." On Claude Platform on AWS specifically, responses carry two IDs: the AWS request ID (`x-amzn-requestid`, primary, CloudTrail-indexed) and the Anthropic request ID (secondary).

[Source: https://platform.claude.com/docs/en/api/errors] Streaming responses can fail *after* the initial 200: "When receiving a streaming response over server-sent events (SSE), an error can occur after the API returns a 200 response. In that case, error handling doesn't follow these standard mechanisms" — instead arriving as an `event: error` SSE frame (e.g. `{"type": "error", "error": {"type": "overloaded_error", ...}}`), which application code must watch for independently of the initial HTTP status.

[Source: https://platform.claude.com/docs/en/api/errors] Named, documented validation-error signatures worth recognizing at a glance (all covered in more depth in Section 13): prefill not supported; thinking blocks modified; extended thinking not supported; adaptive thinking not supported; thinking cannot be disabled; forced tool use not supported (on Fable 5.1/Mythos 5.1, `tool_choice: {"type": "any"}` or `{"type": "tool", ...}` return 400, "including on the token counting endpoint" — only `auto`/`none` are accepted on these models); and, on Claude Fable 5.1 specifically, a replayed `thinking` block whose earlier conversation history changed can be rejected as no longer matching the conversation it was bound to.

## 16. Integration

[Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview] MCP (Model Context Protocol) integration is documented at two levels: to **build your own MCP client**, the docs point to the Model Context Protocol project's own guide; to connect **from the Messages API directly without a separate client**, the docs point to a dedicated **MCP connector**. The same overview page enumerates the full catalog of first-party tools an application can integrate: client-side (your own tools; Anthropic-schema memory/bash/text-editor/computer-use/browser-use) and server-side (web search, web fetch, code execution, advisor, tool search, plus the MCP connector itself).

[Source: https://platform.claude.com/docs/en/managed-agents/overview] Managed Agents documents its own tool surface as a superset built for the sandbox model: "Bash," "File operations" (read/write/edit/glob/grep), "Web search and fetch" (optionally allowlist/blocklist-restricted), and "MCP servers: Connect to external tool providers" — i.e., the same MCP-connector concept re-surfaced as a first-class Managed Agents building block rather than a Messages API parameter pair.

[Source: https://code.claude.com/docs/en/agent-sdk/overview] The Agent SDK's own MCP support is one line in its capability table: "Connect external tools and data sources via the Model Context Protocol." Combined with the Section 11 comparison table, the practical integration decision a builder faces is: raw `mcp_servers`/`mcp_toolset` parameters on the Messages API for fine-grained control inside your own loop; the Agent SDK's MCP surface if you're already using Claude Code's harness in-process; or Managed Agents' MCP servers if you want Anthropic to host both the loop and the sandbox.

[Source: https://platform.claude.com/docs/en/cli-sdks-libraries/overview] For non-agentic integrations into an existing stack, Anthropic documents an **OpenAI SDK compatibility layer** — "Use Claude through the OpenAI SDK surface" — as an explicit, first-party migration/integration path for teams with existing OpenAI-SDK-shaped code, distinct from and narrower in scope than the native client SDKs.

## 17. Production Considerations

[Source: https://platform.claude.com/docs/en/api/rate-limits] Production capacity planning is tier-based: **Start** ($500/mo spend cap, 1,000 RPM baseline), **Build** ($1,000/mo, up to 5,000 RPM on Opus/Sonnet-tier models), **Scale** ($200,000/mo, up to 10,000 RPM), and **Custom** (negotiated, no cap). "Organizations are placed on a tier automatically based on usage history and account standing." New/low-history orgs "may start in the Evaluation tier, with limits below the standard limits... as part of how Anthropic prevents fraud and abuse." A separate documented gotcha: "acceleration limits" can trigger 429s on a *sharp* usage increase even under the nominal tier ceiling — "ramp up your traffic gradually and maintain consistent usage patterns" to avoid it.

[Source: https://platform.claude.com/docs/en/about-claude/pricing] Documented cost-optimization strategies for production: pick the cheapest model tier that meets the bar ("Choose Haiku for simple tasks, Sonnet for most production workloads, and Opus for the most complex reasoning"); implement prompt caching for repeated context; batch non-time-sensitive work for the 50% Batch API discount; and monitor usage patterns to catch drift. Batch and prompt-caching discounts explicitly **stack**: "Batch API and prompt caching discounts can be combined... using both features together provides significant cost savings compared to standard API calls."

[Source: https://platform.claude.com/docs/en/managed-agents/overview] Session-based production billing (Managed Agents) is two-dimensional — token usage at standard Messages API rates, plus **session runtime** billed at $0.08/session-hour, "measured to the millisecond and accrues only while the session's status is `running`" (not while `idle`, `rescheduling`, or `terminated`) — a distinct production cost model from a stateless Messages API integration that builders migrating toward an agent harness need to budget separately.

[Source: https://platform.claude.com/docs/en/api/rate-limits] For workspace-level production governance: "You can set custom spend and rate limits per Workspace... to protect Workspaces in your Organization from potential overuse," with the explicit caveat that "Organization-wide limits always apply, even if Workspace limits add up to more" — sub-limits are a soft internal allocation mechanism, not an escape hatch from the org ceiling.
