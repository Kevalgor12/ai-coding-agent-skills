## 1. Core Concepts

**Pull vs. push — the defining architectural choice.** [Source: https://prometheus.io/docs/introduction/overview/] Prometheus's own feature list states plainly: "time series collection happens via a pull model over HTTP" and, separately, "pushing time series is supported via an intermediary gateway" — pull is the default and primary model; push exists only as an accommodation via the Pushgateway. [Source: https://prometheus.io/docs/introduction/faq/] Prometheus's FAQ gives the project's own rationale for choosing pull over push: "You can start extra monitoring instances as needed, e.g. on your laptop when developing changes," "You can more easily and reliably tell if a target is down," and "You can manually go to a target and inspect its health with a web browser." The FAQ tempers this, however: "we believe that pulling is slightly better than pushing, but it should not be considered a major point when considering a monitoring system." [Source: https://prometheus.io/docs/instrumenting/pushing/] For cases where pull is not viable (notably short-lived batch jobs that may not exist long enough to be scraped), Prometheus offers the **Pushgateway**, an intermediary metrics cache that itself gets scraped normally by Prometheus — batch jobs push to the Pushgateway, and the Pushgateway is pulled by Prometheus like any other target.

**Multi-dimensional data model.** [Source: https://prometheus.io/docs/concepts/data_model/] "Prometheus fundamentally stores all data as time series: streams of timestamped values belonging to the same metric and the same set of labeled dimensions." Every time series is uniquely identified by its metric name plus an optional set of key-value pairs called labels. Metric names SHOULD describe the general feature being measured (e.g. `http_requests_total`); metric names MAY use any UTF-8 characters but SHOULD match `[a-zA-Z_:][a-zA-Z0-9_:]*` "for the best experience and compatibility" — names outside that set require quoting in PromQL. Colons in metric names are reserved for user-defined recording rules and SHOULD NOT be used by exporters or direct instrumentation.

**Four core metric types.** [Source: https://prometheus.io/docs/concepts/metric_types/] "The Prometheus instrumentation libraries offer four core metric types. With the exception of native histograms, these are currently only differentiated in the API of instrumentation libraries and in the exposition protocols. The Prometheus server does not yet make use of the type information and flattens all types except native histograms into untyped time series of floating point values."
- **Counter** — "a cumulative metric that represents a single monotonically increasing counter whose value can only increase or be reset to zero on restart." Documented example uses: requests served, tasks completed, errors. Explicit guidance: "Do not use a counter to expose a value that can decrease... instead use a gauge."
- **Gauge** — "a metric that represents a single numerical value that can arbitrarily go up and down." Used for temperatures, current memory usage, or counts that go up and down (e.g. concurrent requests).
- **Histogram** — "records observations... by counting them in configurable buckets," also providing a sum of observed values; "essentially a bucketed counter." Two variants exist: **native histograms** (exposed/ingested as composite samples with count, sum, and a dynamic set of buckets — "generally much more efficient... allow much higher resolution, do not require explicit configuration of bucket boundaries," and are guaranteed aggregatable even across resolution changes) and **classic histograms** (multiple plain float time series: `<basename>_bucket{le="<bound>"}`, `<basename>_sum`, `<basename>_count`). The docs recommend: "If the instrumentation library you are using supports native histograms (currently... Go and Java), you should probably prefer native histograms over classic histograms." A hybrid — Native Histograms with Custom Bucket boundaries (NHCB) — lets Prometheus ingest classic histograms into the more efficient native-histogram storage representation while keeping the statically-configured classic bucket layout.
- **Summary** — "similar to a histogram," also provides total count and sum, but "calculates configurable quantiles over a sliding time window," exposing `<basename>{quantile="<φ>"}`, `<basename>_sum`, `<basename>_count`. Unlike histogram buckets, summary quantiles are computed client-side and cannot be aggregated across instances.

[Source: https://prometheus.io/docs/concepts/data_model/] Beginning with Prometheus v3.0, the values of the `le` label of classic histograms and the `quantile` label of summaries are normalized during ingestion to follow the OpenMetrics Canonical Numbers format (this is also documented as a breaking change — see Section 13).

## 2. Architecture

[Source: https://prometheus.io/docs/introduction/overview/] "Prometheus scrapes metrics from instrumented jobs, either directly or via an intermediary push gateway for short-lived jobs. It stores all scraped samples locally and runs rules over this data to either aggregate and record new time series from existing data or generate alerts." The ecosystem consists of multiple largely-optional components: the main Prometheus server (scrapes and stores time series), client libraries for instrumenting application code, a Pushgateway for short-lived jobs, special-purpose exporters (HAProxy, StatsD, Graphite, etc.), an Alertmanager to handle alerts, and various support tools. Most components are written in Go, "making them easy to build and deploy as static binaries."

**Jobs and instances.** [Source: https://prometheus.io/docs/concepts/jobs_instances/] "In Prometheus terms, an endpoint you can scrape is called an instance, usually corresponding to a single process. A collection of instances with the same purpose... is called a job." On every scrape Prometheus attaches `job` and `instance` labels automatically and records `up` (1 if healthy/reachable, 0 if the scrape failed), `scrape_duration_seconds`, `scrape_samples_post_metric_relabeling`, and `scrape_samples_scraped`.

**Local TSDB storage engine.** [Source: https://prometheus.io/docs/prometheus/latest/storage/] "Prometheus's local time series database stores data in a custom, highly efficient format on local storage." Ingested samples are grouped into two-hour blocks; each block is a directory with a `chunks` subdirectory (samples, segment files up to 512 MB by default), an `index` file mapping metric/label data to chunk locations, and a `meta.json`. The current (most recent) block lives in memory and is protected by a write-ahead log (WAL, 128 MB segments, minimum three files retained) that is replayed on restart. Deletions are recorded as tombstones rather than removed immediately from chunk segments. Blocks are compacted in the background into larger blocks spanning up to 10% of the retention time or 31 days, whichever is smaller.

**Service discovery.** [Source: https://prometheus.io/docs/prometheus/latest/configuration/configuration/] A `scrape_config` may populate targets via `static_configs` or via any of roughly 30 documented service-discovery mechanisms configured per scrape job, including `kubernetes_sd_configs`, `ec2_sd_configs`, `azure_sd_configs`, `consul_sd_configs`, `dns_sd_configs`, `file_sd_configs`, `gce_sd_configs`, `docker_sd_configs`, `dockerswarm_sd_configs`, `eureka_sd_configs`, `hetzner_sd_configs`, `http_sd_configs`, `marathon_sd_configs`, `nomad_sd_configs`, `openstack_sd_configs`, `puppetdb_sd_configs`, `oci_sd_configs` (Oracle Cloud, added in 3.14 per the changelog), and others. [Source: https://prometheus.io/docs/prometheus/latest/http_sd/] Generic **HTTP service discovery** lets Prometheus poll an arbitrary HTTP(S) JSON endpoint for a target list on a configurable `refresh_interval` (default one minute); the endpoint must return HTTP 200 with `Content-Type: application/json`, return the *entire* target list on every request (no incremental updates), and return `[]` rather than an error when there are no targets. TLS, basic auth, OAuth2, and an Authorization header are all supported for the SD request itself. This is explicitly positioned as complementary to file-based SD, which instead watches a local file via inotify for instant, event-based updates.

**Alertmanager as a separate component.** [Source: https://prometheus.io/docs/alerting/latest/overview/] "Alerting with Prometheus is separated into two parts. Alerting rules in Prometheus servers send alerts to an Alertmanager. The Alertmanager then manages those alerts, including silencing, inhibition, aggregation and sending out notifications via methods such as email, on-call notification systems, and chat platforms." The Alertmanager is a distinct binary/process from the Prometheus server; a Prometheus server is configured with one or more Alertmanager targets under its `alerting.alertmanagers` config block (itself supporting static config or service discovery, plus `relabel_configs` for selecting Alertmanagers).

[Source: https://prometheus.io/docs/prometheus/latest/querying/api/] The Prometheus server's **HTTP API** (`/api/v1/*`) is the mechanism through which all query, series-metadata, and admin operations are exposed to UIs, dashboards, and automation.

## 3. APIs

**PromQL fundamentals.** [Source: https://prometheus.io/docs/prometheus/latest/querying/basics/] "Prometheus provides a functional query language called PromQL... that lets the user select and aggregate time series data in real time." A query request is either an **instant query** (evaluated at one point in time) or a **range query** (equally-spaced steps between a start and end time); PromQL itself behaves identically in both cases. An expression evaluates to one of four types: **instant vector** (one sample per time series, all sharing a timestamp), **range vector** (a range of data points per time series), **scalar** (a single float), or **string** (currently unused). Range queries only support scalar- and instant-vector-typed root expressions.

- **Selectors.** `http_requests_total{job="prometheus",group="canary"}` filters by exact label match; matcher operators are `=`, `!=`, `=~` (regex match), `!~` (regex non-match); regex matches are fully anchored (`env=~"foo"` behaves as `env=~"^foo$"`), and all Prometheus regexes use **RE2 syntax**. A vector selector must specify a metric name or at least one non-empty-matching label matcher — a bare `{job=~".*"}` is illegal. Range vector selectors append a duration in brackets, e.g. `http_requests_total[5m]`; the range is **left-open, right-closed** (as of Prometheus v3 — see Section 13 for the pre-3.0 behavior change).
- **Modifiers.** `offset` shifts the evaluation time backward (or, with a negative duration, forward) and must immediately follow the selector, e.g. `rate(http_requests_total[5m] offset 1w)`. The `@` modifier pins evaluation to an absolute Unix timestamp (or the special values `start()`/`end()` for range queries), also usable together with `offset`.
- **Duration expressions.** [Source: https://prometheus.io/docs/prometheus/latest/querying/basics/] Arithmetic (`+ - * / % ^`) is permitted in range-vector brackets and `offset` durations, e.g. `rate(http_requests_total[5m * 2])`; the functions `step()`, `range()`, `min_of()`, `max_of()` are available inside duration expressions for building adaptive windows relative to the query's own step/range.
- **Subqueries.** `<instant_query>[<range>:<resolution>]` runs an instant query repeatedly over a range at a given resolution, producing a range vector — useful for e.g. computing `max_over_time` of a `rate()`.
- **Staleness.** [Source: https://prometheus.io/docs/prometheus/latest/querying/basics/] Prometheus assigns a value to a queried timestamp by taking "the newest sample that is less than the lookback period ago" (default 5 minutes, tunable via `--query.lookback-delta` or per-query `lookback_delta`). If a target stops exposing a series or is removed, the series is marked stale and subsequently omitted from query results.
- **Query cost guidance.** [Source: https://prometheus.io/docs/prometheus/latest/querying/basics/] The docs explicitly warn to build ad-hoc queries in the tabular view first, keep result sets to "hundreds, not thousands" of series, and pre-record expensive expressions as recording rules — "expressions that aggregate over many time series will generate load on the server even if the output is only a small number of time series."

**HTTP API.** [Source: https://prometheus.io/docs/prometheus/latest/querying/api/] The stable HTTP API is served under `/api/v1` (all non-breaking additions land there); a machine-readable **OpenAPI 3.1/3.2 specification** is published at `/api/v1/openapi.yaml`. Every response is a JSON envelope: `{"status": "success"|"error", "data": ..., "errorType": ..., "error": ..., "warnings": [...], "infos": [...]}`. Key endpoints: `GET/POST /api/v1/query` (instant query; params `query`, `time`, `timeout`, `limit`, `lookback_delta`, `stats`) and `GET/POST /api/v1/query_range` (range query; adds `start`, `end`, `step`). Error responses use `400` (bad/missing params), `422` (expression cannot be executed), or `503` (timeout/abort). Beyond query execution, the v1 API also exposes series/label/metadata lookup endpoints, rule and alert introspection, and TSDB status endpoints (not itemized exhaustively here).

**Remote-write / remote-read APIs.** [Source: https://prometheus.io/docs/prometheus/latest/storage/] Prometheus integrates with remote storage in four directions: it can *write* ingested samples to a remote URL (Remote Write), *receive* samples pushed by other clients in Remote Write format, *read* sample data back from a remote URL (Remote Read), and *serve* Remote Read requests from clients. Both protocols use "a snappy-compressed protocol buffer encoding over HTTP." [Source: https://prometheus.io/docs/prometheus/latest/stability/] The **remote write 1.0 specification is stable**; a **2.0 specification is experimental**, and both are supported by the Prometheus server; **remote read is explicitly unstable** ("Remote read and the remote read endpoint" is listed under "Things considered unstable for 3.x"). [Source: https://prometheus.io/docs/prometheus/latest/storage/] On the read path, "Prometheus only fetches raw series data for a set of label selectors and time ranges from the remote end. All PromQL evaluation on the raw data still happens in Prometheus itself" — this bounds remote-read scalability, since "supporting fully distributed evaluation of PromQL was deemed infeasible for the time being." Prometheus can act as a remote-write/remote-read *receiver* too: the built-in remote-write receiver is enabled with `--web.enable-remote-write-receiver` and served at `/api/v1/write`; the remote-read endpoint is `/api/v1/read`.

**Management API.** [Source: https://prometheus.io/docs/prometheus/latest/management_api/] `GET/HEAD /-/healthy` always returns 200 (liveness); `GET/HEAD /-/ready` returns 200 once Prometheus can serve queries (readiness); `PUT/POST /-/reload` triggers a config/rule-file reload (disabled by default, requires `--web.enable-lifecycle`, or equivalently `SIGHUP`); `PUT/POST /-/quit` triggers graceful shutdown (also gated by `--web.enable-lifecycle`, or equivalently `SIGTERM`).

## 4. Configuration

[Source: https://prometheus.io/docs/prometheus/latest/configuration/configuration/] "Prometheus is configured via command-line flags and a configuration file. While the command-line flags configure immutable system parameters..., the configuration file defines everything related to scraping jobs and their instances, as well as which rule files to load." The config file (path set via `--config.file`) is YAML. **Configuration can be reloaded at runtime** without restarting, via `SIGHUP` or an HTTP POST to `/-/reload` (when `--web.enable-lifecycle` is set) — "If the new configuration is not well-formed, the changes will not be applied."

**Global config block.** Key fields: `scrape_interval` (default `1m`), `scrape_timeout` (default `10s`, cannot exceed the scrape interval), `evaluation_interval` (default `1m`), `external_labels` (attached to all time series/alerts sent to external systems — federation, remote storage, Alertmanager; supports `${var}`/`$var` environment-variable expansion), `scrape_protocols` (negotiation order for scrape content-type), plus several per-scrape safety limits: `body_size_limit`, `sample_limit`, `label_limit`, `label_name_length_limit`, `label_value_length_limit`, `target_limit` — all default to `0` (no limit) and, when exceeded, cause the *entire scrape* to be treated as failed (not partially ingested).

**`scrape_config` structure.** Each entry specifies `job_name`, optional per-job overrides of `scrape_interval`/`scrape_timeout`, `metrics_path` (default `/metrics`), `scheme` (default `http`), `honor_labels` (controls whether scraped labels or server-side labels win on conflict — "useful for use cases such as federation and scraping the Pushgateway"), `honor_timestamps`, an `<http_config>` block (auth/TLS/proxy — see Section 7), one or more `*_sd_configs` blocks or `static_configs`, and `relabel_configs`/`metric_relabel_configs`.

**Relabeling — precise mechanics.** [Source: https://prometheus.io/docs/prometheus/latest/configuration/configuration/] "Relabeling is a powerful tool to dynamically rewrite the label set of a target before it gets scraped. Multiple relabeling steps can be configured per scrape configuration. They are applied to the label set of each target in order of their appearance in the configuration file." Before relabeling, a target already carries its per-target labels plus a `job` label set from `job_name`. Special `__`-prefixed labels are available during this phase: `__address__` (the `host:port` to scrape — after relabeling, `instance` defaults to this value if not otherwise set), `__scheme__`, `__metrics_path__`, `__param_<name>` (first URL param named `<name>`), `__scrape_interval__`, `__scrape_timeout__`, plus histogram-related overrides (`__convert_classic_histograms_to_nhcb__`, `__always_scrape_classic_histograms__`, `__scrape_native_histograms__`) and service-discovery-supplied `__meta_*` labels. **All labels starting with `__` are stripped after target relabeling completes**; a `__tmp`-prefixed label name is the documented convention for a value meant only to be consumed by a later relabeling step (Prometheus itself guarantees never to use that prefix).

Each `<relabel_config>` step takes `source_labels` (a list of label names to read and concatenate with `separator`, default `;`), `regex` (an RE2 pattern, anchored on both ends, default `(.*)`), `target_label`, `replacement` (default `$1`), `modulus`, and `action` (default `replace`). Documented actions: `replace` (match `regex` against concatenated `source_labels`, write `replacement` — with `${1}`, `${2}` capture-group substitution — into `target_label`); `lowercase`/`uppercase`; `keep` (drop targets where `regex` does *not* match); `drop` (drop targets where `regex` *does* match); `keepequal`/`dropequal` (compare concatenated source labels directly against `target_label`'s value rather than a regex); `hashmod` (write `modulus` of a hash of the source labels — used for consistent sharding, e.g. across multiple Prometheus instances horizontally splitting a target set); `labelmap` (copy any *label name* matching `regex` to a new name derived from `replacement`); `labeldrop`/`labelkeep` (remove labels whose *name* matches/doesn't match `regex`).

Three distinct relabeling phases exist with different scope and timing: **target relabeling** (`relabel_configs`, applied before scraping — can rewrite the scrape address itself, drop entire targets, or inject labels from SD metadata); **metric relabeling** (`metric_relabel_configs`, applied to samples as "the last step before ingestion" — does *not* apply to auto-generated series like `up`; documented use case is "to exclude time series that are too expensive to ingest," i.e. cardinality control); and **alert relabeling** (`alert_relabel_configs`, applied to alerts before they reach the Alertmanager, after external labels — documented use case is making an HA pair of Prometheus servers with different `external_labels` send identical alerts so the Alertmanager can deduplicate them).

**Remote write config (`<remote_write>`).** Fields include `url`, `protobuf_message` (`prometheus.WriteRequest` for Remote Write 1.0, default, vs. `io.prometheus.write.v2.Request` for the newer, more efficient 2.0 message that adds metadata/start-timestamps/native-histograms by default), `remote_timeout` (default `30s`), `write_relabel_configs`, `send_exemplars`, `send_native_histograms`, a `queue_config` block (Section 17), and auth options including `sigv4` (AWS SigV4 request signing) and `azuread` (Azure AD auth with managed identity, workload identity, OAuth, or certificate-based auth).

## 5. Recommended Patterns

**RED/USE methods.** Not documented / could not verify: a search of the fetched Prometheus documentation (overview, best-practices, alerting-practices pages) found no verbatim reference to "RED method" or "USE method" terminology anywhere in Prometheus's own docs. [Inference, not confirmed in docs] The alerting-practices guidance below (alert on symptoms, focus on request rate/error rate/latency for serving systems) is substantively the same philosophy commonly labeled "RED," but Prometheus's own documentation frames it independently, citing Rob Ewaschuk's "My Philosophy on Alerting" rather than the RED/USE acronyms.

**Recording rules — naming and aggregation discipline.** [Source: https://prometheus.io/docs/practices/rules/] Recording rules "should be of the general form `level:metric:operations`" — `level` is the aggregation level/labels of the output, `metric` is the (largely) unchanged source metric name (stripping `_total` when `rate()`/`irate()` is applied), and `operations` lists applied operations, newest first. "When aggregating up ratios, aggregate up the numerator and denominator separately and then divide. Do not take the average of a ratio or average of an average, as that is not statistically valid." Always specify a `without` clause naming the labels being aggregated away, to preserve labels like `job` and avoid silent conflicts.

**Recording/alerting rule mechanics.** [Source: https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/] Recording and alerting rules live in a `rule_files`-referenced YAML file organized into named `groups`; "Rules within a group are run sequentially at a regular interval, with the same evaluation time." `promtool check rules /path/to/file.yml` syntax-checks a rule file offline before loading it. [Source: https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/] An alerting rule's optional `for` clause requires the alert expression to stay true across evaluations for that duration before the alert transitions from `pending` to `firing`; `keep_firing_for` keeps a resolved-looking alert firing for a grace period afterward, to dampen flapping. `labels` and `annotations` support Go-template-style variable substitution (`{{ $labels.<name> }}`, `{{ $value }}`, `{{ $externalLabels.<name> }}`).

**Alerting-rule design.** [Source: https://prometheus.io/docs/practices/alerting/] "Aim to have as few alerts as possible, by alerting on symptoms that are associated with end-user pain rather than trying to catch every possible way that pain could be caused." For online serving systems: "Only page on latency at one point in a stack" and "page on user-visible errors" rather than every downstream failure. For batch jobs: page only if a job "has not succeeded recently enough" to cause user-visible problems, generally allowing at least two full run-cycles of slack. The guide also stresses **metamonitoring**: "have alerts to ensure that Prometheus servers, Alertmanagers, PushGateways, and other monitoring infrastructure are available and running correctly," ideally supplemented by external blackbox checks as a fallback if internal monitoring fails outright.

**Exposition format.** [Source: https://prometheus.io/docs/instrumenting/exposition_formats/] "As of Prometheus version 2.0, all processes that expose metrics to Prometheus must use a text format, by default. An alternative, protobuf format may be used behind [] HTTP negotiation." The Prometheus **text format** (`Content-Type: text/plain; version=0.0.4`, UTF-8, `\n`-terminated lines) is line-oriented: `# HELP <metric> <docstring>` and `# TYPE <metric> <type>` comment lines carry documentation and type metadata, and the format natively supports the Counter/Gauge/Histogram/Summary/Untyped primitives. Client libraries in each supported language implement this format (and, optionally, the OpenMetrics or protobuf formats) so that any HTTP server can be scraped by Prometheus without depending on a specific library.

## 6. Anti-Patterns

**High-cardinality labels.** [Source: https://prometheus.io/docs/practices/naming/] Prometheus's own naming/labeling best-practices guidance is explicit and strongly worded: "**CAUTION**: Remember that every unique combination of key-value label pairs represents a new time series, which can dramatically increase the amount of data stored. **Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values.**" The same page also cautions against encoding label *names* into the metric name itself ("this introduces redundancy and will cause confusion if the respective labels are aggregated away"). [Source: https://prometheus.io/docs/prometheus/latest/configuration/configuration/] Operationally, Prometheus provides several config-level guardrails against runaway cardinality: `sample_limit`, `label_limit`, `label_name_length_limit`, `label_value_length_limit`, and `target_limit` on each scrape config, all of which fail the entire scrape rather than silently truncate it once exceeded. [Source: https://prometheus.io/docs/prometheus/latest/command-line/promtool/] `promtool check metrics --extended` performs cardinality analysis against a metrics payload, and `promtool tsdb analyze` analyzes "churn, label pair cardinality and compaction efficiency" directly against an on-disk TSDB.

**Using Prometheus as long-term storage without a remote-write backend.** [Source: https://prometheus.io/docs/prometheus/latest/storage/] "Note that a limitation of local storage is that it is not clustered or replicated. Thus, it is not arbitrarily scalable or durable in the face of drive or node outages and should be managed like any other single node database." The docs frame extended local retention as *possible* ("With proper architecture, it is possible to retain years of data in local storage") but position remote-write/remote-read integration with a dedicated long-term-storage backend as the documented path for durability and horizontal scale beyond a single node, rather than growing local retention indefinitely. [Source: https://prometheus.io/docs/introduction/faq/] The FAQ pushes back on the "Prometheus doesn't scale" framing directly — "A single instance of Prometheus can be more performant than some systems positioning themselves as long term storage solution for Prometheus. You can run Prometheus reliably with tens of millions of active series" — while still directing users who need more to federation or to the long-term-storage integrations list (Section 14).

**Other documented anti-patterns.**
- [Source: https://prometheus.io/docs/prometheus/latest/querying/basics/] Running large, unbounded ad-hoc queries directly in graph mode against high-cardinality data — the docs recommend iterating in tabular view first and pre-recording expensive expressions.
- [Source: https://prometheus.io/docs/operating/security/] Exposing Prometheus's HTTP endpoints (including `/metrics`, API endpoints, and Go's `/pprof`) to "publicly accessible networks like the internet... unless you know what you are doing and have taken appropriate measures" — the docs state it is "easily possible to overload and ultimately DoS servers with requests to these endpoints."
- [Source: https://prometheus.io/docs/alerting/latest/high_availability/] Load-balancing Prometheus → Alertmanager traffic through a load balancer instead of configuring every Alertmanager instance directly in `prometheus.yml`: "❌ Don't use a load balancer / ✅ Configure all instances in Prometheus" — a load balancer reintroduces a single point of failure the HA design is meant to eliminate, and breaks the peer-position-based deduplication the cluster relies on.

## 7. Security

**Native auth/TLS — historically thin, explicitly experimental.** [Source: https://prometheus.io/docs/prometheus/latest/configuration/https/] "Prometheus supports basic authentication and TLS. This is **experimental** and might change in the future." Server-side TLS/auth is configured via a separate `--web.config.file` (YAML), not the main `prometheus.yml` — this file is re-read on every HTTP request, so certificate/config changes apply immediately without a restart. `tls_server_config` supports `cert_file`/`key_file`, `client_auth_type` (must be `RequireAndVerifyClientCert` for genuine mTLS enforcement — "Other values are insecure," per the docs' own annotation), `client_ca_file`, `client_allowed_sans`, `min_version`/`max_version` (default `TLS12`/`TLS13`), and configurable cipher suites. `basic_auth_users` maps usernames to bcrypt-hashed passwords for the web server's own basic auth.

[Source: https://prometheus.io/docs/operating/security/] Consistent with that, the security-model page states: "Prometheus, and most exporters, support TLS. Including authentication of clients via TLS client certificates... We default to TLS 1.2 as minimum version... based on Qualys SSL Labs recommendations, where we strive to achieve a grade 'A'... TLS will be added to Java exporters in the future [i.e., is not yet present everywhere]. HTTP Basic Authentication is also supported. Basic Authentication can be used without TLS, but it will then expose usernames and passwords in cleartext over the network." Basic-auth passwords are stored server-side as bcrypt hashes with a user-chosen round count.

**Delegation to reverse proxies.** The security-model page's own opening caution — that Prometheus HTTP endpoints "should not be exposed to publicly accessible networks like the internet (unless you know what you are doing and have taken appropriate measures)" — combined with the explicitly-experimental native auth feature, is the documented basis for the common practice of terminating auth/TLS at a reverse proxy in front of Prometheus. [Inference, not confirmed in docs] Prometheus's docs do not use the phrase "reverse proxy delegation" verbatim as a recommendation, but the CORS/CSRF guidance below is explicitly framed around a reverse-proxy deployment topology, implying it as the expected production pattern.

**Threat model / trust boundaries.** [Source: https://prometheus.io/docs/operating/security/] "It is presumed that untrusted users have access to the Prometheus HTTP endpoint and logs. They have access to all time series information contained in the database... It is also presumed that only trusted users have the ability to change the command line, configuration file, rule files and other aspects of the runtime environment." The administrative HTTP API (deleting time series, etc.) is gated behind `--web.enable-admin-api` (disabled by default); HTTP-triggered reload/shutdown is gated behind `--web.enable-lifecycle` (also disabled by default). For Alertmanager: "Any user with access to the Alertmanager HTTP endpoint has access to its data. They can create and resolve alerts. They can create, modify and delete silences," and by default Alertmanager serves `/api/v2` with `Access-Control-Allow-Origin: *`, which "grants API access to any website visited by a browser capable of reaching the service" if no authentication is configured.

**API/injection security.** [Source: https://prometheus.io/docs/operating/security/] "As administrative and mutating endpoints are intended to be accessed via simple tools such as cURL, there is no built in CSRF protection" — the docs recommend blocking such paths at a reverse proxy if needed. If untrusted input is interpolated into PromQL (e.g. console-template URL parameters), the docs warn it must be escaped to avoid label-matcher injection, giving the worked example of `up{job="<user_input>"}` becoming an injected matcher if `<user_input>` contains `"} or some_metric{zzz="`.

**Vulnerability disclosure.** [Source: https://prometheus.io/docs/operating/security/] Security bugs not yet public should go to the relevant repo's MAINTAINERS file plus `security@prometheus.io`. "Prometheus is maintained by volunteers, not by a company. Therefore, fixing security issues is done on a best-effort basis. We strive to release security fixes within 7 days for: Prometheus, Alertmanager, Node Exporter, Blackbox Exporter, and Pushgateway." The project explicitly does **not** treat pure denial-of-service reports (crashing a component by overloading it) as private-disclosure-worthy security vulnerabilities, framing resource exhaustion as an expected consequence of the documented security model rather than a bug.

## 8. Performance

**Local TSDB storage/memory footprint.** [Source: https://prometheus.io/docs/prometheus/latest/storage/] "Prometheus stores an average of only 1-2 bytes per sample," giving the capacity-planning formula `needed_disk_space = retention_time_seconds * ingested_samples_per_second * bytes_per_sample`. To reduce ingestion rate, the docs recommend reducing the number of scraped series (fewer targets or fewer series per target) over simply increasing the scrape interval, "due to compression of samples within a series." Retention defaults to `15d` if neither `--storage.tsdb.retention.time` nor `--storage.tsdb.retention.size` is set; when using size-based retention, "we recommend setting the retention size to, at most, 80-85% of your allocated Prometheus disk space" to leave headroom for the temporary extra space compaction needs (source and newly-compacted blocks coexist on disk briefly). **Non-POSIX-compliant filesystems, including NFS (and AWS EFS), are explicitly unsupported for local storage**: "unrecoverable corruptions may happen." `--storage.tsdb.wal-compression` (default enabled since 2.20.0) roughly halves WAL size for modest extra CPU.

**Scrape-interval trade-offs.** [Source: https://prometheus.io/docs/prometheus/latest/getting_started/] The default `scrape_interval` is `15s` in the getting-started example (the documented global default is actually `1m` per the configuration reference — see Section 4); shorter intervals increase both ingestion rate/storage and query-time resolution, longer intervals reduce both. [Source: https://prometheus.io/docs/prometheus/latest/storage/] The docs frame the ingestion-rate/storage trade-off directly in terms of "fewer targets or fewer series per target" vs. scrape interval, and note series-count reduction is "likely more effective" than lengthening the interval, because per-series compression means the per-sample cost mostly comes from the WAL/chunk overhead of series churn, not raw sample count.

**Query performance on high-cardinality data.** [Source: https://prometheus.io/docs/prometheus/latest/querying/basics/] "If a query needs to operate on a substantial amount of data, graphing it might time out or overload the server or browser," with the documented mitigation being iterative query construction in tabular view and pre-computation via recording rules. `--query.max-samples` bounds how many samples a single query may load into memory (default `50000000`); `--query.timeout` bounds wall-clock query time (default `2m`); `--query.max-concurrency` bounds concurrently executing queries (default `20`).

**Automatic resource tuning (Prometheus v3+).** [Source: https://prometheus.io/docs/prometheus/latest/migration/] Prometheus v3 automatically sets `GOMEMLIMIT` to match the detected Linux container (or system) memory limit, and `GOMAXPROCS` to match the detected container CPU quota — both default-enabled and individually disablable via `--no-auto-gomemlimit`/`--no-auto-gomaxprocs`.

**Remote-write resource cost.** [Source: https://prometheus.io/docs/practices/remote_write/] "Using remote write increases the memory footprint of Prometheus. Most users report ~25% increased memory usage" (see Section 17 for tuning detail).

## 9. Testing

**`promtool test rules` — documented unit-testing feature.** [Source: https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/] "You can use `promtool` to test your rules": `promtool test rules test.yml` (or multiple test files). A test file is YAML: `rule_files` (globs of rule files under test), `evaluation_interval`, `fuzzy_compare` (loosens floating-point comparison in the last mantissa bit), `group_eval_order`, and `tests` (a list of `<test_group>` entries). Each test group supplies `input_series` using a compact expanding notation — e.g. `'-2+4x3'` expands to `-2 2 6 10` (start at −2, three further samples incrementing by 4), `'_'` denotes a missing sample, `'stale'` a stale marker — and can also express native-histogram samples inline (`{{schema:1 sum:-0.3 count:3.1 ...}}`). Against that input data, a test group supplies `alert_rule_test` cases (assert the exact set of firing alerts, with expected `exp_labels`/`exp_annotations`, at a given `eval_time`) and/or `promql_expr_test` cases (assert `exp_samples` for an arbitrary PromQL `expr` at a given `eval_time`). A `start_timestamp` field (Unix or RFC3339) anchors what `time()` returns during evaluation, making tests fully deterministic and independent of wall-clock time.

**Static config validation.** [Source: https://prometheus.io/docs/prometheus/latest/command-line/promtool/] `promtool check config <files>` validates configuration file syntax and referenced content, with a `--lint` flag applying checks (`duplicate-rules`, `too-long-scrape-interval`) and `--lint-fatal` to exit nonzero on lint findings. `promtool check rules <files>` validates rule-file syntax independent of a running server (also lint-capable), and `promtool check service-discovery <config-file> <job>` runs SD and relabeling for a given job and reports the resulting targets — a documented way to test relabeling logic without a live scrape. `promtool check metrics` lints a metrics payload (piped via stdin, e.g. from `curl .../metrics`) for exposition-format consistency and, with `--extended`, cardinality.

## 10. Deployment

**Single-server model — Prometheus is not natively clustered.** [Source: https://prometheus.io/docs/prometheus/latest/storage/] "Note that a limitation of local storage is that it is not clustered or replicated. Thus, it is not arbitrarily scalable or durable in the face of drive or node outages and should be managed like any other single node database." [Source: https://prometheus.io/docs/introduction/comparison/] The comparison-to-alternatives page reiterates this as a deliberate architectural stance versus competitors: "Prometheus servers run independently of each other and only rely on their local storage for their core functionality: scraping, rule processing, and alerting... Independent servers (which can be run redundantly in parallel) may also give you better reliability and failure isolation." Where a commercial competitor offers a distributed storage cluster out of the box, "Prometheus will be simpler to run, but at some point you will need to shard servers explicitly along scalability boundaries like products, services, datacenters, or similar aspects." [Source: https://prometheus.io/docs/introduction/faq/] For HA, the FAQ's documented answer is to "run identical Prometheus servers on two or more separate machines" — redundancy through independent replicas, not clustering; deduplication of that redundant data is handled downstream (by systems like Thanos, or by Alertmanager for identical alerts).

**Federation for scaling.** [Source: https://prometheus.io/docs/prometheus/latest/federation/] "Federation allows a Prometheus server to scrape selected time series from another Prometheus server," exposed via each server's `/federate` endpoint, driven by one or more `match[]` instant-vector selectors. Two documented use cases: **hierarchical federation** ("Prometheus to scale to environments with tens of data centers and millions of nodes" — per-datacenter servers collecting fine-grained data, global servers pulling only aggregated series from those) and **cross-service federation** (pulling a narrow slice of another team's/service's metrics into your own server for joint querying/alerting). Federating is configured as an ordinary scrape job against `/federate` with `honor_labels: true` (so the source server's own labels are preserved) and the desired `match[]` params.

**Agent mode.** [Source: https://prometheus.io/docs/prometheus/latest/prometheus_agent/] "The Prometheus Agent is an operational mode built into the Prometheus binary with the same scraping APIs, semantics, configuration, and discovery mechanism" but with querying, alerting, and local TSDB storage disabled in favor of "a customized TSDB WAL" optimized purely for scrape-then-remote-write. Documented benefits: "Improved efficiency" (WAL data is dropped immediately after a successful remote write, with only a ~2-hour on-disk buffer if the remote endpoint is unreachable) and "easier horizontal scalability for ingestion." Documented downsides: no local queries, no recording rules, no alerting — "All alerting must be done by the remote system." Enabled via `--agent`.

**Container deployment.** Not documented in the pages fetched during this pass: Prometheus's own docs (as distinct from the generic Docker Hub `prom/prometheus` image README, not fetched here) do not appear to host a first-party, prometheus.io-hosted container best-practices guide comparable to Node.js's `nodejs/docker-node` working group document. [Source: https://prometheus.io/docs/prometheus/latest/getting_started/] The documented deployment model is: download the release tarball, run the `prometheus` binary with `--config.file=prometheus.yml`, storage under `--storage.tsdb.path` (default `data/`), reload config via `SIGHUP` or `/-/reload`, and shut down gracefully via `SIGTERM`/`SIGINT` (or `Ctrl-C`) rather than an abrupt kill, "recommended... for a clean shutdown," though Prometheus does have recovery mechanisms for abrupt process failure too.

## 11. Migration

**Prometheus 2.x → 3.0 migration guide.** [Source: https://prometheus.io/docs/prometheus/latest/migration/] Prometheus publishes a dedicated "Prometheus 3.0 migration guide," described as covering "a number of backwards incompatible changes" made "in line with our stability promise." Documented migration items include: four feature flags removed and folded into default v3 behavior (`promql-at-modifier`, `promql-negative-offset`, `new-service-discovery-manager`, `expand-external-labels`) plus three removed with a dedicated replacement flag each (`no-default-scrape-port` — v3 no longer appends default ports to scrape targets; `agent` — replaced by the `--agent` CLI flag; `remote-write-receiver` — replaced by `--web.enable-remote-write-receiver`); two flags (`auto-gomemlimit`, `auto-gomaxprocs`) that became default-on behavior disablable via `--no-auto-*` flags; a scrape-config option renamed (`scrape_classic_histograms` → `always_scrape_classic_histograms`); `http_config.enable_http2` for `remote_write` defaulting to `false` (previously `true`) to better parallelize queue shards across sockets; a PromQL regex behavior change (`.` now matches newlines, affecting matchers and relabel configs); range-selector/lookback boundary semantics changing from left-closed-right-closed to **left-open-right-closed** (with a specific, documented gotcha for subqueries whose evaluation aligns perfectly with their own resolution — e.g. `foo[1m:1m]` returning one point instead of two, breaking `rate`/`increase`); `holt_winters` renamed to `double_exponential_smoothing` and gated behind `promql-experimental-functions`; stricter Content-Type enforcement on scrape responses (a missing/unparsable header now fails the scrape rather than falling back silently, configurable via `fallback_scrape_protocol`); normalization of `le`/`quantile` label values to a canonical float-like string (documented as breaking any rule/dashboard that matches on integer-looking label values like `le="1"`); and dropped support for Alertmanager's v1 API (Prometheus 3 "requires Alertmanager 0.16.0 or later").

[Source: https://prometheus.io/docs/prometheus/latest/migration/] "For the migration guide from Prometheus 1.8 to 2.0 please refer to the Prometheus v2.55 documentation" — i.e. the 1.x→2.0 guide is not reproduced in current docs but is preserved in the last 2.x-generation docs snapshot.

**Version-to-version guidance beyond major releases.** Not documented / could not verify: Prometheus does not appear to publish per-minor-version migration guides analogous to the 3.0 document; ordinary minor/patch upgrades are covered by the `[CHANGE]`-tagged entries in each release's changelog rather than a standalone guide (consistent with the API-stability framing in Section 12).

## 13. Breaking Changes

[Source: https://raw.githubusercontent.com/prometheus/prometheus/main/CHANGELOG.md] **Prometheus 3.0.0 (2024-11-14)** is the project's most recent major-version breaking-change event — "As this marks the first new major version in seven years, several breaking changes are introduced." Beyond the migration-guide items already itemized in Section 11, the changelog additionally documents: removal of `discovery.k8s.io/v1beta1` EndpointSlice and `networking.k8s.io/v1beta1` Ingress support in Kubernetes SD (both already gone from Kubernetes itself by that point); removal of the deprecated `storage.tsdb.allow-overlapping-blocks`, `alertmanager.timeout`, and `storage.tsdb.retention` flags; and a complete web UI rewrite (old UI recoverable via `--enable-feature=old-ui`, "still missing some features of the old UI (notably, exemplar display and heatmaps)" at the 3.0 release).

**TSDB on-disk format compatibility.** [Source: https://prometheus.io/docs/prometheus/latest/migration/] "The TSDB format has been changed slightly in Prometheus v2.55 in preparation for changes to the index format. Consequently, a Prometheus v3 TSDB can only be read by a Prometheus v2.55 or newer. Keep that in mind when upgrading to v3 -- you will be only able to downgrade to v2.55, not lower, without losing your TSDB persistent data." The docs recommend upgrading to 2.55 first, confirming stability, before the v3 jump.

**PromQL behavior changes across the 3.0 boundary** (also covered in Section 11): the `.` regex metacharacter began matching newlines (a v2→v3 semantic change for any query or relabel rule using `.*`/`.+` patterns), and range-selector/lookback boundary semantics changed from closed-closed to open-closed.

**Log format change.** [Source: https://prometheus.io/docs/prometheus/latest/migration/] Prometheus v3 switched from `go-kit/log` to Go's standard `log/slog`, changing the on-disk/stdout log line format (`ts=... level=info msg=...` → `time=... level=INFO source=... msg=...`) — documented explicitly as a breaking change for anything parsing Prometheus's own log output.

**API stability guarantee bounding future breakage.** [Source: https://prometheus.io/docs/prometheus/latest/stability/] "Prometheus promises API stability within a major version, and strives to avoid breaking changes for key features." Stable-for-3.x surfaces are enumerated explicitly: the query language and data model, alerting/recording rules, the ingestion exposition format, the v1 HTTP API (excluding endpoints marked experimental), the configuration file format (excluding SD/remote read/write), rule/alert file format, console template syntax, remote-write sending (1.0 spec) and receiving, Agent mode, and the OTLP receiver endpoint. Explicitly unstable-for-3.x: the `double_exponential_smoothing` function, remote read (protocol and endpoint), server-side HTTPS/basic-auth, all service discovery integrations except `static_configs`/`file_sd_configs`/`http_sd_config`, internal Go package APIs, generated web-UI HTML, Prometheus's own `/metrics` output, the exact on-disk TSDB format (though "potential changes... will be forward compatible and transparently handled"), and log-line format. "Any breaking changes will be marked as CHANGE in release notes."

## 14. Limitations

**Metrics only — explicitly not logs or traces.** [Source: https://prometheus.io/docs/introduction/faq/] Asked "How to feed logs into Prometheus?", the FAQ answers bluntly: "Short answer: Don't! Use something like Grafana Loki or OpenSearch instead. Longer answer: Prometheus is a system to collect and process metrics, not an event logging system." The docs explicitly point elsewhere for logs and, by extension, the same scoping applies to distributed tracing — Prometheus is not documented anywhere in the fetched pages as a tracing backend; its only trace-adjacent feature is **exemplars** (an experimental feature, `--enable-feature=exemplar-storage`, that lets a metric sample carry a reference such as a trace ID as metadata, not trace storage itself).

**Not natively long-term-storage/HA — named ecosystem extension points.** [Source: https://prometheus.io/docs/introduction/faq/] "Can Prometheus be made highly available? Yes, run identical Prometheus servers on two or more separate machines. Systems like **Thanos** can deduplicate the data. Many of the external systems that support remote write can also deduplicate the data." [Source: https://prometheus.io/docs/operating/integrations/] Prometheus's own integrations page names specific long-term-storage systems supporting remote write/read, explicitly including **Cortex** ("read and write"), **Grafana Mimir** ("read and write"), and **Thanos** ("read and write"), alongside VictoriaMetrics, M3DB, InfluxDB, and many others — all documented as the project's answer to horizontal scale and long-term retention beyond a single node's local TSDB, rather than Prometheus building that capability natively.

**Other documented limitations.**
- [Source: https://prometheus.io/docs/prometheus/latest/storage/] Local storage is not clustered/replicated and is unsuitable on non-POSIX filesystems (NFS/EFS explicitly called out as unsupported).
- [Source: https://prometheus.io/docs/prometheus/latest/storage/] Backfilling and rule-backfilling via `promtool tsdb create-blocks-from` explicitly do not support native histograms or staleness markers (OpenMetrics format cannot represent them), and backfilled rule groups cannot reference other rules being backfilled in the same run.
- [Source: https://prometheus.io/docs/prometheus/latest/querying/api/] Remote read has scalability limits because all requested raw data must be pulled into the querying Prometheus server before PromQL evaluation happens locally — "supporting fully distributed evaluation of PromQL was deemed infeasible for the time being."
- [Source: https://prometheus.io/docs/prometheus/latest/prometheus_agent/] Agent mode trades away local queries, recording rules, and alerting entirely in exchange for lower resource use and easier horizontal ingestion scaling.

## 15. Debugging

**`promtool debug` — pprof and metrics snapshotting.** [Source: https://prometheus.io/docs/prometheus/latest/command-line/promtool/] `promtool debug pprof <server>` fetches Go profiling (`pprof`) debug information from a running Prometheus server; `promtool debug metrics <server>` fetches metrics debug information; `promtool debug all <server>` fetches both. [Source: https://prometheus.io/docs/operating/security/] The security-model page independently confirms the underlying endpoint exists and should be access-controlled: "the `/pprof` endpoint of server components implemented in Go" is called out by name alongside `/metrics` and API endpoints as something that "should not be exposed to publicly accessible networks."

**TSDB troubleshooting tools.** [Source: https://prometheus.io/docs/prometheus/latest/command-line/promtool/] `promtool tsdb analyze <db-path> [block-id]` analyzes "churn, label pair cardinality and compaction efficiency" (with `--extended` for deeper analysis and `--match` to scope to a series selector); `promtool tsdb list [-r]` lists on-disk blocks (human-readable sizes with `-r`); `promtool tsdb dump`/`dump-openmetrics` dump raw series+sample data from a TSDB for a given time range and series-selector match, in Prometheus or OpenMetrics text output. [Source: https://prometheus.io/docs/prometheus/latest/storage/] For outright corruption, the documented recovery path is "backup the storage directory and restore the corrupted block directories from your backups... If you do not have backups the last resort is to remove the corrupted files," accepting the data-loss for the time range those blocks/WAL cover.

**Query-level debugging aids.** [Source: https://prometheus.io/docs/prometheus/latest/configuration/configuration/] `query_log_file` (global config) logs every executed PromQL query, reopened on config reload; `scrape_failure_log_file` (global or per-job) logs scrape failures specifically. [Source: https://prometheus.io/docs/prometheus/latest/querying/api/] The `stats=true`/`stats=all` query parameter on `/api/v1/query`/`/api/v1/query_range` returns query statistics (`totalQueryableSamples`, `samplesRead`, `peakSamples`, and with `stats=all`, per-step breakdowns) for diagnosing why a particular query is slow or memory-hungry.

**`promtool check service-discovery`.** [Source: https://prometheus.io/docs/prometheus/latest/command-line/promtool/] Runs service discovery for a given job against a config file and reports the resulting targets "including relabeling" — the documented way to debug why a target isn't appearing (or is appearing with unexpected labels) without needing a live Prometheus server scrape cycle to observe it.

## 16. Integration

**Grafana — the primary visualization integration.** [Source: https://prometheus.io/docs/visualization/grafana/] Prometheus's own docs describe Grafana as "an open-source analytics and visualization platform... widely used for observability, providing alerting, plugin extensibility, and a flexible query editor for real-time data visualization," and note "The Grafana data source for Prometheus is included since Grafana 2.5.0 (2015-10-28)" — i.e. first-party, built into Grafana core, not a separate plugin install. The documented setup flow: in Grafana, add a data source of type "Prometheus," point it at the server URL (e.g. `http://localhost:9090/`), then build panels whose "Metrics" tab selects that data source and accepts a raw PromQL expression in the "Query" field, with autocompletion via the "Metric" field. Legend formatting uses Go-template syntax against returned labels, e.g. `{{method}} - {{status}}`. "In Grafana 7.2 and later, the `$__rate_interval` variable is recommended for use in the `rate` and `increase` functions" (a Grafana-side variable that adapts to the panel's own scrape/step interval, avoiding under/over-windowed rate calculations). Pre-built community dashboards can be imported from Grafana.com's shared-dashboards library, filtered to the "Prometheus" data-source type, though downloaded dashboard JSON typically needs its `datasource:` fields manually corrected to match the locally-chosen Grafana data-source name. [Source: https://prometheus.io/docs/introduction/faq/] Elsewhere, Prometheus's FAQ states the project's own dashboarding recommendation directly: "Can I create dashboards? Yes, we recommend Grafana for production usage. There are also Console templates" (Prometheus's own, more limited, built-in templating mechanism).

**OpenTelemetry — receiving OTLP metrics.** [Source: https://prometheus.io/docs/guides/opentelemetry/] "Prometheus supports OTLP (aka 'OpenTelemetry Protocol') ingestion through HTTP." The OTLP receiver is **disabled by default** ("By default, the OTLP receiver is disabled, similarly to the Remote Write receiver. This is because Prometheus can work without any authentication, so it would not be safe to accept incoming traffic unless explicitly configured") and is enabled with `--web.enable-otlp-receiver`, which serves the endpoint at `/api/v1/otlp/v1/metrics`. [Source: https://prometheus.io/docs/prometheus/latest/stability/] Per the API stability page, the **OTLP receiver endpoint is itself listed as a stable surface for 3.x** — unlike remote read or service discovery integrations, it is not marked experimental.

To send OpenTelemetry metrics into that endpoint, an OTel SDK/collector is configured (via standard OTel env vars) with `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` and `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://<host>:9090/api/v1/otlp` (the SDK appends `/v1/metrics` itself per the OTel spec). Prometheus-side tuning documented for OTLP ingestion: enabling out-of-order sample ingestion (`storage.tsdb.out_of_order_time_window`, since OTel Collector replicas can batch and deliver samples out of strict order), and an `otlp.promote_resource_attributes` list that controls which OTel resource attributes (e.g. `service.name`, `k8s.cluster.name`, `deployment.environment`) get promoted directly onto every converted metric's label set rather than being left only on the synthesized `target_info` metric. Prometheus generates a `target_info` series per OTel resource carrying `service.instance.id`→`instance` and `service.name`(+`service.namespace` prefix)→`job`, plus the remaining resource attributes as labels; these can be joined at query time via the experimental `info()` PromQL function (`--enable-feature=promql-experimental-functions`) or a manual `* on (job, instance) group_left(...)` join. Four `otlp.translation_strategy` values govern metric/label name translation, ranging from the default `UnderscoreEscapingWithSuffixes` (full classic-Prometheus-compatible escaping plus type/unit suffixes) to `NoTranslation` (pass OTel names through unaltered, requiring UTF-8 support — stable since Prometheus 3.x). Delta-temporality OTLP metrics are handled via an embedded OpenTelemetry-Collector-contrib delta-to-cumulative processor, gated behind the experimental `otlp-deltatocumulative` feature flag.

**Alertmanager integration.** [Source: https://prometheus.io/docs/alerting/latest/overview/] The two-part pipeline — Prometheus evaluates alerting rules and forwards firing alerts to Alertmanager; Alertmanager owns grouping, silencing, inhibition, deduplication, and notification delivery — is configured via the `alerting.alertmanagers` block in `prometheus.yml` (Section 4), itself supporting static config or service discovery plus `relabel_configs` for Alertmanager target selection. [Source: https://prometheus.io/docs/prometheus/latest/migration/] Note the documented v3 constraint: Prometheus 3 dropped support for Alertmanager's v1 API, requiring Alertmanager ≥ 0.16.0 and `api_version: v2` in the alerting config.

## 17. Production Considerations

**Remote-write tuning at scale.** [Source: https://prometheus.io/docs/practices/remote_write/] Each remote-write destination runs its own queue, sharded, reading from the WAL: "|--> queue (shard_1) --> remote endpoint / WAL --|--> queue (shard_...) --> remote endpoint / |--> queue (shard_n) --> remote endpoint." If a shard's queue backs up, the WAL read blocks for *all* shards; failed sends retry without data loss "unless the remote endpoint remains down for more than 2 hours," after which the WAL compacts and unsent data is lost. Prometheus continuously recalculates the number of active shards based on incoming rate, outstanding-sample backlog, and per-sample send latency. Documented resource impact: "Most users report ~25% increased memory usage" with remote write enabled, dependent on data shape and series churn (each WAL series caches an ID→label mapping, so high churn drives memory up specifically). Tunable `queue_config` parameters: `capacity` (per-shard in-memory queue depth before blocking the WAL; recommended 3–10× `max_samples_per_send`), `max_shards`/`min_shards` (parallelism bounds), `max_samples_per_send`, `batch_send_deadline`, `min_backoff`/`max_backoff` (exponential retry backoff, doubling per failure up to the max). Default `capacity: 10000` and `max_samples_per_send: 2000` are documented to bound shard memory to "less than 2 MB per shard." Prometheus exposes `prometheus_remote_storage_samples_pending` for detecting when a server is falling behind on remote write.

**Federation and remote-write for multi-cluster setups.** [Source: https://prometheus.io/docs/prometheus/latest/federation/] Hierarchical federation is the documented pattern for scaling "to environments with tens of data centers and millions of nodes" — per-datacenter Prometheus servers holding full-resolution data, global servers federating only pre-aggregated (recording-rule) series from each. This is explicitly positioned as complementary to, not a replacement for, remote-write-based long-term storage integrations (Thanos/Cortex/Mimir/etc.) for durability and cross-cluster global query views.

**Scrape-interval and retention tuning.** [Source: https://prometheus.io/docs/prometheus/latest/storage/] Retention tuning trades disk footprint against history depth (`--storage.tsdb.retention.time` / `.size`, whichever triggers first wins); the docs' own guidance is to prefer reducing scraped series count over lengthening scrape interval when trying to shrink ingestion volume, since compression makes per-series overhead (not raw sample count) the dominant cost driver.

**Alerting-rule governance.** [Source: https://prometheus.io/docs/practices/alerting/] The documented operational discipline is to keep the total alert count low and symptom-focused, avoid duplicate paging across stack layers (page once, "as high up in the stack as possible"), and explicitly include metamonitoring alerts covering the health of the Prometheus/Alertmanager/Pushgateway pipeline itself, ideally backstopped by external blackbox checks in case the whole internal monitoring pipeline fails silently. [Source: https://prometheus.io/docs/alerting/latest/high_availability/] For HA Alertmanager clusters in production: configure every Alertmanager instance directly in Prometheus's `alerting.alertmanagers` (never behind a load balancer), size clusters at "2-3 instances" for typical single-datacenter production or "4-5 instances" for multi-datacenter/highly-critical setups (odd vs. even cluster size is documented as irrelevant, since the gossip protocol has no quorum/voting, "unlike consensus-based systems (etcd, Raft)"), open the cluster gossip port (default `9094`, both TCP and UDP unless using TLS transport) between all instances, and monitor `alertmanager_cluster_members`, `alertmanager_cluster_peer_info`, and `alertmanager_cluster_failed_peers` for split-brain detection. The documented "fail open" design deliberately favors duplicate notifications over missed ones during a network partition.

**LTS-line tracking for stability-sensitive production deployments.** [Source: https://prometheus.io/docs/introduction/release-cycle/] Production operators wanting bounded upgrade risk are the documented intended audience for tracking an LTS release line (currently 3.5 or 3.13, each supported for roughly one year from designation) rather than every 6-week minor release.

- **Exact scope of `io-threads`-style internal parallelism** (a Redis-comparison point raised in the sibling Redis research) has no Prometheus analogue documented in the pages fetched — Prometheus's server-side concurrency model (goroutine-per-scrape, WAL/shard architecture for remote write) is documented piecemeal across the storage, remote-write-tuning, and CLI-flags pages rather than in one consolidated internals chapter, mirroring a gap noted in the sibling Redis research for that product's own architecture chapter.

**On Grafana and OpenTelemetry integration specifically** (flagged by the task as important for downstream skill generation): both are **directly documented** by Prometheus's own docs, not unresolved. Grafana integration (Section 16) is precise and mechanical — native "Prometheus" data-source type, present in Grafana core since 2.5.0, configured with the server URL plus PromQL entered directly into panel query fields; nothing about this integration was left unresolved. OpenTelemetry integration (Section 16) is also precisely documented on the ingestion side: the OTLP receiver endpoint, its `--web.enable-otlp-receiver` gate, its stable-surface status under the 3.x API stability guarantee, the four `translation_strategy` values, the `target_info`/`promote_resource_attributes` mechanism, and the experimental delta-to-cumulative conversion path.
