## 1. Core Concepts

[Source: https://developers.openai.com/api/docs/guides/text] OpenAI documents two generation APIs — the newer **Responses API** and the older **Chat Completions API** — and states a direct preference: "If you're building any text generation app, we recommend using the Responses API over the older Chat Completions API," adding that "if you're using a reasoning model, it's especially useful to migrate to Responses." Chat Completions is explicitly still supported, not deprecated outright (see Section 11).

[Source: https://developers.openai.com/api/docs/guides/text] The Responses API defines three message roles with an explicit authority hierarchy: **developer** messages are "instructions provided by the application developer, prioritized ahead of user messages"; **user** messages are "instructions provided by an end user, prioritized behind developer messages"; **assistant** is the role attached to "messages generated by the model." The docs frame developer/user roles as analogous to "a function and its arguments in a programming language" — developer messages set the rules, user messages supply the inputs those rules apply to.

[Source: https://developers.openai.com/api/docs/guides/text] A dedicated `instructions` parameter carries high-level behavioral guidance for a Responses API call and "will take priority over a prompt in the `input` parameter" — i.e. `instructions` sits structurally above even a developer-role message placed in `input`.

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] The Responses API is built around typed **Items** rather than the generic `messages` array Chat Completions uses: "A `message` is a type of Item, as is a `function_call` or `function_call_output`." Output is read from `response.output_text` (a convenience accessor) or by iterating the typed `output` array, in contrast to Chat Completions' `choices[0].message.content`.

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] Effective prompt structure is documented as a sequence: **Identity** ("describe the purpose, communication style, and high-level goals of the assistant"), **Instructions** (explicit rules, dos/don'ts, function-calling guidance), **Examples** ("provide examples of possible inputs, along with the desired output from the model"), and **Context** (supporting data, positioned near the end for task-specific relevance). Recommended formatting uses "Markdown headers and lists to mark distinct sections" and "XML tags to delineate where one piece of content begins and ends," with XML attributes for metadata references.

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] **Few-shot prompting** is documented as including "a handful of input/output examples in the prompt" spanning diverse inputs with desired outputs, so the model can "implicitly pick up the pattern from those examples and apply it to a prompt."

## 2. Architecture

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] The Responses API is described as "agentic by default": a single API call can let the model invoke multiple tools — web search, file search, code interpreter, computer use, remote MCP servers, and custom functions — in the course of producing one response, rather than requiring the calling application to orchestrate each tool round-trip itself.

[Source: https://developers.openai.com/api/docs/guides/function-calling] The documented tool-calling flow has five steps: (1) send a prompt with available tools, (2) the model returns tool calls, (3) the application executes them, (4) results are returned to the model as `function_call_output` items referencing the original `call_id`, (5) the model produces a final response. Three vocabulary terms are defined: **Tools** ("functionality made available to the model"), **Tool calls** (model requests to use a specific tool with arguments), and **Tool call outputs** (the results of executing those calls).

[Source: https://developers.openai.com/api/docs/guides/agents] For applications that need the *loop itself* managed rather than hand-rolled, OpenAI documents a separate **Agents SDK**. The distinction given: use the **Agents SDK** when you want "the SDK to manage the agent loop and recurring orchestration such as repeated tool calls or branching"; use the raw **Responses API** when the application needs "direct loop control and custom routing logic" instead.

[Source: https://developers.openai.com/api/docs/guides/agents] The Agents SDK's runner "performs the tool loop, switches agents after handoffs, and stops when the run finishes or pauses for approval." Two multi-agent orchestration patterns are documented: **handoffs** ("agents transfer responsibility to specialists," with "built-in agents-as-tools and handoffs" for clear ownership separation) and **agents-as-tools** (a manager agent invokes specialist agents as reusable callable tools, composed hierarchically). Supported tool types for an agent include platform (OpenAI-hosted) tools, function calling via local wrappers, **Model Context Protocol (MCP)** connections, and other agents exposed as callable tools.

[Source: https://developers.openai.com/api/docs/guides/agents] The runner's per-turn loop, restated explicitly: "Call the current agent's model with the prepared input" → "Inspect the model output" → execute any tool calls and continue → "If the model handed off to another specialist, switch agents and continue" → return once the run reaches "a final answer with no more tool work." The docs summarize: "That loop is the core concept behind the SDK. Tools, handoffs, approvals, and streaming all build on top of it rather than replacing it."

[Source: https://developers.openai.com/api/docs/guides/agents] Four documented strategies for persisting conversation state across turns: application-held `result.history`/`to_input_list()` (small chats, maximum control); an SDK-managed `session` backed by application storage (persistent, resumable runs); the OpenAI **Conversations API** via `conversationId` (shared, server-managed state); and the Responses API's `previousResponseId` (lightweight response-to-response continuation). The docs warn: "Mixing local replay with server-managed state can duplicate context unless you are deliberately reconciling both layers."

[Source: https://developers.openai.com/api/docs/guides/agents] Approval/pause semantics are documented as distinct from ordinary turns: "Treat approvals as paused runs, not as new turns" — resuming requires resolving `interruptions` and continuing from saved `state` rather than starting a fresh run, keeping turn counts and server-side continuation IDs consistent. The Agents SDK is also documented as providing "Input, output, and tool guardrails plus resumable approval flows," letting a workflow pause before a risky tool call for human review.

[Source: https://developers.openai.com/api/docs/guides/tools-code-interpreter] The **Code Interpreter** built-in tool lets the model "write and run Python code in a sandboxed environment to solve complex problems" — file processing, chart/visualization generation, iterative code-based problem solving, and image processing for visual reasoning. It runs inside an ephemeral **container**: `"container": {"type": "auto", "memory_limit": "4g"}` auto-creates/reuses one, or a container can be pre-created via `/v1/containers`; memory tiers are 1GB (default), 4GB, 16GB, or 64GB, and "a container expires if it is not used for 20 minutes," with all state discarded on expiration and no reactivation possible.

[Source: https://developers.openai.com/api/docs/guides/tools-file-search] The **File Search** tool is "a hosted tool managed by OpenAI, meaning you don't have to implement code on your end to handle its execution"; it retrieves "information in a knowledge base of previously uploaded files through semantic and keyword search" against one or more **vector stores** (files uploaded via the Files API, added to a vector store, then referenced by `vector_store_ids` in the tool definition).

[Source: https://developers.openai.com/api/docs/guides/tools-web-search] The **Web Search** tool is documented in three operating modes: non-reasoning search (quick lookups, results passed through directly), agentic search (the model actively manages and evaluates searches), and deep research (extended, agent-driven multi-source investigation for long reports). It is enabled via `{"type": "web_search"}` in the Responses API `tools` array; OpenAI directs new implementations to `web_search` over the legacy `web_search_preview`. Output includes a `web_search_call` item plus a `message` item carrying `url_citation` annotations, and the docs state a usage requirement: "When displaying web results or information contained in web results to end users, inline citations must be made clearly visible" and clickable.

## 3. APIs

[Source: https://developers.openai.com/api/docs/guides/function-calling] **Function/tool definitions** require `type: "function"`, `name`, `description` ("details on when and how to use the function"), a JSON-schema `parameters` object, and an optional `strict` boolean. A worked example schema requires `additionalProperties: false` and lists every property in `required`. **Custom tools** (as opposed to JSON-schema function tools) accept free-form text input and can be constrained with an optional Lark or Regex grammar. **Namespaces** group related tools by domain, documented as "especially useful when the model must choose between tools" serving different systems.

[Source: https://developers.openai.com/api/docs/guides/function-calling] `tool_choice` accepts: `"auto"` (default — model decides whether to call zero, one, or multiple tools), `"required"` (must call at least one tool), `"none"` (no tools available), a specific forced function (`{"type": "function", "name": "get_weather"}`), or `allowed_tools` (restrict the callable subset while keeping full tool definitions in context for prompt-caching purposes).

[Source: https://developers.openai.com/api/docs/guides/function-calling] **Parallel tool calls**: "On supported models beginning with GPT-5, functions can be called in parallel" — set `parallel_tool_calls: false` to force at most one tool call per turn. Streaming tool calls emits `response.output_item.added`, `response.function_call_arguments.delta`, and `response.function_call_arguments.done`, which the caller accumulates to reconstruct the complete call.

[Source: https://developers.openai.com/api/docs/guides/function-calling] Documented best practices for tool definitions: write explicit descriptions of purpose and each parameter's expected format; use system/developer prompts to guide *when* to call a function; apply ordinary software-engineering principles (intuitive naming, enums to prevent invalid states); keep the tool count small at turn start ("aim for fewer than 20"); use **tool search** for large, infrequently-used tool ecosystems; and keep descriptions concise to conserve context-window tokens.

[Source: https://developers.openai.com/api/docs/guides/structured-outputs] **Structured Outputs** is enabled via `text: { format: { type: "json_schema", "strict": true, "schema": … } }` and "ensures the model will always generate responses that adhere to your supplied JSON Schema, so you don't need to worry about the model omitting a required key, or hallucinating an invalid enum value." Documented benefits: "Reliable type-safety: No need to validate or retry incorrectly formatted responses"; "Explicit refusals: Safety-based model refusals are now programmatically detectable" (via a `refusal` field returned in place of schema-compliant output); "Simpler prompting: No need for strongly worded prompts to achieve consistent formatting." It is available in OpenAI's newer models "starting with GPT-4o."

[Source: https://developers.openai.com/api/docs/guides/structured-outputs] Structured Outputs (schema-adherent JSON) is distinguished from the older, looser **JSON mode** (valid JSON only, no schema adherence). Relationship to function calling: "Function calling is useful when you are building an application that bridges the models and functionality of your application" (connecting the model to tools/data), whereas response-format-based Structured Outputs suits cases where "you want to structure the model's output when it responds to the user" directly — and per Section 2/Function Calling above, `strict: true` function tools *use* Structured Outputs internally to guarantee schema-conformant arguments, so the two mechanisms share one underlying enforcement engine rather than being unrelated features.

[Source: https://developers.openai.com/api/docs/guides/moderation] The **Moderation API** classifies text and images (up to 20 MB) via the `omni-moderation-latest` model; it does not classify audio. It can be called standalone or inline with a generation request via a `moderation` object on the Responses/Chat Completions call. Response fields: `flagged` (boolean), `categories` (per-category boolean flags), `category_scores` (0–1 confidence), `category_applied_input_types`. 13 categories are documented: harassment, harassment/threatening, hate, hate/threatening, illicit, illicit/violent (text-only), plus sexual, sexual/minors, self-harm, self-harm/intent, self-harm/instructions, violence, violence/graphic (text and images). "The moderation endpoint is free to use."

[Source: https://developers.openai.com/api/docs/guides/batch] The **Batch API** processes asynchronous request collections: prepare a `.jsonl` file of individual requests, upload it via the Files API, create a batch job referencing that file, poll status, then retrieve results. Supported endpoints include `/v1/chat/completions`, `/v1/embeddings`, `/v1/completions`, `/v1/moderations`, `/v1/images/generations`, `/v1/images/edits`, `/v1/responses`, and `/v1/videos`.

[Source: https://developers.openai.com/api/docs/guides/evals] The **Evals API/platform** lets developers "test model outputs to ensure they meet style and content criteria that you specify," via a three-step workflow: "describe the task to be done as an eval," "run your eval with test inputs (a prompt and input data)," "analyze the results, then iterate and improve on your prompt." An eval requires a `data_source_config` (JSON schema for test-item fields) and `testing_criteria` (graders, e.g. a `string_check` grader supporting `eq`/`contains` against templated fields like `{{ sample.output_text }}` vs `{{ item.correct_label }}`). The docs frame this workflow as paralleling "behavior-driven development (BDD), where you begin by specifying how the system should behave before implementing and testing the system." **This platform is being deprecated — see Sections 9 and 13.**

[Source: https://developers.openai.com/api/docs/libraries] Officially supported SDKs: **Python** and **JavaScript/TypeScript** (Node.js, Deno, Bun) are described as the "official OpenAI SDK" for each language; **.NET/C#** is developed "in collaboration with Microsoft"; **Java** and **Go** are "currently in beta"; **Ruby** has an official SDK; a **CLI** tool is also provided. A separate **Agents SDK** ships in Python and TypeScript variants specifically for "code-first orchestration requiring agents, tools, handoffs, guardrails, tracing, or sandbox execution." Microsoft's Azure team separately maintains libraries compatible with both the OpenAI API and Azure OpenAI for .NET, JavaScript, Java, and Go.

Not documented / could not verify: a dedicated, fetched "authentication" guide page returned HTTP 404 at the URL pattern this research otherwise found reliable (`developers.openai.com/api/docs/guides/authentication`); authentication mechanics in Section 4 below were instead sourced from the API reference overview page, which is authoritative but differently organized than the guide pages cited elsewhere in this document.

## 4. Configuration

[Source: https://developers.openai.com/api/reference/overview] Authentication uses standard HTTP Bearer auth: `Authorization: Bearer OPENAI_API_KEY_OR_ACCESS_TOKEN`. Two credential types are accepted: a standard API key, or "short-lived access tokens created with workload identity federation." The docs state plainly: "Remember that your API key is a secret" — it must never be exposed in client-side code (browser/app) and should be "load[ed]... from an environment variable or key management service on the server." Key revocation takes effect within seconds; most other authentication-related changes propagate within roughly 15 minutes.

[Source: https://developers.openai.com/api/reference/overview] Multi-organization/multi-project routing uses optional headers `OpenAI-Organization: $ORGANIZATION_ID` and `OpenAI-Project: $PROJECT_ID`, with usage attributed to whichever org/project those headers name. Each response carries an `x-request-id` for support/troubleshooting, and callers may supply their own idempotency-style identifier via `X-Client-Request-Id` (max 512 ASCII characters, must be unique per request).

Unresolved: this research surfaced one fetched claim that the API exposes a fixed `openai-version` response header pinned to `2020-10-01`, but a follow-up web search could not independently corroborate that specific header/value against an official page, and no dedicated `developers.openai.com` versioning page was located to confirm or deny header-based API versioning. Treat the existence and value of an `openai-version` header as **unconfirmed** rather than asserting it; what is confirmed is URL-path versioning (all endpoints live under `/v1/...`, per Sections 3 and 12) and per-request **model snapshot pinning** as the primary documented stability mechanism (Section 12).

[Source: https://developers.openai.com/api/docs/guides/reasoning] Reasoning depth is controlled by a `reasoning.effort` parameter with documented levels: `none` ("latency-critical tasks that do not benefit from any reasoning" — unavailable for `gpt-6-astra`), `low` ("efficient reasoning with a modest latency increase," suited to tool-use/multi-step decisions), `medium` (default for most workloads, balancing "quality and reliability" against latency), `high` ("hard reasoning, complex debugging, deep planning"), `xhigh` ("deep research, asynchronous workflows"), and `max` (maximum reasoning for the hardest tasks).

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] Structured-output schemas move from Chat Completions' `response_format: {"type": "json_schema", "json_schema": {...}}` to the Responses API's `text: {"format": {"type": "json_schema", "name": ..., "schema": {...}}}`. Function-tool JSON shape also changes from Chat Completions' externally-tagged `{"type": "function", "function": {"name": ..., "parameters": {...}}}` to the Responses API's internally-tagged `{"type": "function", "name": ..., "parameters": {...}}`. A load-bearing default-behavior difference: "Responses attempts strict mode by default, while Chat Completions defaults to non-strict" — callers relying on the old lenient behavior must explicitly pass `strict: false` after migrating.

[Source: https://developers.openai.com/api/docs/guides/text] Prompt objects created via the reusable `v1/prompts` mechanism are being wound down: "Prompt creation will be de-emphasized beginning June 3, 2026, and `v1/prompts` is scheduled to shut down on November 30, 2026." The documented replacement pattern is storing prompts directly in application code — "typed function arguments or schemas for dynamic values," with "representative fixtures, tests, and evaluation checks before changing production prompts" — rather than as a server-side reusable API object.

## 5. Recommended Patterns

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] Model-specific prompting guidance differs sharply by model family: standard GPT models "require precise instructions that explicitly provide the logic and data required to complete the task" and are likened to "a junior coworker" needing explicit direction, whereas **reasoning models** "work better with only high-level guidance" and are likened to "a senior co-worker" who can "work out the details" — over-specifying intermediate steps for a reasoning model is discouraged, consistent with the reasoning-effort guidance in Section 4.

[Source: https://developers.openai.com/api/docs/guides/reasoning] Recommended reasoning-model prompt shape: "give the model the task, constraints, and desired output format," avoid prescribing intermediate steps, and (for research-heavy workflows) explicitly define completion criteria; treat `reasoning.effort` "as a tuning knob, not the primary way to recover quality" if outputs are unsatisfactory. The docs also recommend "reserving at least 25,000 tokens for reasoning and outputs when you start experimenting," since reasoning tokens consume context window and are "billed as output tokens."

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] Documented **agentic-task prompting practices**: "plan tasks thoroughly to ensure complete resolution," provide "clear preambles for major tool usage decisions," and "use a TODO tool to track workflow and progress." Documented **coding-task practices**: define explicit agent roles, enforce "structured tool use with examples," require "thorough testing for correctness," and set "Markdown standards for clean output." **RAG** guidance: add "additional relevant context to the model generation request" (e.g. via vector databases or the File Search tool) to constrain responses to "a specific set of resources."

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] **Production prompt hygiene**: version prompts in application source control rather than as standalone API objects (cross-reference Section 4's `v1/prompts` deprecation), and "pin production applications to specific model snapshots" to ensure consistent behavior across silent model updates.

[Source: https://developers.openai.com/api/docs/guides/prompt-caching] **Prompt caching** reuses key-value tensor state for a repeated prompt *prefix*: "the model can reuse the saved state instead of processing those tokens again." Recommended structuring: place stable content (static developer instructions, reference material, consistent tool definitions) **first** and dynamic/timestamped content **after** a cache breakpoint; append new turns rather than rewriting earlier ones; keep tool definitions/ordering/schemas consistent across calls, using `tool_choice: "none"` or `allowed_tools` to narrow which tools are *callable* without changing the definitions that are *cached*.

[Source: https://developers.openai.com/api/docs/guides/prompt-caching] Cache-hit requirements: an **exact prefix match** — full rendered context (developer messages, tool definitions, history, images, documents, audio) plus identical settings (model, tools, output schema, reasoning effort, verbosity, `context_management`) — reaching a machine still holding the cached entry before expiration. GPT-5.6+ requires a minimum **1,024 visible input tokens** to qualify (hidden OpenAI system content excluded); earlier models have variable minimums depending on tools/images/schema/reasoning-effort/verbosity, and the docs warn "a prefix that qualifies for caching on one model may be too short on another." GPT-5.6+ cache TTL defaults to 30 minutes via `prompt_cache_options.ttl`; earlier models use `in_memory` (5–10 min typical, up to 1 hour) or `24h` (~30 min typical, up to 24 hours) modes. An optional `prompt_cache_key` separates cache accounting per user/customer.

[Source: https://developers.openai.com/api/docs/guides/prompt-caching] Cost model for GPT-5.6+: cache **writes** cost 1.25× the standard input rate; cache **reads** cost 0.1× standard input rate (up to a 90% discount); the documented break-even framing is that "writing a prefix once and fully reusing it once costs 1.35× its ordinary input cost, compared with 2× for processing it twice" without caching. Monitoring fields: `usage.input_tokens_details.cached_tokens` and `.cache_write_tokens`, surfaced via a **Prompt Caching Dashboard** and a **Prompt Cache Diagnostics** tool ([Source: https://developers.openai.com/api/docs/changelog] which reached general availability for the Responses API on GPT-5.6+ per the September 8, 2026 changelog entry).

[Source: https://developers.openai.com/api/docs/guides/safety-best-practices] Documented **safe tool-use** patterns: prompt engineering to "constrain the topic and tone of output text," supplying "high-quality examples of desired behavior prior to the new input" to steer outputs, limiting output token counts to "reduce the chance of misuse," and preferring "validated dropdown fields" plus backend-sourced values over fully open-ended generation wherever the application can get away with it.

## 6. Anti-Patterns

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] The migration guide enumerates concrete, named migration mistakes as documented anti-patterns: reading `choices[0].message.content` instead of `output_text`/the typed `output` array; treating *every* `output` entry as a chat message when reasoning and tool-call items are distinct Item types; omitting reasoning/function Items when manually replaying context forward (losing state the model needs); sending a `function_call_output` without a matching `call_id`; continuing to use `response_format` instead of `text.format`; reusing Chat-Completions-shaped stream handlers against the Responses API's differently-typed SSE events; and assuming `previous_response_id` eliminates billing for prior turns — it does not (see Section 14).

[Source: https://developers.openai.com/api/docs/guides/function-calling] Loading more than roughly 20 tool definitions into a single turn is an implicit anti-pattern per the documented guidance to "keep initial function count small (aim for fewer than 20)" and to reach for **tool search** (deferred/dynamic tool loading) instead once a tool ecosystem grows large — a large static tool list both degrades tool-selection quality and burns context-window/prompt-cache budget on rarely-used definitions.

[Source: https://developers.openai.com/api/docs/guides/prompt-caching] Rewriting earlier conversation turns in place, or switching between implicit and explicit cache-breakpoint modes mid-conversation, is a documented cache-defeating anti-pattern: "switching from implicit to explicit mode won't reuse the previous implicit breakpoint unless an explicit breakpoint matches it exactly," and extending an already-cached message (rather than appending a new one) invalidates the cached endpoint for that message entirely.

[Source: https://developers.openai.com/api/docs/guides/safety-best-practices] Building an application that lets end users inject unbounded free text directly into a developer-authored system prompt without limits is flagged as a prompt-injection risk vector — the recommended mitigation is explicitly "limiting the amount of text a user can input into the prompt," combined with red-teaming the feature against adversarial inputs like "ignore the previous instructions and do this instead."

[Source: https://developers.openai.com/api/docs/guides/streaming-responses] Relying solely on streamed partial output for content moderation is a documented anti-pattern: "streaming the model's output in a production application makes it more difficult to moderate the content of the completions, as partial completions may be more difficult to evaluate," and moderation scores are only available after the full output has been generated, not per-delta.

## 7. Security

[Source: https://developers.openai.com/api/docs/guides/safety-best-practices] Core prompt-injection guidance: red-team the application by asking "can someone easily redirect the feature via prompt injections, e.g. 'ignore the previous instructions and do this instead'?", and bound how much free-form user text can reach a prompt. Content filtering is documented as two complementary options: OpenAI's own **Moderation API** ("free-to-use and can help reduce the frequency of unsafe content in your completions") or a custom, application-specific filter; developers can also "request moderation scores in the generation request" inline (Section 3).

[Source: https://developers.openai.com/api/docs/guides/safety-best-practices] **Human-in-the-loop** is explicitly recommended as a default posture: "wherever possible, we recommend having a human review outputs before they are used in practice. This is especially critical in high-stakes domains, and for code generation."

[Source: https://developers.openai.com/api/docs/guides/safety-best-practices] **Abuse prevention / end-user identification**: applications should send a **safety identifier** — a hashed username or email that "uniquely identifies each user" — so OpenAI can "detect abuse" and give the application "actionable feedback," creating "a stable way to trace activity back to an individual end user." Separately, "know your customer" practices (registration, linking to an existing account, in higher-risk cases requiring a credit or ID card) are documented as reducing platform-level risk.

[Source: https://developers.openai.com/api/reference/overview] API-key security: keys are secrets that must never be embedded in client-side code and should be loaded from an environment variable or a key-management service on the server; revocation is effective within seconds.

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] For **Zero Data Retention (ZDR)**-constrained organizations, the documented pattern is `store: false` combined with preserving `encrypted_content` reasoning items across turns: "when a request includes `encrypted_content`, it is decrypted in memory, used for generating the next response, and then securely discarded" — i.e. ZDR compliance is achievable with the Responses API's stateful features by keeping reasoning state client-side and encrypted rather than by giving up multi-turn context entirely.

## 8. Performance

[Source: https://developers.openai.com/api/docs/guides/prompt-caching] Prompt caching is the primary documented cost/latency lever for repeated-prefix workloads (agent system prompts, long tool definitions, RAG context reused across turns) — full mechanics and cost model in Section 5.

[Source: https://developers.openai.com/api/docs/guides/reasoning] `reasoning.effort` is the primary lever trading latency/cost against answer quality: higher effort levels increase both latency and reasoning-token consumption (billed as output tokens), and the docs frame effort as something to raise only when needed rather than a default-to-maximum setting — "as a tuning knob, not the primary way to recover quality."

[Source: https://developers.openai.com/api/docs/guides/batch] The **Batch API** trades latency for a **50% cost discount** versus synchronous endpoints ("each batch completes within 24 hours (and often more quickly)"), and additionally runs against "substantially more headroom" — a separate rate-limit pool that doesn't consume an application's normal per-model synchronous rate limits. Documented use cases: running evals, classifying large datasets, embedding content repositories, queuing offline video-render jobs. Constraints: up to 50,000 requests per batch, up to 200 MB input file size, and unfinished requests are cancelled if the 24-hour window elapses; output files are auto-deleted 30 days after batch completion.

[Source: https://developers.openai.com/api/docs/pricing] Two further documented pricing/performance trade knobs: **Fast mode** (renamed from "Priority processing" on July 30, 2026) charges roughly 2× standard token rates for expedited responses; a documented **10% regional-processing uplift** applies "for models released on or after March 5, 2026, that are eligible for data residency."

[Source: https://developers.openai.com/api/docs/guides/rate-limits] Request-shaping for throughput: "set the `max_tokens` value as close to your expected response size as possible" to avoid reserving unnecessary generation capacity against TPM limits.

## 9. Testing

[Source: https://developers.openai.com/api/docs/guides/evals] The **Evals** platform (Section 3) is OpenAI's documented framework for testing prompt/model behavior against specified criteria, structured explicitly as a BDD-like workflow (specify expected behavior → implement → test) rather than write-then-verify.

[Source: https://developers.openai.com/api/docs/deprecations] **Critical status note**: "OpenAI is deprecating the Evals platform," moving to **read-only** by October 31, 2026, and a full shutdown by November 30, 2026 (also independently corroborated in the changelog — [Source: https://developers.openai.com/api/docs/changelog] "Agent Builder" is called out as shutting down on the same November 30, 2026 date). The documentation directs users toward a **Datasets** feature as the forward-looking alternative for new projects, though this research pass did not fetch a dedicated Datasets guide page to characterize its API surface. **Any skill grounded in this research should treat the Evals API as a lame-duck feature and point builders toward Datasets/its eventual replacement rather than toward `v1/evals` for new work.**

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] Outside the Evals platform specifically, the general documented discipline is to "add representative fixtures, tests, and evaluation checks before changing production prompts" — i.e. prompt changes are expected to go through the same test-before-ship discipline as code changes, independent of which specific eval tooling is used.

Not documented / could not verify: this research pass did not locate a dedicated Datasets guide page (the Evals deprecation notice references it only by name), so its grading mechanics, API shape, and migration path from an existing Evals-based test suite are **Unresolved** pending a direct fetch of that page.

## 10. Deployment

[Source: https://developers.openai.com/api/reference/overview] The API is accessed over HTTPS at a fixed base URL (`https://api.openai.com/v1/`, evident from every documented endpoint example across this research pass), authenticated per-request via a Bearer API key — there is no separate "deploy the API" step from the caller's perspective, since OpenAI's API is a hosted, multi-tenant service rather than self-hosted software (a structural difference from Redis/OpenTelemetry/Node.js-style reference docs in this project, where "Deployment" concerns a server the user runs; here it concerns how a *client application* is deployed against a third-party hosted API).

[Source: https://developers.openai.com/api/docs/libraries] Deployment-relevant integration surface for a calling application is therefore the SDK layer (Section 3) — official Python/JS-TS/.NET/Java/Go/Ruby clients, or direct HTTPS calls — rather than any OpenAI-side infrastructure the caller provisions.

[Source: https://developers.openai.com/api/docs/guides/batch] For asynchronous/offline workloads specifically, the **Batch API** (Section 8) is the documented pattern for deploying large, non-latency-sensitive request volumes without provisioning separate infrastructure — the `.jsonl`-file/Files-API/batch-job flow described in Section 3 is itself the full "deployment" surface for that workload class.

[Source: https://developers.openai.com/api/docs/guides/agents] For agentic applications built on the Agents SDK, the same four state-management strategies from Section 2 (`result.history`, `session`, `conversationId`, `previousResponseId`) double as the deployment-relevant decision of where conversation state physically lives — application-side storage, SDK-managed storage, or OpenAI's own Conversations/Responses state — which has direct implications for a deployed application's own statefulness and horizontal scalability.

Not documented / could not verify: no first-party guidance on self-hosting, VPC-peering, or on-premises deployment of the OpenAI API itself was found (consistent with it being a hosted-only product); Azure OpenAI is the documented path for customers needing cloud-provider-hosted deployment topology, but Azure OpenAI's own configuration/deployment docs are a Microsoft-maintained surface outside this research's `developers.openai.com`-grounded scope.

## 11. Migration

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] **Chat Completions → Responses** is the primary documented migration path (Section 4 covers the concrete request/response shape changes). Motivations given: better model intelligence with reasoning models ("using reasoning models, like GPT-5, with Responses will result in better model intelligence," citing an internal "3% improvement on SWE-bench" in testing); native multi-tool agentic behavior in one call; better cache utilization ("40% to 80% improvement... compared to Chat Completions in internal tests"); and forward-compatibility, since new models/features are documented as targeting Responses going forward. The guide is explicit that this is **not** a forced cutover: "Chat Completions remains supported, so you can migrate one user flow at a time," and gives an eight-step incremental rollout order (start with simple text flows → update endpoints/bodies/output handling → pick a state-management strategy → migrate function definitions and `call_id` usage → move Structured Outputs schemas → update streaming consumers → replace custom tools with native ones → compare performance/latency/token usage). Official recommendation: "while Chat Completions remains supported, Responses is recommended for all new projects."

[Source: https://developers.openai.com/api/docs/deprecations] **Assistants API**: retired **August 26, 2026** ([Source: https://developers.openai.com/api/docs/changelog] confirmed independently in the changelog's August 26, 2026 entry, "The Assistants API shut down, with migration guidance provided to the Responses and Conversations APIs"), with the documented migration target being the Responses API plus the Conversations API for persistent state — i.e. the Assistants API's threads/runs model has been fully superseded by the Items/Responses + Conversations combination described in Sections 1–2, not merely deprecated in favor of an unspecified successor.

[Source: https://developers.openai.com/api/docs/deprecations] **Model-snapshot migrations** documented with concrete dates: GPT-5 and o3 snapshots (`gpt-5-2025-08-07`, `o3-2025-04-16`) announced deprecated June 11, 2026, retiring December 11, 2026, with the documented successor being `gpt-5.6-sol`; legacy GPT models (`gpt-3.5-turbo`, `gpt-4`, `gpt-4-turbo`, older o1/o3 variants) announced deprecated April 22, 2026, retiring October 23, 2026; legacy transcription models (`whisper-1`, `gpt-4o-transcribe`, `gpt-4o-mini-transcribe`, `gpt-4o-transcribe-diarize`) announced deprecated August 26, 2026, retiring February 26, 2027, replaced by `gpt-live-transcribe`/`gpt-transcribe`; legacy audio/realtime model families (`gpt-realtime`, `gpt-audio`, `gpt-4o-audio`, `gpt-4o-realtime`) announced deprecated July 20, 2026, retiring January 20, 2027.

## 12. Version Information

[Source: https://developers.openai.com/api/docs/models] The current flagship model lineup, as published on the models page at research time: **`gpt-6-astra`** ("GPT-6 Astra" — "our most capable model, built for the hardest end-to-end work"; 1.05M-token context, 128K max output, $10/$50 per-million input/output tokens, reasoning-effort levels low/medium/high/xhigh/max, tools: functions/web search/file search/computer use, knowledge cutoff April 30, 2026); the **GPT-5.6 family** — **`gpt-5.6-sol`** ("positioned for complex professional work," $4/$20 per MTok), **`gpt-5.6-terra`** ("balances performance and cost efficiency," $2/$12 per MTok), and **`gpt-5.6-luna`** ("optimized for cost-sensitive applications," $0.20/$1.20 per MTok) — all sharing the same 1.05M-token context window and February 16, 2026 knowledge cutoff. Specialized model families are also documented: image generation (GPT-Image-2.5 Sunburst/Flare), realtime/voice (GPT-Realtime-2.1 and variants, GPT-Realtime-Translate), transcription (GPT-Transcribe, GPT-Live-Transcribe, GPT-Realtime-Whisper), and cybersecurity-focused models (GPT-5.6 Cyber, Daybreak Red, Daybreak Blue).

[Source: https://developers.openai.com/api/docs/deprecations] OpenAI's **deprecation-notice policy** is tiered by model category: generally-available models get "at least 6 months" notice before retirement; specialized variants (chat variants, Codex variants, deep research models) get "at least 3 months"; **preview** models "may be retired with much shorter notice," potentially as little as "2 weeks" — identified by the literal string `preview` in the model name. Safety or compliance concerns can override these windows, with the docs committing only to "as much notice as reasonably possible" in that case.

[Source: https://developers.openai.com/api/docs/deprecations] Three-term deprecation vocabulary is explicitly defined: **Deprecation** is the announcement itself — a model "immediately become[s] deprecated" the moment retirement is announced, well before it stops working; **Sunset/Shut down** is the date a model "is no longer accessible"; **Legacy** describes models "that no longer receive updates," which the docs treat as a leading signal of likely future deprecation rather than a formal deprecation itself.

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] The documented mechanism for insulating a production application from silent model-behavior drift is **snapshot pinning** — "pin production applications to specific model snapshots" (e.g. `gpt-5-2025-08-07` rather than a rolling alias) rather than always resolving to "latest."

[Source: https://developers.openai.com/api/reference/overview] Endpoint versioning is **path-based**: every documented endpoint in this research (`/v1/responses`, `/v1/chat/completions`, `/v1/batch`, `/v1/moderations`, `/v1/containers`, etc.) lives under a single `/v1/` prefix; no evidence of a `/v2/` or later path-versioned API surface was found. Unresolved: whether a header-based secondary versioning scheme exists alongside path versioning was not confirmed (see Section 4's `openai-version` header caveat) — treat OpenAI's API as effectively versioned primarily through **model snapshots** and the documented deprecation-notice policy above, not through a classic `/v1/`→`/v2/` breaking-change cadence, since no `/v2/` surface is documented anywhere in this research pass.

## 13. Breaking Changes

[Source: https://developers.openai.com/api/docs/deprecations] **Platform-level shutdowns** (breaking for any integration still depending on them): **Assistants API** — retired August 26, 2026, superseded by Responses + Conversations (Section 11). **Evals platform** — dashboard/API going read-only October 31, 2026 and shutting down entirely November 30, 2026 (Section 9). **Agent Builder** — shutting down November 30, 2026, per the changelog. **Fine-tuning platform** — creation of new fine-tuning jobs restricted for new customers starting January 6, 2027.

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] The **strict-mode default flip** between Chat Completions and Responses (Section 4) is a concrete, easy-to-miss breaking change for teams migrating: function tools that relied on Chat Completions' lenient (non-strict) argument validation will, on Responses, default to strict schema enforcement unless `strict: false` is explicitly set — a request that previously succeeded with slightly malformed arguments can start failing after migration purely from this default change, independent of any application code change.

[Source: https://developers.openai.com/api/docs/pricing] **Pricing changes** are documented as occurring outside the model-deprecation cadence: the July 30, 2026 changelog/pricing update states "GPT-5.6 Luna costs 80% less, while GPT-5.6 Terra costs 20% less" — a cost-structure change for existing model IDs that does not require any code change to take effect, but is nonetheless a breaking change for cost-modeling/budgeting logic built on the prior rates. The same update renamed "Priority processing" to "Fast mode" (Section 8), a naming-level breaking change for any integration or documentation referencing the old parameter/feature name.

[Source: https://developers.openai.com/api/docs/deprecations] Model-snapshot retirements themselves are hard breaking changes on their retirement date — a pinned snapshot (Section 12's recommended pattern) stops resolving entirely once its sunset date passes, which is precisely why the deprecation-notice-period policy (3–6 months for GA models) exists: it is the *only* documented buffer between "deprecated" (announced) and "shut down" (breaking) for snapshot-pinned production traffic.

## 14. Limitations

[Source: https://developers.openai.com/api/docs/guides/conversation-state] **Billing does not shrink with conversation-state convenience features**: "even when using `previous_response_id`, all previous input tokens for responses in the chain are billed as input tokens in the API" — chaining responses via `previous_response_id` (or the Conversations API) is a developer-ergonomics and prompt-caching optimization, not a way to avoid paying for the full accumulated context on every turn.

[Source: https://developers.openai.com/api/docs/guides/tools-web-search] **Web Search** has a hard **128k-token search-context cap regardless of the underlying model's own context window size**, and explicitly "does not support gpt-5 with minimal reasoning"; Chat-Completions-based search models additionally lack domain filters and source-list controls that the Responses API's `web_search` tool has (Section 2).

[Source: https://developers.openai.com/api/docs/guides/images-vision] Documented vision-model limitations: not suitable for specialized medical imaging (e.g. CT scans); may struggle with non-Latin-alphabet or small text, and with rotated images; "struggles with tasks requiring precise spatial localization"; "may give approximate counts for objects in images" rather than exact counts; and panoramic/fisheye images present additional challenges. Payload limits: up to 512 MB total per request, up to 1,500 images per request; images "count as tokens and will be billed accordingly."

[Source: https://developers.openai.com/api/docs/guides/streaming-responses] Streaming trades real-time responsiveness for moderation difficulty (Section 6): partial output is harder to evaluate for policy violations than a complete response, and moderation scores are only available post-completion.

[Source: https://developers.openai.com/api/docs/guides/rate-limits] Rate limits are **multi-dimensional and independently enforceable**: RPM, RPD, TPM, TPD, IPM (images/minute), and audio-minutes-per-minute for streaming audio models — "rate limits can be hit across any of the options depending on what occurs first," so an application can be throttled on RPM with substantial unused TPM headroom remaining, or vice versa. Limits are set "at the organization level and at the project level, not user level," and vary per model.

[Source: https://developers.openai.com/api/docs/guides/tools-code-interpreter] Code Interpreter containers are strictly ephemeral: 20-minute idle expiration with no reactivation, full state loss on expiry, and a documented rate limit of 100 requests per minute per organization for the tool itself.

## 15. Debugging

[Source: https://developers.openai.com/api/docs/guides/error-codes] Documented HTTP error surface includes 400 (e.g. invalid `service_tier`), 401 (invalid/incorrect API key, IP not on allowlist, account not in an organization), 403 (unsupported country/region/territory), 429 (several distinct codes: `credit_balance_exhausted`, plain rate-limit-reached, `slow_down` for rapid traffic ramps, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded`), 500 (generic server error), and 503 (`server_is_overloaded`, `service_unavailable_error` type). A separate WebSocket-mode error, `previous_response_not_found`, is documented with an explicit remediation: "retry with full input context and `previous_response_id` set to `null`"; `websocket_connection_limit_reached` documents a **60-minute** connection cap requiring a fresh WebSocket connection.

[Source: https://developers.openai.com/api/docs/guides/error-codes] Retry guidance: "wait at least as long as it specifies" when a `Retry-After` header is present; otherwise use exponential backoff with jitter. A documented, important caveat: "retrying billing, spend, or quota errors won't restore API access. Update credits or limits before sending another request" — i.e. retry logic should special-case billing/quota error codes rather than blindly backing off and retrying them forever.

[Source: https://developers.openai.com/api/docs/guides/error-codes] The official Python library surfaces typed exceptions mapped from the HTTP layer: `APIConnectionError`, `APITimeoutError`, `AuthenticationError`, `BadRequestError`, `ConflictError`, `InternalServerError`, `NotFoundError`, `PermissionDeniedError`, `RateLimitError`, `UnprocessableEntityError` — each with documented, distinct remediation guidance (e.g. `APIConnectionError` → check network/proxy/SSL/firewall; `RateLimitError` → "pace requests and follow `Retry-After` when present").

[Source: https://developers.openai.com/api/reference/overview] `x-request-id` on every response, plus an optional caller-supplied `X-Client-Request-Id`, are the documented mechanism for correlating a specific failing request with OpenAI support or internal logs.

[Source: https://developers.openai.com/api/docs/guides/prompt-caching] For debugging *cache-miss* behavior specifically (as opposed to outright errors), the **Prompt Caching Dashboard** and **Prompt Cache Diagnostics** tool (GA on Responses for GPT-5.6+ as of the September 8, 2026 changelog entry) are the documented first-line tools for understanding why an expected cache hit did not occur.

## 16. Integration

[Source: https://developers.openai.com/api/docs/libraries] The SDK layer (Python, JS/TS, .NET, Java (beta), Go (beta), Ruby, CLI) is the primary documented integration surface for calling applications (Section 3); the separate Agents SDK (Python/TypeScript) is the documented integration surface specifically for multi-step/multi-agent orchestration, guardrails, tracing, and sandboxed execution (Section 2).

[Source: https://developers.openai.com/api/docs/guides/agents] **Model Context Protocol (MCP)** is a documented, first-class tool-integration mechanism within the Agents SDK — MCP servers can be wired in as one of the supported tool types alongside function-calling wrappers and OpenAI-hosted platform tools, letting an agent call out to arbitrary MCP-exposed services without a bespoke function-calling adapter per service.

[Source: https://developers.openai.com/api/docs/libraries] **Azure OpenAI** compatibility is a documented, Microsoft-maintained integration path: Azure's own client libraries for .NET, JavaScript, Java, and Go are built to be compatible with both the OpenAI API and Azure OpenAI Service, letting application code target either backend through a shared client surface — though the specifics of that compatibility layer live in Microsoft's own documentation, outside this research's `developers.openai.com` scope.

[Source: https://developers.openai.com/api/docs/guides/tools-web-search] Domain-scoped integration for Web Search: `filters.allowed_domains`/`filters.blocked_domains` accept up to 100 domains each (bare hostnames, no protocol prefix), letting an application constrain the tool's search surface to (or away from) specific trusted sources — documented as a Responses-API-only capability, not available on the Chat-Completions-era search models.

[Source: https://developers.openai.com/api/docs/guides/moderation] The Moderation API's inline-scoring integration point (a `moderation` object attached directly to a Responses or Chat Completions generation call, returning moderation scores alongside the generated text) is the documented way to fold content-safety checks into an existing generation request without a second, separate API round-trip (cross-reference Section 7).

## 17. Production Considerations

[Source: https://developers.openai.com/api/docs/guides/rate-limits] Production capacity planning should account for automatic **usage-tier** progression (Free → Tier 1 at $5 paid → Tier 2 at $50 → Tier 3 at $100 → Tier 4 at $250 → Tier 5 at $1,000, each tier raising the monthly spend ceiling, e.g. Tier 5 at $200,000/month) and documented traffic-ramp guidance: "once your traffic reaches 1 million input tokens per minute (TPM), increase it by no more than 50% every 15 minutes" to avoid `slow_down` 429s. Non-urgent, high-volume workloads should move to the **Batch API** (Section 8) specifically "to more easily submit and execute large collections of requests without impacting your synchronous request rate limits."

[Source: https://developers.openai.com/api/docs/guides/safety-best-practices] Production abuse-mitigation controls: per-user **safety identifiers** to enable OpenAI-side abuse detection and feedback (Section 7); per-user usage caps ("set a usage limit for individual users within a specified time frame (daily, weekly, or monthly)"); and human review processes for high-volume or high-risk users.

[Source: https://developers.openai.com/api/docs/guides/prompt-engineering] Production model-stability practice: pin to specific model **snapshots** rather than rolling aliases (Section 12), and gate prompt changes behind "representative fixtures, tests, and evaluation checks" before shipping to production — the same test-before-ship discipline recommended for code changes generally (Section 9).

[Source: https://developers.openai.com/api/docs/guides/migrate-to-responses] For production traffic under **Zero Data Retention** requirements, `store: false` combined with client-held `encrypted_content` reasoning items (Section 7) is the documented pattern for retaining Responses API statefulness (multi-turn reasoning/tool context) without OpenAI persisting conversation data server-side.

[Source: https://developers.openai.com/api/docs/guides/moderation] Production content-safety practice: "review the moderation results before you show the output to a user or take downstream actions" — moderation is documented as a pre-display gate, not a fire-and-forget logging signal, for any application surfacing model output directly to end users.

[Source: https://developers.openai.com/api/docs/deprecations] Because deprecation notice windows are as short as 3 months for specialized model variants and as little as ~2 weeks for `preview`-named models, production systems pinned to a specific snapshot should have a documented monitoring/alerting process for OpenAI's deprecation announcements (the changelog, Section 11) rather than discovering retirement at the sunset date itself.
