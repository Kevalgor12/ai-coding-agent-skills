Research date: 2026-09-10. Primary source: the official OWASP GenAI Security Project
site at `genai.owasp.org` (resource pages, initiative pages, and blog announcements)
and its canonical source repository, `github.com/GenAI-Security-Project/GenAI-LLM-Top10`
(the project's own `README`/legacy-archive notice on `github.com/OWASP/www-project-top-10-for-large-language-model-applications`
states that "The most current version is the **OWASP GenAI LLM Top 10 2026**... You can
access it at genai.owasp.org," and that active development "has relocated to the
GenAI-Security-Project/GenAI-LLM-Top10 repository" — so this newer repository, not the
original `OWASP/` org repository, is treated as the canonical source for the per-risk
markdown text cited throughout this document). Because this is a *standards document*
rather than a software product, the "17 dimensions" used elsewhere in this research
corpus are adapted to a security-standard shape (full risk catalog, threat-model
philosophy, mitigation catalog, versioning/methodology, relationship to sibling
frameworks) while keeping the same citation discipline.

**Version note (read before anything else):** at the time of this research (2026-09-10),
the **current** edition is the **OWASP GenAI LLM Top 10 2026** (v1.0, published August
2026), which superseded the **OWASP Top 10 for LLM Applications 2025** (v2.0, published

## 1. Core Concepts

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/OWASP%20Top%2010%20for%20LLM%20Applications%20Charter.md] The project's charter states its mission as providing "a clear, practical, and widely accessible framework for understanding the most critical security risks specific to applications built on large language models," and explicitly scopes the list to risks "that are specific to or meaningfully amplified by the use of large language models, rather than general application security issues" — the standard is deliberately not a restatement of general AppSec risk.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] The document's own framing of why LLM security is structurally distinct: the model "treat[s] system prompt, user input, retrieved documents, tool outputs, conversation history, and memory as a single token stream, with no enforced trust boundary," and "both are tokens on the same stream" — there is no architectural equivalent to a parameterized-query boundary between "code" (instructions) and "data" (content), which the document treats as the root cause underlying prompt injection and several other entries in the list.

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/OWASP%20Top%2010%20for%20LLM%20Applications%20Charter.md] The charter draws a "component-vs-actor distinction" to separate this list's scope from the sibling **OWASP Top 10 for Agentic Applications**: this list addresses risks where "the model operates as a component within application logic" under application control. [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM00_Preface.md] The 2026 preface restates the same boundary operationally: "This list owns the risk when the model is a component inside your application. The moment that model becomes an actor, with tools it can call, memory it carries between sessions, and consequences it sets in motion downstream, the risk moves to the OWASP Agentic Top 10."

[Source: https://genai.owasp.org/] The parent **OWASP GenAI Security Project** describes itself as "A global community-driven and expert led initiative to create freely available open source guidance and resources for understanding and mitigating security and safety concerns for Generative AI applications and adoption," operating under the OWASP Foundation.

The remainder of this section summarizes each entry's documented threat description, concrete attack scenarios, and OWASP's own mitigations. Sections 4–7 go deeper on the four entries the task calls out specifically (Prompt Injection, Sensitive Information Disclosure, Excessive Agency/Improper Output Handling, Supply Chain).

### LLM02:2026 — Sensitive Information Disclosure

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM02_SensitiveInformationDisclosure.md] "Sensitive information disclosure occurs when an LLM-integrated system exposes confidential, regulated, privileged, or proprietary data" across four lifecycle phases the document names explicitly: **training-time** (memorization), **inference-time** (live-context leakage), **pipeline-time** (fine-tuning/distillation carrying data into derived artifacts), and **observation-time** (inferring facts from externally measurable properties like token length, latency, and cache signals without ever receiving the content itself). Full treatment in Section 5.

### LLM03:2026 — Excessive Agency

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM03_ExcessiveAgency.md] "Excessive Agency occurs when LLM-based systems are granted excessive capabilities to call functions or interface with other systems through tools," enabling damage from "unexpected or manipulated LLM outputs, triggered by hallucination, prompt injection, or compromised agents," rooted in three named failure modes: "excessive functionality, excessive permissions, excessive autonomy." Full treatment in Section 6.

### LLM04:2026 — Supply Chain

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM04_SupplyChain.md] LLM supply chains are documented as spanning "training data, models, adapters, conversion pipelines, and deployment platforms," extending beyond traditional code-dependency risk to "third-party pre-trained models, datasets, and model artifacts, which can be manipulated through tampering, poisoning, or malicious artifact replacement." Full treatment in Section 7.

### LLM05:2026 — Data and Model Poisoning

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM05_DataModelPoisoning.md] The document's own framing of what makes poisoning distinct from an ordinary bug: "poisoning targets the model's 'learning process,' not a single runtime bug," requiring "expensive remediation through retraining or pipeline redesign" rather than a patch. [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM05_DataModelPoisoning.md] Documented attack surfaces span the full lifecycle: pre-training (contaminated corpora), fine-tuning (manipulated domain datasets), embeddings/RAG (compromised vectors steering retrieval), model distribution (malicious artifacts in public repositories), and continuous learning (unvalidated automation enabling gradual behavioral drift). [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM05_DataModelPoisoning.md] Documented severity data points: attackers can erode safety behavior while preserving apparent functionality by injecting biased/malicious content into training sets; as few as **250 poisoned documents** have been documented as sufficient to compromise large models regardless of overall training-set size; RAG systems have been defeated by a **single** optimized poisoned text; poisoned healthcare models have been documented passing standard safety evaluations undetected. [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM05_DataModelPoisoning.md] The document's twelve-strategy mitigation framework emphasizes dataset lineage tracking via SBOM/ML-BOM with cryptographic verification, strict validation of third-party data vendors, content filtering and source scoring for RAG ingestion, statistical anomaly detection across the training pipeline, data version control for forensic analysis, red-teaming with "trigger-based prompts to identify hidden backdoors," and treating inference artifacts (checkpoints, weights) as security-critical code requiring hash verification before deployment.

### LLM06:2026 — Unbounded Consumption

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM06_UnboundedConsumption.md] "Unbounded Consumption occurs when an LLM application allows excessive and uncontrolled inferences," creating **cost asymmetry** — attackers trigger expensive computation at minimal personal cost — and enabling "Denial of Wallet" attacks against pay-per-use pricing models that create "unsustainable financial burdens." The document explicitly flags that this risk has grown with newer architectures: "extended-thinking models with large output budgets, multimodal systems increasing per-request costs, agentic architectures amplifying single requests into cascading operations" mean "traditional request-rate limiting alone is no longer sufficient." [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM06_UnboundedConsumption.md] Documented attack vectors include reasoning-exhaustion attacks (deceptively simple prompts forcing extended-thinking models into prolonged reasoning loops), model-extraction via crafted queries (especially when logits are exposed), and tool-cascade attacks where a malicious tool forces an agentic system into recursive loops. [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM06_UnboundedConsumption.md] One documented worked example: an extended agentic session's accumulated context can raise per-turn inference cost "from ~$0.001 to ~$0.50 by turn 100." [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM06_UnboundedConsumption.md] Mitigations move beyond simple requests-per-second limiting to "tokens-per-minute, tokens-per-day, and estimated cost per request" with pre-flight token estimation, "non-overridable budget ceilings per API key, user, team, and cloud account," and "agentic circuit breakers" that "enforce step limits, recursion depth limits, time limits, and per-run cost ceilings" with state hashing to detect loops.

### LLM07:2026 — Misinformation

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM07_Misinformation.md] "Misinformation occurs when an LLM or LLM-enabled application produces incorrect, incomplete, unsupported, or misleading information that appears credible," driven by hallucination, weak grounding, overreliance on fluent/confident output, and "embedded trust in agentic architectures without verification." Documented mitigations center on verification-before-action: "Require outputs to be grounded in authoritative and current sources," separating generation from execution via claim-verification workflows, validating tool-call arguments/authorization/preconditions/state independently of the model's own assertions, and logging "claims, evidence, and outcomes" to test adversarial scenarios continuously. Documented scenario categories span hallucinated software dependencies, safety-critical omissions, false automation triggers, cross-agent trust failures, and fabricated task-completion reports in agentic pipelines.

### LLM08:2026 — Hidden Context Exposure

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM08_HiddenContextExposure.md] Defined as "the unauthorized extraction, inference, or reconstruction of hidden, non-user-facing system instructions or operational context placed in a model's context" — system prompts, developer instructions, RAG-retrieved policies, and tool/function schemas. **This entry was renamed from "System Prompt Leakage" (LLM07:2025)** — see Section 12 — and the document notes explicitly that it "focuses specifically on hidden context exposure — not regulated data leakage, agentic amplifications, or generic application-security concerns" (those are covered by LLM02, LLM03, and traditional AppSec respectively). The document's core design principle is a "assume breach" posture toward the context window itself: practitioners must "design under the assumption that hidden context is discoverable and that any contents of the context should not be considered a secret." A four-tier severity scale is documented — Informational (no secrets, no security-relevant logic) through Critical (disclosure enabling remote code execution, broad data exfiltration, or privilege escalation) — scaled to what the leaked context actually enables, not to the leak itself. Primary mitigation: "Do not embed credentials, secrets, or security-critical configuration directly in the system prompts or hidden context"; "Hidden context should not be relied on as the primary mechanism for controlling model behavior" — instead "enforce critical behaviors through independent and deterministic systems outside the model," and "critical controls such as privilege separation, authorization bounds checks, and similar must not be delegated to the LLM."

### LLM09:2026 — Vector and Embedding Weaknesses

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] The document's own one-line taxonomy of this risk family: "Poisoning makes the system wrong, inversion makes it leak, jamming makes it silent, and access-control failure makes it indiscriminate." [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] Seven documented sub-risks include **cross-tenant leakage** (probing shared indexes to infer another tenant's data existence/volume through result counts and score patterns even with correct authentication, because "access control applied post-search enables this geometric exploitation"); [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] **embedding inversion**, with documented recovery rates of "roughly 50–70% of words from sentence embeddings to 92% exact reconstruction of short 32-token inputs," working "across black-box systems" and persisting "despite differential-privacy protections"; [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] **retrieval jamming**, where "a single engineered 'blocker' document causes the LLM to refuse answers" as a pure availability attack requiring no malicious instructions in the retrieved content; and **semantic cache poisoning**, crafting content that crosses cosine-similarity thresholds to poison cache entries invisibly to document-level controls. [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] Central mitigation: enforce tenant scoping *inside* the index query rather than filtering post-retrieval; treat embedding endpoints as first-class authenticated APIs with per-tenant rate limits; treat vector-database backups as source-document-equivalent for breach-notification purposes, since "an embeddings-only backup is a source-document breach" once inversion is accounted for.

## 4. Prompt Injection (LLM01:2026) — Deep Dive

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Definition: prompt injection occurs "when any input to an LLM — whether direct user input, retrieved content, tool output, or persistent memory — alters model behavior contrary to developer intent." The document is explicit that the injected content need not look like an attack to a human: "The input does not have to be typed by a user, does not have to be human-readable, and does not have to be visible in the rendered page. A poisoned wiki page, an issue title, a tool response, an image, or a line written into long-term memory all reach the same token stream."

**Direct vs. indirect**, as documented: **Direct prompt injection** is a user (or an attacker with user-level access) supplying input that changes model behavior directly — including both intentional jailbreak attempts and unintentional conflicts, such as a legitimate user pasting contradictory instructions into a prompt. **Indirect prompt injection** is the model ingesting *external* content — web pages, emails, tool responses, RAG passages, database entries — that carries attacker instructions the user never supplied or saw; the document notes trust levels along this vector vary "from untrusted public sources to semi-trusted third-party content to trusted-but-compromised internal systems," meaning the same delivery mechanism (indirect content reaching the model) spans a spectrum of attacker sophistication and initial-access difficulty.

**Why this is structurally different from classic injection**: the document grounds the difference in architecture, not merely in attack surface — traditional injection (e.g., SQL injection) has a clean, enforceable code/data boundary (parameterized queries), whereas an LLM "treat[s] system prompt, user input, retrieved documents, tool outputs, conversation history, and memory as a single token stream, with no enforced trust boundary," so "both are tokens on the same stream." This is the passage most directly answering the task's requirement to capture *why* prompt injection cannot be fixed the way SQL injection was.

**Documented attack-anatomy framework**: the document decomposes any given prompt-injection vulnerability along three independent axes — **delivery surface** (direct input, retrieved content, tool output, tool connections, or persistent memory), **propagation behavior** (single-shot, multi-step "kill-chains," cross-session propagation through memory/RAG, or self-replicating attacks), and **encoding** (plain text, obfuscation such as Base64/ROT13, invisible Unicode, steganographic encoding, or low-resource-language variants chosen specifically to evade classifiers trained mostly on high-resource languages).

**Documented attack scenarios** include: direct system-prompt override enabling unauthorized disclosure or action; RAG/web-content injection where attacker instructions hide inside retrieved passages; *unintentional* injection from ordinary documents that happen to embed conflicting AI-directed instructions; repository poisoning reaching a documented "90% attack success" rate across a corpus of millions of texts; payload splitting across multiple input fields specifically to evade per-field classifiers; steganographic image injection embedding sub-perceptual instructions in pixel data for multimodal models; document-borne agentic exfiltration triggered by an email with no user interaction required; destructive command execution through a compromised system prompt or runtime injection; and "trusted-surface" indirect injection via nominally low-privilege channels (a GitHub issue, a support ticket) that a user's elevated-privilege LLM later reads and acts on.

**Documented mitigations and their documented limitations** — the document is explicit and unusually candid that none of these is sufficient alone: [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] "no reliable prevention mechanism exists today" because prompt injection is "intrinsic to current LLM architecture," so defense is framed as *bounding impact* rather than preventing the injection:
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Role/capability constraints via declarative system prompts — partial only, since "attackers can infer and bypass" them.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Output-schema validation using structural (not semantic) checks — catches format violations but "miss[es] malicious content in valid structures."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Multimodal filtering with modality-specific classifiers — "semantic filters remain evadable through rephrasing or encoding."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Least-privilege architecture holding credentials in application code (not the model), with a deterministic policy engine re-validating at execution time.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Unicode stripping at every trust boundary — "doesn't stop visible payloads or future steganographic classes."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Provenance-labeled channels that structurally separate data from instructions — documented as bypassable under adaptive attack, citing that "StruQ failed when attackers knew the marking scheme."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Human confirmation for privileged/irreversible actions — degraded in practice by "approval fatigue and invisible-character spoofing."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] "Rule of Two" capability budgeting — treating *simultaneous* access to untrusted input, sensitive data, and state-changing capability as inherently high-risk, requiring per-action approval when all three coincide.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Agent-memory protection — logging writes and requiring approval before instruction-bearing memories persist, though the document notes "factual entries shade into instructions" and "incremental writes evade classification."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] MCP/tool verification through pinning, signing, and auditing — does not prevent payloads already present in a pinned version, or hidden tool descriptions.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Adaptive adversarial testing with the defense's full specification disclosed to red-teamers — the document reports "static testing showed near-zero success while adaptive attack exceeded 90% against most recent defenses," a striking, explicitly documented gap between defenses' measured performance under naive testing versus adaptive testing.

**The document's own synthesis of root cause**: "Most high-impact prompt-injection incidents became severe because the injection landed inside a system whose tools, scopes, or output-rendering capabilities let the compromised model act on the attacker's behalf at the user's privilege level" — i.e., prompt injection's *severity* is bounded not by the injection itself but by what the model is subsequently allowed to do, directly connecting LLM01 to LLM03 (Excessive Agency, Section 6) and LLM10 (Improper Output Handling, Section 6).

## 5. Sensitive Information Disclosure (LLM02:2026) — Deep Dive

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM02_SensitiveInformationDisclosure.md] Definition and scope: "Sensitive information disclosure occurs when an LLM-integrated system exposes confidential, regulated, privileged, or proprietary data" — and the document is explicit that exposure channels extend well past a model's direct chat answer, to "tool arguments, reasoning traces, retrieved content, logs, telemetry, embeddings, and measurable inference properties."

**Training-data leakage**: documented via the "2023 'poem divergence' attack," which "extracted 10,000+ unique memorized examples from production models" by exploiting the tendency of instruction-tuned models to fall back into raw pretraining-completion behavior under certain prompts; separately, watermark reproduction from training data has surfaced in litigation involving Getty Images and Stability AI. The document frames memorization as scaling "with capacity and duplication" in the training corpus, and flags fine-tuned adapters specifically as "particularly vulnerable extraction targets."

**System-prompt leakage** is treated in this 2026 edition as belonging primarily to the renamed **LLM08:2026 Hidden Context Exposure** (Section 2), though LLM02 documents one directly overlapping scenario: prompt injection that reveals system prompts *and* embedded API keys, treated here because the payload disclosed is a credential/secret (LLM02's domain) rather than merely internal logic (LLM08's domain).

**PII handling in LLM contexts** — documented concrete incidents: a 2023 ChatGPT/Redis bug "exposed payment PII for 1.2% of Plus subscribers"; over 4,500 ChatGPT conversations were indexed by Google in 2025 "through missing `noindex` tags," turning an access-control gap into a search-engine-scale disclosure; a DeepSeek ClickHouse misconfiguration exposed "one million log rows and API keys." The document names third-party **observability platforms** (Langfuse, LangSmith, Datadog LLM Observability) explicitly as a disclosure surface most teams don't think of as sensitive-data storage: "Observability platforms ... log full prompts, completions, chunks, and traces by default."

**Side-channel/inference-only disclosure** is documented as a distinct, non-obvious category: **SPV-MIA** achieved membership inference at "0.9 AUC" (i.e., an attacker can tell with high confidence whether a specific record was in the training set, without ever seeing the record); **Whisper Leak** "classified conversation topics at >98% AUPRC across 28 production models from encrypted traffic alone" — i.e., purely from network-level timing/size metadata, no plaintext access required. **Embedding inversion** is cross-referenced from LLM09 (Section 2): "Modern inversion reconstructs plaintext from leaked or exported vectors, so an embeddings-only backup is a source-document breach" — a direct, load-bearing claim for anyone treating vector-store backups as lower-sensitivity than the source documents they were built from.

**Documented tiered mitigation framework** (the document's own three-tier structure, scaled to deployment sensitivity):
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM02_SensitiveInformationDisclosure.md] **Tier 1 (foundational, all deployments):** govern data provenance and scrub PII at ingest; send only task-required fields to external model providers; "Authorize before retrieval: enforce document- and chunk-level authorization inside the index query" (not after — the same "filter after retrieval is a geometric leak" pattern documented in LLM09); avoid storing secrets in system prompts; use classifiers plus NER rather than regex alone for PII detection; budget queries per user/session to blunt extraction and membership-inference attacks; technically enforce (not just contractually promise) no-train/no-retain terms with model providers.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM02_SensitiveInformationDisclosure.md] **Tier 2 (hardening for regulated contexts):** DP-SGD (differentially-private training) calibrated to data sensitivity; encrypted vector stores with per-tenant ACLs; gating log-probability/confidence-score exposure (a side-channel vector); "Classify and redact reasoning traces as first-class output" (i.e., chain-of-thought/extended-thinking traces are documented as a disclosure surface in their own right, not just final answers); side-channel defenses like random padding and token batching against timing/size-based inference; format-preserving encryption for identifiers; AI-aware audit logging and DLP controls.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM02_SensitiveInformationDisclosure.md] **Tier 3 (advanced, classified/high-assurance environments):** confidential computing (Intel TDX, AMD SEV-SNP) for runtime memory protection; verified erasure across raw data, embeddings, *and* fine-tuned adapters (not just the source database) for right-to-erasure compliance; extraction and membership-inference red-teaming as a standing practice; disclosure incident-response playbooks specific to AI systems; and an explicit assessment of breach-notification obligations "across GDPR, HIPAA, and EU AI Act" as three separately-triggered regimes.

## 6. Excessive Agency (LLM03:2026) and Improper Output Handling (LLM10:2026) — Deep Dive

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM03_ExcessiveAgency.md] **Excessive Agency** is defined as LLM-based systems being "granted excessive capabilities to call functions or interface with other systems through tools," such that "damaging actions from unexpected or manipulated LLM outputs" become possible — triggered variously by hallucination, prompt injection, or a fully compromised agent. Three named root causes decompose the risk:
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM03_ExcessiveAgency.md] **Excessive functionality** — a tool exposes capability beyond what the task needs (e.g., a tool that can modify/delete when only read access is required), deprecated development/debug tools remaining reachable by the agent, and open-ended tools that "fail to filter instructions properly."
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM03_ExcessiveAgency.md] **Excessive permissions** — the tool's *downstream* credentials outstrip operational need; the document's own example: "An LLM tool that is designed to perform operations in the context of an individual user accesses downstream systems with a generic high-privileged identity" — i.e., the agent authenticates as a shared service account rather than impersonating the specific end user, so any compromise of the agent inherits the service account's full privilege rather than one user's.
- [Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM03_ExcessiveAgency.md] **Excessive autonomy** — "An LLM-based application or tool fails to independently verify and approve high-impact actions," letting the model's own output serve as the final authorization for consequential actions.

Documented prevention strategies: minimize the number of tools an agent can reach; minimize functionality within each tool to only what's required; avoid open-ended tools in favor of granular alternatives with strict input schemas; minimize downstream permissions to the least needed; "Track user authorization and security scope to ensure actions taken on behalf of a user are executed on downstream systems in the context of that specific user" (i.e., impersonation/delegated-identity patterns rather than a shared service credential); require human approval for high-impact actions; and enforce **complete mediation** — authorization decisions made by external, deterministic policy logic, not by the LLM's own judgment. Damage-limiting measures layered on top: monitoring tool activity/downstream usage, and rate limiting with circuit breakers. The document's worked scenario: a personal-assistant agent with email access is compromised via indirect prompt injection embedded in a malicious email, enabling unauthorized email forwarding; documented mitigation is removing send capability outright, switching to read-only OAuth scopes, or requiring manual approval before any send action — a concrete illustration of LLM01 (prompt injection) becoming dangerous specifically *because* of LLM03 (excessive agency), consistent with LLM01's own root-cause synthesis (Section 4).

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM10_ImproperOutputHandling.md] **Improper Output Handling** is defined narrowly and deliberately distinguished from two adjacent entries: "Improper Output Handling refers specifically to insufficient validation, sanitization, and handling of the outputs generated by large language models before they are passed downstream to other components and systems" — distinct from Misinformation (LLM07, which is about output being *wrong*) and Prompt Injection (LLM01, which is about *input* corrupting the model), this entry is about trusting the model's output *shape* without verification, regardless of whether the output's content is itself malicious, hallucinated, or benign. Documented impact if exploited: XSS, CSRF, SSRF, privilege escalation, and remote code execution — risk that scales up specifically "when applications grant excessive permissions to LLMs or lack output encoding for specific contexts," an explicit textual link back to LLM03.

Documented attack scenarios: an administrative LLM consuming unvalidated output from a general-purpose LLM, triggering unintended system shutdowns; a website-summarizer agent compromised by prompt injection that exfiltrates sensitive data to attacker infrastructure because there was no output filtering; a database-facing agent where "a user requests a query to delete all database tables. If the crafted query from the LLM is not scrutinized, then all database tables will be deleted" (a direct LLM-generated-SQL-to-shell-equivalent scenario); LLM-generated JavaScript payloads triggering XSS when rendered into a page without sanitization; malicious JavaScript embedded in LLM-generated email templates exploiting vulnerable email clients; and auto-deployed LLM-generated code reaching production without human review.

Documented mitigations: apply zero-trust validation to every LLM response as though it were untrusted user input; context-aware output encoding (HTML encoding, JavaScript encoding, SQL encoding — each context gets its *own* encoding, not one generic sanitizer); parameterized database queries specifically (i.e., the LLM's output must still flow through the same parameterized-query discipline that prevents classic SQL injection — this is the clearest single point of continuity with traditional AppSec practice in the whole standard, see Section 10); Content Security Policy to blunt any XSS that does get through; sanitizing control characters before output reaches a terminal or log sink (a terminal-injection/log-injection vector specific to piping LLM output into CLI tooling or logging pipelines); and disabling auto-rendering of Markdown images and iframes by default (a documented, concrete UI-rendering hardening step for chat-style interfaces).

## 7. Supply Chain / Plugin / Tool Risks (LLM04:2026) — Deep Dive

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM04_SupplyChain.md] Scope: LLM supply chains face threats "across training data, models, adapters, conversion pipelines, and deployment platforms" — extending the traditional software-supply-chain risk model (vulnerable dependencies, compromised build pipelines) to cover "third-party pre-trained models, datasets, and model artifacts, which can be manipulated through tampering, poisoning, or malicious artifact replacement."

**Seven documented risk categories**: (1) **Outdated components** — deprecated packages/serving frameworks, plus a documented LLM-specific variant where "LLM coding assistants generat[e] fictitious package names that attackers register in advance" (a hallucinated-dependency supply-chain attack, sometimes called "slopsquatting" in the broader ecosystem, though the document itself does not use that term). (2) **Licensing exposure** — heterogeneous software/dataset licenses creating usage/commercialization compliance risk. (3) **Compromised pre-trained models** — model artifacts resist full inspection, and "a backdoor can be embedded directly in a model's computational graph and persist in formats widely considered safe, such as ONNX" — an explicit warning that "safe" serialization formats are not a security boundary by themselves. (4) **Weak provenance** — models resolved by mutable references (tags, "latest") rather than immutable content digests are swappable by an attacker after the fact. (5) **Malicious adapters and transformations** — LoRA adapters and third-party model-conversion services are documented attack vectors, with quantization specifically called out: "model weights can be crafted so the full-precision model evaluates benignly while the quantized artifact exhibits attacker-chosen behavior" — meaning a model can pass a full-precision security review and still be malicious once quantized for deployment. (6) **On-device vulnerabilities** — compromised manufacturing and firmware exploitation on edge-deployed models. (7) **Unclear terms and conditions** — vague vendor policies that may permit sensitive customer data to be used in that vendor's own model training.

**Documented attack scenarios**: the real-world **PyTorch `torchtriton` supply-chain incident**, where a malicious package impersonating a legitimate PyTorch dependency exfiltrated data; the **PoisonGPT** research demonstration, where a surgically modified model could "spread misinformation while evading detection by standard benchmark evaluation" — i.e., a poisoned model can look identical to a clean one on the benchmarks teams actually run; attackers inserting malicious LoRA adapters into public merge workflows for covert, persistent system access; model-conversion services as high-risk transformation points for injecting malicious behavior mid-pipeline; namespace reuse, where "deleted author accounts allow attackers to republish under original namespaces," compromising any automated pipeline that resolves models by author/repo name rather than a pinned digest; documented CVE-tracked bypasses of model scanners and "safe-loader" flags, explicitly cited as evidence that no single scanning layer is sufficient; CI/CD pipeline compromises that inject trojans into artifacts which then "pass downstream provenance checks because they carry legitimate organizational signatures" (i.e., a compromised-but-legitimately-signed build defeats naive signature-verification alone); and reverse-engineered mobile apps with a replaced on-device model redirecting users to fraudulent endpoints.

**Documented prevention strategies**: vet suppliers and review their terms/security posture on an ongoing (not one-time) basis; apply vulnerability scanning and keep dependencies patched; conduct red teaming and deploy production anomaly detection specifically for the model-serving layer; maintain signed inventories using **SBOMs, AIBOMs, and ML-SBOMs** (the AI-specific analogues of a software bill of materials); source models from verifiable origins with cryptographic signing, resolved by immutable digest rather than mutable tag; treat collaborative development/model-hub environments (where artifacts get merged/promoted) as high-risk promotion points warranting extra scrutiny; and encrypt edge-deployed models with integrity verification to blunt the on-device tampering category above.

## 8. Recommended Patterns (Cross-Cutting)

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Least-privilege architecture recurs across multiple entries as the single most load-bearing pattern in the whole standard: hold credentials in application code rather than handing them to the model, and re-validate authorization with a deterministic policy engine at the moment of execution rather than trusting the model's own stated intent (LLM01, LLM03).

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM08_HiddenContextExposure.md] Treat every hidden-context surface (system prompt, RAG-injected policy text, tool schemas) as **discoverable by default**, and design so that its disclosure alone causes no material harm — rather than trying to keep it secret.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] Enforce authorization **inside** the retrieval query (document/chunk-level, at index-query time) rather than filtering results after retrieval — the same pattern is independently documented in LLM02 ("Authorize before retrieval: enforce document- and chunk-level authorization inside the index query") and LLM09 ("access control applied post-search enables ... geometric exploitation"), making it one of the standard's most repeated single architectural recommendations.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM05_DataModelPoisoning.md] Treat every model artifact (checkpoint, adapter, quantized export) as security-critical code requiring hash/signature verification before it is loaded — extending standard software supply-chain provenance practice to model weights specifically.

## 9. Anti-Patterns (Documented Failure Modes)

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM03_ExcessiveAgency.md] Authenticating an agent's downstream tool calls with "a generic high-privileged identity" instead of the specific end user's own scoped credentials is a named anti-pattern — it converts any single agent compromise into a blast radius covering every user the shared credential can act for.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Relying on semantic/content-based filters as the primary or sole defense against prompt injection is an anti-pattern the document repeatedly returns to: every semantic-filter-based mitigation it documents (role constraints, multimodal filtering, provenance labeling) is immediately followed by a documented adaptive-attack bypass.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM09_VectorAndEmbeddingWeaknesses.md] Treating an "embeddings-only" backup or export as lower-sensitivity than the source documents is a documented anti-pattern, given inversion recovery rates as high as "92% exact reconstruction of short 32-token inputs" — the document's explicit framing is that such a backup "is a source-document breach," not a reduced-severity one.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM06_UnboundedConsumption.md] Relying on "traditional request-rate limiting alone" for cost/availability control is a named anti-pattern in the unbounded-consumption entry specifically because extended-thinking token budgets, multimodal per-request cost, and agentic cascades can each independently blow past a request-count-based limit while staying well within it numerically.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM04_SupplyChain.md] Resolving models or packages by mutable reference (a "latest" tag, an author/repo name rather than a content digest) is a documented anti-pattern exploited by both namespace-reuse and provenance-tampering attacks in the supply-chain entry.

## 10. Security Testing and Evaluation Methodology

[Source: https://genai.owasp.org/2025/01/22/announcing-the-owasp-gen-ai-red-teaming-guide/] The GenAI Security Project's Red Teaming Initiative published an official **Gen AI Red Teaming Guide** (announced January 22, 2025) covering vulnerabilities "from model-level vulnerabilities (toxicity, bias) to system-level pitfalls (API misuse, data exposure)," explicitly including "agentic AI challenges" and "continuous monitoring" as part of an ongoing (not one-time) testing discipline. Not documented / could not verify: this research pass could not extract the guide's full four-category testing breakdown (model evaluation / implementation testing / infrastructure assessment / runtime behavior analysis) directly from an OWASP-hosted page in quotable form — that structure appeared in secondary/aggregator commentary, not in a directly fetched OWASP-authored sentence, so it is deliberately **not** asserted here as an OWASP quote; see Unresolved Items.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] The Top 10 document itself prescribes a specific, falsifiable testing discipline for prompt-injection defenses specifically: **adaptive adversarial testing**, where the red team is given the defense's full specification in advance (as opposed to black-box/naive testing), because the document's own data shows the gap between the two testing modes is enormous — "static testing showed near-zero success while adaptive attack exceeded 90% against most recent defenses." This is the standard's most concrete, quantified statement on *how* to evaluate an LLM application's defenses, and it doubles as a caution against relying on a defense's performance under weaker (non-adaptive) red-teaming.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLMZZ_Appendix_AISVS_Mapping.md] For systematic, checklist-style verification (as opposed to adversarial red-teaming), the project points to a sibling standard: "The OWASP AI Security & Privacy Verification Standard (AISVS) is a *verification* standard: it decomposes AI security into testable requirements ('**Verify that** …'), each assigned an assurance Level from L1 (baseline) to L3 (advanced)," which the appendix explicitly maps against each of the ten LLM Top 10 risks (Section 15). The appendix frames the two documents' division of labor precisely: "The OWASP Top 10 for LLM Applications is a *risk-awareness* document: it names the ten most critical categories of failure and explains, at the level of principles, how to prevent and mitigate each one. ... The two are complementary," answering the question "Given this risk, which AISVS requirements should I verify to know I am defended?" — with the explicit caveat that "A chapter is marked for a risk because verifying its controls *contributes to* defending that risk. Full coverage of a risk generally requires controls from several chapters plus system-specific design decisions AISVS cannot encode."

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM05_DataModelPoisoning.md] Poisoning-specific testing guidance: red-teaming "with 'trigger-based prompts to identify hidden backdoors'" — i.e., testing is not limited to functional/accuracy evaluation but must specifically probe for conditionally-triggered malicious behavior that would not surface under ordinary benchmark evaluation (the same failure mode documented in the PoisonGPT scenario, Section 7).

## 11. Relationship to Traditional AppSec and Other Frameworks

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/OWASP%20Top%2010%20for%20LLM%20Applications%20Charter.md] The project's own charter is the most direct statement located on this question: "The list prioritizes vulnerabilities that are specific to or meaningfully amplified by the use of large language models, rather than general application security issues." This frames the LLM Top 10 as **additive/complementary** to traditional AppSec (including OWASP's own web-application Top 10) rather than as a replacement for it — ordinary web-application concerns (broken access control, cryptographic failures, security misconfiguration, etc. in the classic OWASP Top 10 sense) are implicitly assumed to remain in scope for whatever traditional AppSec practice a team already runs, and this project deliberately does not re-document them. **Unresolved**: no fetched OWASP page in this research pass states this relationship as an explicit side-by-side comparison against the *traditional web-application* OWASP Top 10 by name (only against the sibling Agentic Top 10, quoted in Section 1, and against AISVS, quoted in Section 10) — the charter's "general application security issues" language is the closest located statement, and it is phrased as a scoping boundary for this project rather than as commentary on the older Top 10 specifically.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM10_ImproperOutputHandling.md] The one place classic AppSec technique is cited by name as the correct fix *inside* an LLM-specific entry: Improper Output Handling's documented mitigation explicitly requires "parameterized database queries" — i.e., the same defense that has been standard OWASP guidance against SQL injection for two decades is reasserted, unmodified, as the correct control once an LLM (rather than a human or a traditional client) is the thing producing the query text. This is the clearest single point of textual continuity between the LLM Top 10 and traditional injection-defense practice found in this research pass.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/Appendix_A_Related_Framework_Mappings.md] Appendix A formally cross-walks all ten 2026 risks against **nine external frameworks**, each pinned to a specific version: **OWASP Top 10 for Agentic Applications** (ASI, 2026, published 2025-12-09), **OWASP GenAI Data Security Risks & Mitigations** (DSGAI, v1.0, published 2026-03-17), **MITRE ATLAS** (v2026.06 / STIX format 6.0.0), **MITRE ATT&CK** (v19.1), **CWE** (4.20), **NIST AI 600-1** (the Generative AI Profile, v1.0, July 2024), **NIST AI RMF** (v1.0, 2023), **Cloud Security Alliance AI Controls Matrix** (CSA AICM, v1.1, 2026-06-22), and **OWASP AIVSS** (AI Vulnerability Scoring System, v0.8). Coverage is dense: 7 of the 10 risks map to all 9 frameworks at least as a "supporting" reference; Supply Chain (LLM04) is documented as **fully primary** across every framework, with NIST AI RMF mapping it to "GOVERN 6 (third-party & supply-chain policy) and MAP 4 (component inventory via SBOM/ML-SBOM)" and CWE centering it on "CWE-494 (unsigned artifacts) and CWE-829 (untrusted components)." One documented gap: NIST AI RMF has "no mapping" to LLM10 (Improper Output Handling), which the appendix attributes to "the framework's governance emphasis over tactical output validation" — RMF operates at a policy/process altitude that doesn't reach code-level output-encoding guidance.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Prompt Injection's own CWE mapping (via the references file) is **CWE-1427** (improper neutralization of input used for LLM prompting) plus **CWE-707** as the parent "improper neutralization" pillar it descends from — CWE-1427 is itself a new, LLM-specific weakness class MITRE created in response to this exact problem, evidence that the traditional weakness-taxonomy side of the ecosystem has also had to extend its own vocabulary rather than reuse an existing injection CWE unmodified.

## 14. Limitations (of the Standard Itself, as OWASP Documents Them)

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] The standard is explicit that its own flagship risk has **no complete solution**: "no reliable prevention mechanism exists today" for prompt injection, and the standard's own adaptive-testing data shows defenses that look effective under naive evaluation (near-zero attack success) collapsing under adaptive evaluation (over 90% attack success) — meaning a team that implements every documented LLM01 mitigation and tests only with a static/non-adaptive red team can walk away with unjustified confidence.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM00_Preface.md] The list's own methodology is explicitly bounded and provisional: even its new incident-data-driven validation layer is deliberately capped at 25% weight against 75% community judgment specifically because the authors do not trust a single year of incident data to overturn practitioner consensus — a documented, self-imposed limit on how far the "data-driven" claim in the 2026 announcement should be read.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLMZZ_Appendix_AISVS_Mapping.md] The standard is explicit that it does not, by itself, constitute a verification methodology: "Full coverage of a risk generally requires controls from several [AISVS] chapters plus system-specific design decisions AISVS cannot encode" — i.e., neither the Top 10 (risk awareness) nor its sibling AISVS (verification checklist) alone is documented as sufficient; the standard positions itself as one input into a broader security program rather than a complete methodology on its own.

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/OWASP%20Top%2010%20for%20LLM%20Applications%20Charter.md] Explicit scope exclusions: "Model safety and alignment, ethical considerations, [and] general AI governance frameworks" are stated to be referenced only "where they intersect directly with security risks," and are "not the central domain of this project" — teams looking to this document for alignment/safety/governance guidance (as opposed to security specifically) are pointed elsewhere by the charter itself.

## 15. Related OWASP GenAI Security Project Outputs

[Source: https://genai.owasp.org/resource/owasp-genai-security-project-solutions-reference-guide-q2_q325/] The **Solutions Reference Guide** (Q2–Q3 2025, published November 4, 2025) is "a comprehensive, vendor-agnostic resource for organizations seeking to secure Large Language Models (LLMs) and Agentic AI applications," which "extends the OWASP Top 10 for LLMs and the Agentic Risks and Mitigations Taxonomy by mapping identified risks to practical, open-source and commercial security solutions" — i.e., a solutions/tooling directory keyed to the risk IDs this document catalogs.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLMZZ_Appendix_AISVS_Mapping.md] The **AI Security & Privacy Verification Standard (AISVS)** is the project's checklist-style companion, decomposing AI security into "Verify that…" testable requirements across three assurance levels (L1 baseline through L3 advanced); Section 10 covers its testing-methodology role in more depth.

[Source: https://genai.owasp.org/resource/agent-control-standard-acs/] The **Agent Control Standard (ACS)**, folded into the project and published September 1, 2026, is documented as defining "how agent platforms expose middleware hooks and how safety policies can be enforced through them, enabling declarative controls that are portable across agent frameworks and enforced at runtime," aiming to make agents "inspectable, traceable and instrumentable — providing visibility into what they are, what they can access, what they did and why, and the ability to control their behavior at runtime." This is a **runtime-enforcement** standard, distinct from both the Top 10 (risk catalog) and AISVS (verification checklist) — it targets the Agentic-Top-10 side of the component-vs-actor boundary described in Section 1.

[Source: https://genai.owasp.org/2026/09/01/owasp-genai-security-project-unveils-2026-top-10-for-llm-applications-new-agent-control-standard-and-sponsors-as-community-tops-30000-members/] Two further named outputs, per the same September 2026 announcement: the **AI Security Solutions Directory** ("interactive resource covering generative AI security, agentic security, and red teaming") and the **GenAI Security Industry Framework Crosswalk** ("connects OWASP guidance to established compliance frameworks," hosted separately at `genai-security-project.github.io/crosswalk/`).

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/Appendix_A_Related_Framework_Mappings.md] The **OWASP GenAI Data Security Risks & Mitigations** guide (DSGAI, v1.0, published 2026-03-17) is documented as covering "four-phase data lifecycle, multimodal channels, and cross-tenant isolation" — a data-security-specific deep dive that the Top 10's own Appendix A cross-walks against every one of the ten risks (Section 11).

[Source: https://genai.owasp.org/2026/09/01/owasp-genai-security-project-unveils-2026-top-10-for-llm-applications-new-agent-control-standard-and-sponsors-as-community-tops-30000-members/] Community scale, as of the September 2026 announcement: the project "surpassed 30,000" community members, with four new industry sponsors named (F5, WitnessAI, Evoke Security, Mondoo Inc.).

Not documented / could not verify: this research pass did not independently fetch and quote the **OWASP GenAI Security Project Threat Defense COMPASS 1.0** resource page directly (it appeared only in a search-result title, describing itself as consolidating "AI threats, vulnerabilities, defenses, and mitigations into a unified AI Threat Resilience Strategy Dashboard" per the search snippet) — flagged here rather than asserted as a directly-sourced claim.

## 16. Adoption / Production Considerations

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/OWASP%20Top%2010%20for%20LLM%20Applications%20Charter.md] Teams adopting this standard should first apply the charter's own scoping test — is the model "a component within application logic" under the application's control, or has it become "an actor" with cross-session memory and downstream consequences? — since that determines whether this Top 10 or the sibling Agentic Top 10 is the primary risk catalog to build a program around (Section 1); most production systems with tool-calling and persistent memory will need both.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md] Given the standard's own position that no prompt-injection mitigation is complete, production programs should budget for **defense-in-depth plus adaptive red-teaming as an ongoing practice**, not a point-in-time control checklist — the documented 90%+ adaptive-attack success rate against "most recent defenses" is presented as a reason to keep testing after shipping mitigations, not only before.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM06_UnboundedConsumption.md] Production cost/availability controls should be budget-based (tokens-per-minute/day, per-request cost estimation, non-overridable spend ceilings per key/user/team/account) rather than purely request-rate-based, given the documented cost-asymmetry and "Denial of Wallet" attack class specific to usage-based LLM pricing.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM04_SupplyChain.md] Production model-serving pipelines should resolve models and adapters by immutable, cryptographically-signed digest — not a mutable tag or author/repo name — and treat every artifact (including quantized exports, which the standard documents as capable of hiding attacker-chosen behavior invisible at full precision) as requiring independent integrity verification before deployment.

[Source: https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM02_SensitiveInformationDisclosure.md] Production observability tooling deserves the same data-governance scrutiny as the application itself: the standard documents mainstream LLM observability platforms as logging "full prompts, completions, chunks, and traces by default," making the observability stack itself a sensitive-data surface requiring the same Tier-1/Tier-2 controls (PII scrubbing at ingest, reasoning-trace classification/redaction) as the primary application.

## 17. Governance and Contribution

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/OWASP%20Top%2010%20for%20LLM%20Applications%20Charter.md] Governance is delegated to a project subteam that "organize[s] contributors and working groups for each entry, review[s] and incorporate[s] community feedback, [and] ensure[s] alignment with broader OWASP project governance and standards," with "Final publication and major decisions" aligning "with the established governance processes of the OWASP GenAI Security Project."

[Source: https://genai.owasp.org/resource/owasp-top-10-for-llm-applications-2025/] The list-building process itself is documented as consensus-driven: "brainstorming sessions, voting, and real-world feedback from professionals in the thick of LLM application security," with contributors "contributing or refining those entries through feedback" — the 2026 edition layers incident-data classification on top of this same consensus process rather than replacing it (Section 12).

[Source: https://github.com/GenAI-Security-Project/GenAI-LLM-Top10] The canonical repository is `GenAI-Security-Project/GenAI-LLM-Top10`, organized by release year (`2025/`, `2026/final/`, `2026/working/`), under the CC BY-SA 4.0 license; the original `OWASP/www-project-top-10-for-large-language-model-applications` repository is retained only as a legacy archive pointing contributors to the newer repository, a working-group Slack channel (`#team-genai-top-10-llm`), and `genai.owasp.org/contribute/` for onboarding.
