## 1. Core concepts

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS] CSS (Cascading Style Sheets) is a stylesheet language used to describe the presentation of a document written in HTML, XML, SVG, MathML, or XHTML — controlling how elements are rendered on screen, paper, speech, or other media. It is one of the core languages of the open web and is standardized across browsers by the W3C.

[Source: https://www.w3.org/TR/css-2026/] CSS evolved from monolithic sequential specifications (CSS1, CSS2, CSS2.1) to a modular approach starting with CSS3: "CSS Level 3 builds on CSS Level 2 module by module," and independent modules now advance beyond Level 3 on their own schedules — there is no unified "CSS Level 4" specification.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Cascade (redirect target of the older CSS_cascade/Cascade path)] The **cascade** is the algorithm that determines which CSS declaration applies when multiple rules match the same element. It proceeds through five ordered steps: (1) relevance — filter to rules whose selector matches and whose `@media`/conditional context applies; (2) origin and importance — rules are ranked by origin (user-agent, user, author) and whether they carry `!important`, with author non-important styles beating user non-important beating user-agent non-important, and the order reversing for `!important` declarations, with CSS transitions given the single highest precedence and CSS animations sitting just below `!important` author declarations; (3) specificity — same origin/importance ties are broken by selector specificity; (4) scoping proximity — within `@scope` blocks, the rule closer (fewer DOM hops) to the scope root wins on a specificity tie; (5) order of appearance — final tiebreak is source order, last declaration wins.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity] **Specificity** is a three-column weight (ID, CLASS, TYPE) compared left-to-right: ID selectors contribute 1-0-0, class/attribute/pseudo-class selectors contribute 0-1-0, type selectors and pseudo-elements contribute 0-0-1; the universal selector (`*`) and combinators contribute nothing. Inline `style=""` attributes have a specificity above all three columns. `:where()` always contributes 0-0-0 regardless of its argument; `:is()`, `:not()`, and `:has()` themselves contribute nothing but take on the specificity of their highest-specificity argument.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity] **Inheritance**: some CSS properties (e.g., typography-related properties like `color`, `font-family`) are inherited by descendant elements by default; most box/layout properties are not.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/box-sizing] The **box model** describes how an element's rendered size is computed from `content`, `padding`, `border`, and `margin`. `box-sizing: content-box` (the default) sizes only the content box, so padding/border add to the specified width/height; `box-sizing: border-box` makes the specified width/height include padding and border.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container] **Selectors, at-rules, and functions** form the rest of the language surface: selectors target elements (type, class, ID, attribute, pseudo-class, pseudo-element, combinators); at-rules (`@media`, `@supports`, `@keyframes`, `@font-face`, `@container`, `@layer`, `@property`, `@scope`, etc.) introduce conditional or declarative blocks; functions (`calc()`, `min()`, `max()`, `clamp()`, `color-mix()`, `var()`, etc.) compute values.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Syntax/Error_handling] CSS's error-handling model is a defining architectural trait, not an incidental detail: invalid declarations, unknown properties, and unrecognized at-rule preludes are silently discarded by the parser rather than raising errors, which is explicitly described in the docs as "a feature of CSS, not a bug" enabling both backward and forward compatibility.

## 2. Architecture

[Source: https://www.w3.org/TR/css-2026/] Architecturally, CSS is not a single spec but a federation of independently versioned **modules** (Selectors, Cascade, Flexbox, Grid, Color, Nesting, Containment, etc.), each progressing through the W3C maturity ladder at its own pace. The CSS Working Group publishes an annual **CSS Snapshot** Group Note (e.g., CSS Snapshot 2026) that names which module levels currently constitute "CSS" for implementers, grouped into tiers: modules with an "Official Definition" (e.g., Selectors Level 3, Flexbox, Grid, Cascading and Inheritance Level 4, Color Module Level 4), "Reliable Candidate Recommendations" with stable implementations but not yet Recommendation status (e.g., Grid Layout Level 2, Media Queries Level 4), and "Fairly Stable" design-complete modules awaiting further implementation experience.

[Source: https://www.w3.org/2004/02/Process-20040205/tr.html] Each module advances through W3C maturity stages: Working Draft (WD) → Candidate Recommendation (CR, requiring two independent interoperable implementations and a test suite to exit) → Proposed Recommendation (PR) → Recommendation (REC, the stable/maintenance stage where the WG maintains only an errata document).

[Source: https://developer.mozilla.org/en-US/docs/Web/API/CSS_Object_Model] The **CSS Object Model (CSSOM)** is the architectural bridge between CSS and JavaScript, analogous to the DOM for HTML: it exposes stylesheets, rules, and declarations as live JS objects (`CSSStyleSheet`, `CSSRule`, `CSSStyleRule`, `CSSStyleDeclaration`, `CSSMediaRule`, `CSSKeyframesRule`, `CSSFontFaceRule`, `CSSSupportsRule`, `CSSImportRule`, `CSSPageRule`, etc.), plus a more recent **CSS Typed Object Model** (`CSSStyleValue`, `CSSNumericValue`, `CSSUnitValue`, `CSSKeywordValue`, `CSSTransformValue`) for typed (rather than string-based) manipulation of CSS values.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_shadow_parts] For component-based architectures, CSS defines explicit **style-encapsulation boundaries** around Shadow DOM: by default styles inside a shadow root don't leak out and external styles don't penetrate in, except for (a) naturally inherited properties, (b) custom properties (CSS variables), which do cross the shadow boundary, (c) elements explicitly exposed via the `part` HTML attribute and styled from outside via the `::part()` pseudo-element, and (d) light-DOM content distributed into `<slot>`s, styleable from inside the shadow root via `::slotted()`. `:host`, `:host()`, and `:host-context()` let a component style its own host element from within its shadow tree.

## 3. APIs

[Source: https://developer.mozilla.org/en-US/docs/Web/API/CSS_Object_Model] CSS's primary programmatic surface is the CSSOM, accessed from JavaScript via `document.styleSheets`, `element.style` (a live `CSSStyleDeclaration`), `window.getComputedStyle(element)` (a read-only resolved-style view), and stylesheet mutation methods such as `CSSStyleSheet.insertRule()` / `.deleteRule()`.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@supports] The `@supports` at-rule (a "feature query") lets CSS itself branch on browser support for a property/value pair, an at-rule (`supports-at-rule()`), a selector (`supports-selector()`), or a font technology (`font-tech()`), enabling progressive enhancement authored directly in stylesheets. It is exposed to JS via the `CSSSupportsRule` interface and the `CSS.supports()` static method.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property] The `@property` at-rule (part of the CSS Houdini family of APIs) registers a custom property with an explicit `syntax` (type), `inherits` flag, and `initial-value`, giving custom properties type-checking and making them animatable — functionality equivalently available from JavaScript via `CSS.registerProperty()` (JS registration takes precedence if both are present, and the last `@property` rule with a given name wins among CSS-only registrations). [Version-sensitive] Baseline "Newly available" since July 2024, per MDN's Baseline compatibility indicator on the `@property` reference page — recent enough that older browsers won't support it.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties] **Custom properties** (`--name: value；`) are the other primary "API-like" surface: declared with a `--` prefix, they participate in the cascade and inherit like normal properties, and are read via the `var(--name, fallback)` function. `var()` may appear in any property value but not in selectors, property names, media-query conditions, or (per this guide) container-query conditions.

## 4. Configuration

[Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Getting_started] CSS has no build-time "configuration file" of its own; "configuring" CSS for a document means choosing how to attach it: (1) an **external stylesheet** via `<link rel="stylesheet" href="styles.css">` in `<head>` — MDN's explicitly recommended default, since one file can style many pages; (2) an **internal stylesheet** via a `<style>` element in `<head>`, which must be duplicated per page; (3) **inline styles** via the `style=""` attribute on an element, which MDN says is "strongly discouraged" except in narrow cases (restrictive CMS environments limited to HTML-only editing, HTML email compatibility, or dynamic styling applied by JavaScript).

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties] Site-wide "configuration" (theme tokens, design-system values) is idiomatically expressed via custom properties declared on `:root` and consumed with `var()` throughout a stylesheet, rather than through any external config mechanism.

Not documented / could not verify: MDN's Getting Started tutorial explicitly states it does not cover `@import` or `@charset` in that particular guide; this document does not fabricate details of those at-rules beyond what was independently verified elsewhere in this research pass.

## 5. Recommended patterns

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/box-sizing] MDN recommends the universal `box-sizing: border-box` reset ("`* { box-sizing: border-box; }`") as a best practice, stating it "makes dealing with the sizes of elements much easier, and generally eliminates a number of pitfalls you can stumble on while laying out your content." [Baseline: widely available since July 2015.]

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity] MDN recommends **cascade layers (`@layer`) over `!important`** for managing precedence, explicitly calling heavy `!important` use a workaround pattern in the specificity/cascade discussion, and recommending `:where()` to give third-party or reset CSS zero added specificity so it can be easily overridden.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Logical_properties_and_values (topic confirmed via search of the MDN "CSS logical properties and values" guide)] MDN recommends **logical properties** (`margin-inline-start`, `padding-block-end`, etc.) over physical directional properties (`margin-left`, `padding-bottom`) for layouts that need to adapt automatically to writing mode / text direction (e.g., RTL languages), since logical properties update automatically with the document's writing mode.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change] MDN recommends `will-change` be used only "as a last resort to try to deal with existing performance problems," not proactively, and to remove it (e.g., toggle it via JS on interaction start/end) rather than leave it applied indefinitely; targeting the smallest possible subtree is recommended over applying it broadly (e.g., to `<body>`).

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_shadow_parts] For component authors, the recommended pattern for exposing internal styling hooks without breaking encapsulation is the `part` attribute + `::part()` pseudo-element (plus `exportparts` for re-exposing parts through nested custom elements), rather than leaking global class-based styling into a shadow tree.

## 6. Anti-patterns

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change] MDN explicitly warns against **overusing `will-change`**: applying it to too many elements "results in excessive memory consumption and makes rendering more complex than necessary, which will cause even more of a slowdown" — an optimization applied prematurely can make performance worse, not better. It also warns against setting `will-change` inside `@keyframes` blocks (animated properties are already implicitly treated as changing).

[Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Getting_started] Inline styles are documented as an anti-pattern for general development: they mix presentational code into markup, are hard to maintain, and cannot be reused across elements/pages, which is why MDN restricts their recommended use to a few edge cases.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity] Overusing `!important` to win specificity fights is implicitly framed as an anti-pattern throughout MDN's cascade/specificity material — it inverts and complicates the cascade (its own precedence order reverses relative to layer order) and cascade layers are presented as the more maintainable alternative for controlling precedence, especially against third-party CSS.

[Inference, not confirmed in docs] Universal broad resets that fight the cascade (e.g., blanket `!important` overrides, deeply nested/high-specificity selector chains as a substitute for cascade layers or naming conventions) are a commonly cited anti-pattern in the wider CSS community, but this document only asserts what MDN/W3C state directly above; broader community anti-pattern lists (BEM violations, specificity wars, "CSS-in-JS vs. vanilla" debates) were not found documented as such in official CSSWG/MDN material and are therefore not claimed as officially documented anti-patterns.

## 7. Security

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Selectors/Privacy_and_:visited] The most significant, explicitly documented CSS-specific privacy/security issue is the **`:visited` selector history-sniffing attack**: because `:visited` styling once could differ arbitrarily from unvisited-link styling, a page could programmatically probe styling (e.g., via `getComputedStyle` or by measuring rendered layout/pixel differences) to detect a user's browsing history. Browser vendors mitigated this by restricting what `:visited` styling can reveal — `getComputedStyle()` and similar APIs are made to report values as though the link had never been visited, and CSS properties usable inside `:visited` rules are limited (broadly to `color`, `background-color`, `border-color`, `outline-color`, and the color parts of a few other properties), preventing layout-based side-channel leaks.

Not documented / could not verify: this research pass did not find an official W3C/CSSWG or MDN page specifically cataloguing broader "CSS injection" / data-exfiltration attack techniques (e.g., using attribute selectors to exfiltrate form input values via background-image requests) as a named security topic; such material exists in third-party security literature (e.g., OWASP) but per this project's sourcing rules that non-official material is not cited here as a primary source. Readers concerned with CSS-based data exfiltration should consult OWASP's own guidance directly rather than relying on this document, since it falls outside official CSS-maintainer documentation.

## 8. Performance

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Using] **CSS containment** (`contain` property) lets authors tell the browser that a subtree is independent from the rest of the page, so the browser can skip layout/paint/style work outside that subtree when only the subtree changes.

[Source: https://web.dev/articles/content-visibility] `content-visibility` (Google/Chrome team's web.dev, an official browser-vendor engineering blog, cited here as a secondary source alongside MDN's property reference) builds on containment: `content-visibility: auto` lets the browser skip layout and paint for off-screen content until it's needed, while keeping that content in the DOM and accessibility tree (unlike `visibility: hidden` or `display: none`) so it remains searchable/navigable. web.dev's own demos report up to a 7x rendering-performance improvement on initial load for long, chunked pages using `content-visibility: auto`.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change] `will-change` is CSS's explicit rendering-optimization hint API, letting authors pre-warn the browser about upcoming property changes (commonly `transform`, `opacity`) so the browser can do ahead-of-time compositing work — but MDN frames it as a targeted, temporary fix for measured problems, not a general-purpose performance lever (see Anti-patterns above for the overuse warning, which is itself part of the same official performance guidance).

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container] Container queries carry their own documented performance-relevant constraint: an element must be given `container-type` (establishing size containment) before it can be queried by `@container`, which is itself a containment-driven performance/architecture mechanism, not just a layout convenience.

## 9. Testing

[Source: https://web-platform-tests.org/test-suite-design.html] CSS's own "official" testing infrastructure is oriented at **browser conformance**, not application testing: the CSS Working Group maintains its conformance test suite inside the shared **web-platform-tests (WPT)** repository (primarily under its `css/` directory), used by browser vendors to verify their implementations match the specifications; tests are described as short, cross-platform, self-contained HTML pages that either programmatically report a pass/fail result or provide manual verification steps.

[Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Debugging_CSS] MDN's own testing/validation guidance for authors (as distinct from browser conformance testing) centers on the **W3C CSS Validator** (`https://jigsaw.w3.org/css-validator/`) and HTML Validator (`https://validator.w3.org/`) as first-line tools to catch syntax errors, since invalid CSS is otherwise silently ignored rather than raising visible errors (see Core concepts / error handling above).

Not documented / could not verify: MDN/W3C do not, in the material reviewed, prescribe an official unit-testing or visual-regression-testing methodology for authored CSS (e.g., snapshot testing, automated cross-browser diffing) — that space is occupied by third-party/ecosystem tools (Percy, Chromatic, BackstopJS, etc.) which fall outside this project's official-sources-only citation rule and are therefore not detailed here.

## 10. Deployment

Not documented / could not verify as an official CSS-spec topic: CSS itself has no "deployment" process — a stylesheet is deployed simply by being served as a static asset (typically with MIME type `text/css`) alongside the HTML that references it. [Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Getting_started] The only deployment-adjacent guidance found in official material is the linking mechanism itself (external `<link rel="stylesheet">` vs. inline/internal), which MDN frames as a maintainability choice rather than a deployment pipeline concern. Minification, bundling, critical-CSS extraction, and CDN delivery are standard industry practices for shipping CSS in production but are implemented by third-party build tooling (bundlers, minifiers) rather than being specified or documented by the CSS Working Group or MDN as part of the language itself; this document does not fabricate official guidance on those tools since none was found.

## 11. Migration

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Syntax/Error_handling] Because unrecognized declarations, values, and at-rule preludes are silently ignored rather than causing parse failures, CSS's own design supports incremental **feature migration via graceful fallback**: authors can declare an older syntax followed by a newer one for the same property (e.g., `display: inline-flex;` followed by `display: inline flex;`), and browsers that don't understand the newer syntax simply keep the last value they could parse, while browsers that do understand it apply the later (cascade-order-winning) declaration.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@supports] The **`@supports` feature query** is CSS's official mechanism for conditionally migrating to new features (progressive enhancement): authors gate new-syntax rule blocks behind a support check for a property/value pair, at-rule, selector, or font technology, so unsupported browsers fall back to previously-declared rules.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_nesting] **Native CSS nesting** (CSS Nesting Module Level 1) is documented by MDN as a migration target away from preprocessors: nesting is parsed natively by the browser rather than compiled ahead of time by tools like Sass/Less, with the `&` nesting selector required to reference the parent selector inside a nested block; MDN cross-references a dedicated "CSS nesting and specificity" guide because nesting can change how specificity is calculated compared to flattened, non-nested rules — a concrete migration gotcha when porting Sass/Less nested rules to native nesting.

[Source: https://developer.mozilla.org/en-US/docs/Glossary/Vendor_Prefix] Historically, **vendor-prefixed properties** (`-webkit-`, `-moz-`, `-ms-`) were CSS's migration mechanism for experimental features; MDN's current guidance is to use a prefixed alternative only if the standard (unprefixed) feature is unavailable, and states that Firefox's own `-moz-` extensions are now "mostly experimental or deprecated but kept for backward compatibility" and should be avoided on production sites — the modern replacement mechanism for testing unstable features is browser-specific "flags" rather than shipping vendor prefixes to production.

## 12. Version information

[Source: https://www.w3.org/TR/css-2026/; https://developer.mozilla.org/en-US/docs/Web/CSS] There is no single "CSS version number" post-CSS3 — CSS is versioned per-module (e.g., Selectors Level 4, Color Module Level 5, CSS Nesting Module Level 1, Grid Layout Level 2), and the annual **CSS Snapshot** Group Note (CSS Snapshot 2026 is the latest identified in this research pass, published by the CSS Working Group; prior editions include CSS Snapshot 2025, 2024, 2023, 2018) is the closest thing to an official "current state of CSS as a whole" reference, aimed at implementers rather than authors.

[Source: https://www.w3.org/2004/02/Process-20040205/tr.html] Individual modules progress through W3C maturity stages (Working Draft → Candidate Recommendation → Proposed Recommendation → Recommendation) independently and on no fixed release cadence; a module reaching "Recommendation" enters a maintenance phase where only errata are tracked.

[Source: https://developer.mozilla.org/en-US/docs/Glossary/Baseline/Compatibility] For practical "is this safe to use" versioning, MDN/the web-platform community use **Baseline** status rather than a CSS version number: "Widely available" means consistent support across Baseline browsers for at least 2.5 years; "Newly available" means it works in the latest stable version of each Baseline browser but may not work in older browsers/devices; "Limited availability" means it's not yet supported everywhere. This document tags several individual features above with their Baseline status (e.g., `box-sizing` widely available since July 2015; `@container` widely available, Baseline established February 2023; `@property` newly available since July 2024; `will-change` widely available since January 2020).

Not applicable / no LTS concept: [Inference, not confirmed in docs] CSS has no "LTS" or formal support-window concept analogous to software releases — browsers auto-update continuously and CSS's own backward-compatible error-handling design (see Core concepts) is the mechanism that substitutes for a support-window guarantee: old syntax generally continues to work indefinitely because the CSSWG avoids breaking changes to shipped syntax (see Breaking changes below).

## 13. Breaking changes

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Syntax/Error_handling] CSS's forward-compatible, error-tolerant parsing model is explicitly designed to avoid the kind of breaking changes seen in traditional software: unknown/invalid syntax is ignored rather than causing failures, so introducing new syntax does not break pages relying on old syntax, and old browsers encountering new syntax simply ignore what they don't understand.

Not documented / could not verify: this research pass did not find an official CSSWG "breaking changes" or "deprecations" changelog analogous to a software project's release notes. A general web search for CSSWG-documented deprecated/removed features in 2025–2026 surfaced only the CSS Snapshot documents (which describe current module status, not a changelog of removals) and did not surface a specific list of recently removed CSS syntax. [Source: https://www.w3.org/2004/02/Process-20040205/tr.html — general W3C process background only, not CSS-specific removals] Given CSS's documented error-handling philosophy above, the most defensible statement is: the CSSWG's process strongly disfavors ever removing previously-shipped, interoperably-implemented syntax, and "breaking changes" in CSS more typically take the form of new modules superseding old ones (e.g., new Grid Level 2 features layered on top of Grid Level 1) rather than removal of existing behavior. Unresolved: whether any specific CSS property/value combination was formally removed from a Recommendation-track spec in the 2024–2026 window was not confirmed against an official CSSWG changelog in this research pass.

## 14. Limitations

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties] `var()` cannot be used for property names, selectors, or in media-query / container-query conditions — only within property *values*, which is an explicit, documented constraint on CSS custom properties.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property] `@property` requires both `syntax` and `inherits` descriptors to be valid, and `initial-value` is required unless `syntax` is the universal `"*"`; the `initial-value` must be "computationally independent" (e.g., `10px` is valid, `3em` is not, since `em` depends on context) — a documented constraint on how custom properties can be typed.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Selectors/Privacy_and_:visited] `:visited` styling is deliberately limited by browsers to a small set of color-related properties and cannot be introspected via `getComputedStyle()` in a way that reveals true visited state — a hard, privacy-motivated limitation on what CSS/JS can jointly observe about link state.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Syntax/Error_handling] A single invalid selector in a comma-separated selector list invalidates the *entire* rule block in standard CSS selector lists (this is a documented limitation of ordinary selector lists); `:is()` and `:where()` use "forgiving" selector-list parsing as the documented exception, where only the invalid member is dropped rather than the whole rule.

[Inference, not confirmed in docs] Because CSS has no native module/import system beyond `@import` (which was not independently verified in depth in this pass) and no native way to scope class names without `@scope`/Shadow DOM, complex applications generally rely on external tooling (build-time bundlers, CSS Modules, preprocessors, or Shadow DOM/`@scope`) to manage naming collisions at scale — this is a widely understood practical limitation but is stated here as inference, not as an official documented limitation, since no official CSSWG/MDN page was found asserting it in those terms.

## 15. Debugging

[Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Debugging_CSS] MDN's official debugging workflow centers on browser DevTools (documented using Firefox DevTools as the reference implementation, described generically enough to apply to any modern browser's devtools): the **Rules view** lists all CSS rules applying to a selected element ordered from most- to least-specific, with overridden or invalid declarations shown crossed out; the **Layout view** visualizes the box model; declarations can be toggled on/off via checkboxes and edited live (including a color-swatch picker) without reloading the page; new properties can be added directly in the Rules view with autocomplete.

[Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Debugging_CSS] Documented debugging workflow/checklist: validate markup/CSS with the official W3C validators first (since invalid CSS fails silently, see Core concepts), check MDN browser-compatibility tables for property support, use DevTools to find cascade/specificity overrides, and build a minimal reduced test case (removing unrelated HTML/CSS/JS, e.g., in an online code-sharing tool) to isolate the root cause. MDN explicitly notes the DOM shown in DevTools reflects what the browser is *actually* rendering (including browser auto-corrections and JS-driven mutations), making it more reliable for debugging than reading the original source files.

[Source: https://firefox-source-docs.mozilla.org/devtools-user/page_inspector/how_to/examine_grid_layouts/index.html] Firefox DevTools additionally ships a dedicated **CSS Grid Inspector** for examining grid layouts, and (per the Debugging CSS learning guide) shows compatibility tooltips next to properties with known cross-browser compatibility issues, sourced from the MDN browser-compat-data project.

## 16. Integration

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_shadow_parts] CSS's officially documented integration surface with **Web Components** is `:host`, `:host()`, `:host-context()`, `::slotted()`, the `part`/`exportparts` HTML attributes, and the `::part()` pseudo-element — collectively the mechanism for styling across Shadow DOM boundaries while preserving encapsulation.

[Source: https://developer.mozilla.org/en-US/docs/Web/API/CSS_Object_Model] CSS integrates with **JavaScript** through the CSSOM: `document.styleSheets`, `element.style`, `window.getComputedStyle()`, and rule-manipulation methods (`insertRule`/`deleteRule`) let scripts read and mutate styles at runtime; the CSS Typed OM additionally lets script work with strongly-typed CSS values instead of strings.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property] The CSS **Houdini** family (of which `@property` is a part) is the officially documented lower-level integration point between CSS and JS for extending the CSS engine itself, with `@property` having a direct JS equivalent in `CSS.registerProperty()`.

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@supports] `@supports`/`CSS.supports()` is the documented integration point for feature-detecting CSS support from both CSS and JS, commonly used by libraries/polyfills to decide whether to apply fallback behavior.

Not documented / could not verify: official CSSWG/MDN material does not, in the pages reviewed, document integration with specific third-party build ecosystems (webpack/Vite/PostCSS/Sass/Tailwind) — those integrations are the province of each tool's own documentation, not the CSS specification or MDN's CSS reference, and are therefore out of scope for official-source citation here.

## 17. Production considerations

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change] Production performance guidance: apply `will-change` only to elements with an active, measured performance problem, keep the affected DOM subtree small, and remove the hint once the interaction/animation completes rather than leaving it applied statically in a stylesheet indefinitely (excessive/static use increases memory consumption and can create unwanted stacking contexts, actively hurting performance).

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Using; https://web.dev/articles/content-visibility] For large/long pages, `contain` and `content-visibility: auto` are the documented production techniques for reducing rendering cost of off-screen or independent content while preserving accessibility-tree/searchability — unlike `display: none`, which removes content from both rendering and accessibility trees.

[Source: https://developer.mozilla.org/en-US/docs/Glossary/Baseline/Compatibility] Before shipping a feature to production, MDN's Baseline status (widely available / newly available / limited availability) is the documented way to gauge safe browser-support boundaries for a given CSS feature; features that are only "newly available" or "limited availability" may need `@supports`-gated fallbacks in production (see Migration).

[Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Selectors/Privacy_and_:visited] Production stylesheets styling `:visited` links must stay within the browser-enforced limited property set (color-related properties only) — attempting to style layout-affecting properties on `:visited` will simply not take effect, by design, in production browsers.

[Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Getting_started] External stylesheets are the documented production-recommended delivery method over inline/internal styles, for cacheability and maintainability across multiple pages.

## Summary of version-sensitive facts to track

- [Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/box-sizing] `box-sizing` — Baseline widely available since **July 2015**.
- [Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container] `@container` container queries — Baseline widely available, established **February 2023**.
- [Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property] `@property` — Baseline **newly available since July 2024** (recent; expect gaps on older browsers).
- [Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change] `will-change` — Baseline widely available since **January 2020**.
- [Source: https://www.w3.org/TR/css-2026/] The CSS Working Group publishes a new **CSS Snapshot** Group Note roughly annually (2018, 2023, 2024, 2025, 2026 editions identified); it is the closest official document to a "current CSS version" statement and is aimed at implementers, not authors.
- [Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_nesting] Native **CSS nesting** (CSS Nesting Module Level 1) is comparatively new; MDN's nesting page carries a "last update November 2025" note in the page metadata found during this research, and MDN advises checking current compatibility tables before production use.
