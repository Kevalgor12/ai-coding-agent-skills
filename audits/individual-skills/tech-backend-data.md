## Cross-cutting finding — the "not yet authored" staleness pattern (fixed everywhere it was mechanical)

This exact pattern recurred across every sub-cluster in this batch, and in every case the fix was the same: a forward-referenced skill that has since been authored, with the referencing skill's text never updated.

- **postgresql, mysql, mongodb, clickhouse** — all four referenced `database-operations` (SK-DATA-003) and/or `search-integration` (SK-DATA-005) as "not yet authored." Both exist, authored one day after these four skills. **Fixed**: stale annotations corrected across all 8 files (4× skill.yaml + 4× SKILL.md); `grep -rn -i "not yet authored\|forward reference"` across all four directories now returns nothing; all four skill.yaml files re-validated with `yaml.safe_load`.
- **nodejs** — referenced `SK-TECH-express`/`SK-TECH-fastify` as "forthcoming, not yet authored." Both are fully authored (they're in this same batch). **Fixed** in `nodejs/SKILL.md`, with working links added.
- **python** — referenced `SK-AI-001` (llm-application-engineering) as "a forward reference — research-gap, not yet authored" in six locations (4 in skill.yaml, 2 in SKILL.md). This skill is fully authored (the AI/LLM domain's root skill, resolved the same day per the taxonomy). **Fixed** across all six locations, with a working link added; `python/skill.yaml` re-validated.
- **redis** — its three parent skills (`caching-strategy`, `realtime-communication`, `search-integration`, all now real) are still described as "forward references, not yet authored anywhere in this library" four separate times, including in a Tier-2 reference file. **Not fixed** — this one is architecture-adjacent rather than a one-line correction, because the stated rationale for redis staying fully self-contained ("can't yet borrow from them") no longer holds, and updating the framing properly requires re-deriving what redis should now defer vs. keep (see the duplication finding below). Reported for a follow-up pass.
- **opensearch** — describes its `SK-QA-004` (observability) tie-in as "a documented research gap... forward-referenced only" and instructs routing observability requests there "do not fabricate guidance." This is now wrong: `observability` was fully authored and its research gap explicitly marked **Resolved** two batches ago. (What remains a real, separate open gap is application-level resilience/fault-tolerance patterns — a different thing opensearch doesn't actually reference.) **Not fixed**, same reasoning as redis — requires a duplication-aware rewrite, not a one-line swap.

**Recommendation for a follow-up pass**: search the whole repo for "not yet authored" / "forward reference" / "research gap" and re-verify each hit against current `skills/` contents — this pattern was found in essentially every batch of this Step 28 review (see the other 5 batch reports too), not just this one.

Reported as a judgment call for the owning team (keep as-is per the decision-matrix, or narrow mongoose's `conflicts_with` and soften the decision-matrix's "mutual alternative" framing), not changed unilaterally — this exceeds the narrow "asymmetric pair" fix authority for this review.

## Overall assessment

Technology accuracy is strong across the batch — 15 of 16 skills had zero contradicted or fabricated technical claims against their cited research. The one exception (`nodejs`'s unsourced TypeScript-type-stripping version numbers) is a genuine, if narrow, SG-3 violation worth prioritizing for a follow-up research pass. The dominant theme, consistent with every other Step 28 batch, is staleness: several skills in this batch were authored before their own forward-referenced parents existed, and the "not yet authored" framing was never swept once those parents landed — in the redis/opensearch case, this isn't just a wording problem but has produced confirmed, concrete content duplication with the now-real parent skills (`caching-strategy`, `search-integration`), which is the single highest-value follow-up from this batch. The four-way ORM `conflicts_with` question and the three-runtime `conflicts_with` question are both genuine architectural judgment calls grounded in this project's own research rather than authoring errors, and were correctly left for a human decision rather than unilaterally rewritten.
