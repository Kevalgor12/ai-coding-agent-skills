## Purpose & scope

Write comments that carry real information and actively prevent comment
noise — including the specific noise patterns AI-generated code
introduces. This is a mandated, first-class skill in this library
alongside [git-conventions](../git-conventions/SKILL.md): every code-
producing skill composes with it rather than inventing its own commenting
convention. Prose documentation (READMEs, API docs, ADRs) belongs to
technical-documentation.

## When to use / When not to use

**Use** whenever writing or substantially editing source code, reviewing
code specifically for comment quality, or cleaning up AI-generated/auto-
generated code artifacts. **Do not use** for prose documentation, or for
a file whose established style legitimately uses a convention this skill
would otherwise flag (e.g. banner comments) — respect the local norm.

## Knowledge

**The single governing test for whether a comment should exist: does it
carry information the code itself cannot say?** The *why* — a hidden
constraint, a non-obvious invariant, a workaround for a specific bug,
behavior that would genuinely surprise a reader. Well-named identifiers
and clear structure already communicate the *what*; a comment restating
that is pure redundancy that will drift out of sync with the code the
first time it changes and nobody updates the comment.

**AI-generated code introduces a specific, recognizable family of comment
noise that a human author rarely produces on their own, and this skill
exists partly to actively counter it**: phase/step narration comments
(`// Step 1:`, `// Now we loop over...`) that describe the control flow
instead of explaining anything non-obvious about it; AI/tool signatures or
attribution embedded in code comments (`// Generated by...`, co-author
lines inside source rather than in commit metadata where they belong);
decorative banners (`////////`, ASCII separator bars) that add visual
noise without information; and comments that merely restate what the
adjacent code already says plainly. **These four patterns are the
concrete, checkable things to scan for** — not a vague "avoid unnecessary
comments" instruction.

**Matching the surrounding file's existing comment style and density is a
real, separate discipline from deciding what to comment** — a file that
already uses a denser or sparser commenting convention, or a legitimate
local banner convention, should be matched, not overridden by this
skill's own defaults. Consistency within a file matters more than any
single comment being individually "more correct" by this skill's general
rules.

**Preferring deletion over repair for a stale comment is a deliberate,
load-bearing rule, not a minor stylistic preference.** A comment that no
longer accurately describes the code it sits next to is actively worse
than no comment — it actively misleads a future reader. When a comment
has drifted from the code, the default action is to delete it (or rewrite
it to be accurate), never to leave it as-is out of caution about removing
something.

## Decision framework

1. **Does this comment explain something the code cannot say for
   itself** (why, a non-obvious constraint, an invariant, a specific-bug
   workaround, genuinely surprising behavior)? If not, it shouldn't exist.
2. **Is this a phase/step-narration comment, an AI/tool signature, a
   decorative banner, or a plain restatement?** If any of these, remove
   it — these are the four concrete, checkable noise patterns this skill
   exists to catch.
3. **Does the surrounding file have an established comment style/density
   (including a legitimate banner convention)?** If so, match it rather
   than imposing this skill's own default.
4. **Is an existing comment stale relative to the code it sits next to?**
   Delete or rewrite it — never leave a misleading comment in place out
   of caution.
5. **Is this prose documentation rather than an in-code comment**
   (a README, API doc, ADR)? Route to technical-documentation instead.

## Workflow

1. When writing or editing code, add a comment only where the why/
   constraint/invariant test is met.
2. When reviewing existing code for comment quality, scan specifically
   for the four noise patterns: step narration, AI/tool signatures,
   decorative banners, obvious restatement.
3. Check the file's existing comment style/density before applying a
   default; match the local convention.
4. Delete or rewrite any comment that has drifted from the code it
   describes.
5. Never comment code the way this skill would comment it if the file
   has already established a different, legitimate convention.

## Engineering rules

- A comment must carry information the code cannot say for itself — the
  why, not the what.
- Remove phase/step-narration comments, AI/tool signatures, decorative
  banners, and obvious-restatement comments on sight.
- Match the surrounding file's existing comment style and density.
- Prefer deleting a stale/redundant comment over "fixing" it to match
  code that changed around it.
- Never add an AI/tool signature or co-author attribution inside source
  comments — that belongs in commit metadata, not code.

## Trade-offs

None material — writing fewer, higher-value comments costs nothing
relative to writing more, lower-value ones; the discipline is purely
additive quality, not a trade-off between competing goods.

## Anti-patterns

- **Phase/step-narration comments** (`// Step 1:`, `// Now we loop
  over…`) describing control flow instead of explaining anything
  non-obvious.
- **AI/tool signatures or attribution embedded in code comments** —
  belongs in commit metadata, never in source.
- **Decorative banners** (`////////`, ASCII separator bars) adding visual
  noise without information.
- **Comments that merely restate what the code already says plainly.**
- **Leaving a stale comment in place** instead of deleting or correcting
  it once it no longer matches the code.

## Security

Not a primary concern for this skill's scope; a comment should never
embed a secret, credential, or sensitive internal detail — if code near a
comment reveals something sensitive, that's a
[security-engineering](../security-engineering/SKILL.md) finding, not a
commenting-style concern.

## Performance

Not applicable to this skill's scope.

## Testing

This skill's own correctness is verified by its evaluation criteria in
`skill.yaml` (fixture-based: producing a why comment where warranted,
producing none where not, flagging/removing the four noise patterns)
rather than a runtime test suite — there's no application code to test
here.

## Failure handling

- If a file's established style legitimately uses a convention this
  skill would otherwise flag, respect the local norm.
- If it's unclear whether a comment carries real information or is
  noise, err toward removing rather than leaving ambiguous noise in
  place.

## Escalation

None — this skill composes with every code-producing skill and has no
escalation path of its own beyond the code-producing skill's own
escalation rules.

## Outputs & verification

- **Outputs:** comments inserted, edited, or removed in source; review
  findings flagging comment noise.
- **Verify:** every kept comment explains something the code cannot say
  for itself; none of the four noise patterns are present; a file's
  legitimate existing style is preserved and matched.
